# 业务规则与状态机

## 认证与会话管理模块

### MVP Lite 适用性裁决

当前 MVP Lite 仅实施用户名密码注册、登录、`GET /api/v1/auth/me` 与短期 Access Token。Refresh Token、刷新、登出、服务端会话持久化及以下与其有关的状态机是后续增强设计；它们不得成为当前 MVP 的注册、登录或身份解析前置条件，也不得由当前 API 暴露。MVP 范围以 `.harness/wiki/01-governance/MVP scope and development boundaries.md` 为准。

### 模块职责与边界

- 负责账户注册、用户名密码登录、Access Token 签发与校验、Refresh Token 刷新与撤销，以及当前用户身份解析。
- 注册成功时必须在同一数据库事务中创建 `users` 和与其一对一关联的 `candidates` 记录。
- 仅负责身份与会话有效性；候选人资料是否可用于匹配或投递由“候选人资料准备模块”定义。
- 不提供游客身份，不允许客户端提交或指定自己的 `user_id`、`candidate_id`。

### 开发前置条件

| 前置条件 | 验收标准 | 不满足时 |
| --- | --- | --- |
| `users` 表与密码哈希策略 | 用户名唯一；密码仅保存强哈希，绝不保存明文 | 认证模块不得开始实现 |
| `candidates.user_id` 一对一约束 | `uq_candidate_user_id` 已迁移且可用 | 注册功能 blocked |
| Refresh Token 持久化设计 | 可保存 Token 哈希、用户 ID、签发与过期时间、撤销时间及当前轮换状态 | 登录、刷新、登出功能 blocked |
| Access Token 配置 | JWT 签名密钥、签发方、受众和有效期已配置，生产环境密钥来自安全配置 | 受保护接口不得上线 |
| 统一认证依赖 | 可从有效 Bearer Access Token 解析并复核 `user_id` 与 `candidate_id` | 任何受保护业务接口 blocked |

### 接口前置条件

| 接口 | 调用前置条件 | 成功后的关键结果 |
| --- | --- | --- |
| `POST /api/v1/auth/register` | 用户名未被占用；用户名和密码通过 Pydantic 与密码策略校验 | 原子创建用户与候选人，签发会话令牌 |
| `POST /api/v1/auth/login` | 用户存在；密码校验通过；用户存在唯一关联候选人 | 创建新会话并签发会话令牌 |
| `POST /api/v1/auth/refresh` | Refresh Token 存在、未过期、未撤销且为当前有效 Token | 轮换 Refresh Token 并签发新的 Access Token |
| `POST /api/v1/auth/logout` | Access Token 有效；Refresh Token 属于当前用户且未撤销 | 撤销该会话的 Refresh Token |
| `GET /api/v1/auth/me` | Access Token 有效；用户与候选人的一对一关系有效 | 返回当前用户和候选人的最小必要信息 |

### 会话状态机

会话状态以服务端保存的 Refresh Token 会话为准；Access Token 是短期凭证，其过期不等同于会话终止。

| 状态 | 含义 | 是否可访问受保护业务接口 | 是否可调用刷新接口 |
| --- | --- | --- | --- |
| `unauthenticated` | 未建立有效会话，或请求未携带有效 Access Token | 否 | 否 |
| `active` | Refresh Token 有效，且当前 Access Token 未过期 | 是 | 是 |
| `refreshable` | Refresh Token 有效，但 Access Token 已过期或不可用 | 否 | 是 |
| `revoked` | 会话已登出、被管理员撤销，或检测到 Refresh Token 重放 | 否 | 否 |
| `expired` | Refresh Token 已到期 | 否 | 否 |

### 合法状态迁移

| 触发事件 | 前置状态 | 后置状态 | 处理规则与审计要求 |
| --- | --- | --- | --- |
| 注册成功 | `unauthenticated` | `active` | 在创建用户与候选人的同一事务提交后创建会话；失败时整体回滚 |
| 登录成功 | `unauthenticated`、`revoked`、`expired` | `active` | 新建会话；不得复用已撤销或过期的 Refresh Token |
| Access Token 到期 | `active` | `refreshable` | 不写入业务数据；受保护接口返回 `401` |
| 成功刷新 | `active`、`refreshable` | `active` | 轮换 Refresh Token，旧 Token 立即撤销；记录会话轮换审计事件 |
| 主动退出登录 | `active`、`refreshable` | `revoked` | 仅撤销当前用户所属会话；记录撤销原因 `logout` |
| 检测到旧 Refresh Token 重放 | `active`、`refreshable` | `revoked` | 撤销该 Token 家族的全部会话；记录安全事件，不记录 Token 明文 |
| Refresh Token 到期 | `active`、`refreshable` | `expired` | 不允许刷新，要求重新登录 |

### 统一当前用户解析规则

1. 受保护路由必须通过统一认证依赖读取 `Authorization: Bearer <access_token>`。
2. 认证依赖必须校验 Token 格式、签名、签发方、受众和过期时间。
3. 验证通过后，必须通过 Repository 复核 `user_id` 存在，并取得其唯一关联的 `candidate_id`。
4. Service 仅接收可信的当前身份上下文；不得解析 Token，不得接受请求体中的当前用户或候选人 ID。
5. Repository 对候选人资源的读取和修改必须同时以资源 ID 和 `candidate_id` 校验归属。

### 错误处理与安全约束

| 场景 | API 行为 |
| --- | --- |
| 用户名已存在 | 返回 `409` |
| 注册或登录参数不合法 | 返回 `400` |
| 用户名或密码错误 | 返回 `401`，不区分用户不存在和密码错误 |
| Access Token 缺失、无效或过期 | 返回 `401` |
| Refresh Token 无效、已撤销或过期 | 返回 `401`，要求重新登录 |
| Refresh Token 不属于当前用户 | 返回 `403` |
| 当前用户缺少唯一关联候选人 | 返回 `401`，并记录不含敏感信息的内部异常 |

- Access Token 默认有效期为 30 分钟；Refresh Token 默认有效期为 14 天，具体配置不得由客户端决定。
- Refresh Token 在存储、日志、Prompt、追踪平台和错误响应中不得以明文出现；数据库仅保存其哈希值。
- 密码、密码哈希及任意 Token 均不得写入日志或接口响应的非必要字段。
- 所有认证接口均须具备限流、防暴力破解和超时控制；登录失败审计不得包含密码或 Token。

## 候选人资料准备模块

### 模块职责与边界

- 本模块仅负责候选人本人简历、附加资料、解析状态和已校验画像的受控读取；不计算、存储或返回 `profile_status`，也不读取求职目标。
- 正式简历是生成画像、岗位匹配和投递可使用的唯一简历资料来源。`candidate_documents` 是候选人明确选择、授权后可由 Agent 发送的系统内沟通消息附件，不得替代简历或生成画像；正文不自动进入 Agent/LLM 输入，也不提供 HR 直接读取或真实外发。
- 简历解析工作流在简历结构化校验成功时原子写入确定性画像。本模块不负责求职目标状态迁移、匹配、投递或沟通会话的准入。

### 资料事实边界

| 资料事实 | 判定规则 | 数据来源 |
| --- | --- | --- |
| 正式简历 | 归属当前候选人，且仅有 `processing`、`succeeded`、`failed` 三种解析状态 | `resumes` |
| 已校验简历画像 | 通过 `resume_id` 关联到归属当前候选人的 `parse_status = succeeded` 简历；与简历解析成功原子生成 | `resumes` → `candidate_profiles` |
| 附加资料 | 归属当前候选人的原始附件；不解析、不生成画像、不创建异步解析任务 | `candidate_documents` |

本模块不将资料事实聚合为候选人级求职状态，也不查询 `job_goals`。下游模块必须在其自身操作中，对所指定简历、画像、目标及其他资源逐项校验归属、存在性和业务状态。

### 开发前置条件

| 前置条件 | 验收标准 | 不满足时 |
| --- | --- | --- |
| 当前身份解析 | 可取得可信的 `candidate_id`，且不信任客户端传入的候选人 ID | 所有候选人资源操作返回安全错误 |
| 简历归属与解析状态查询 | Repository 可按 `candidate_id` 查询简历并读取 `parse_status` | 简历状态与画像查询不可提供 |
| 简历画像归属查询 | Repository 可经 `candidate_profiles.resume_id → resumes.candidate_id` 原子校验简历画像归属与简历解析成功状态 | 画像读取不可提供 |

### 业务接口前置条件与错误行为

| 业务操作 | 需要的资料条件 | 不满足时 |
| --- | --- | --- |
| 上传简历、上传附加资料 | 已认证 | 参数或文件格式非法返回 `ErrorCode.INVALID_REQUEST (400)`，超出大小限制返回 `ErrorCode.FILE_TOO_LARGE (413)` |
| 获取简历、画像、求职目标 | 已认证且资源归属当前候选人 | 无归属或不存在时返回安全的 `ErrorCode.RESOURCE_NOT_FOUND (404)` |
| 发起岗位匹配 | 指定 `goal_id` 为当前候选人的 `active` 目标；指定 `resume_id` 为已解析成功且已原子生成画像的可用简历 | 缺少指定资料或状态不合法返回 `ErrorCode.PRECONDITION_NOT_MET (409)`，`data` 可返回不含敏感信息的 `missing_requirements` |
| 创建投递 | 目标、简历及可选匹配结果均归属当前候选人且状态可用 | 前置条件不足返回 `ErrorCode.PRECONDITION_NOT_MET (409)`；归属不符返回安全的 `ErrorCode.RESOURCE_NOT_FOUND (404)` |
| 创建 AI 求职沟通会话 | 申请记录归属当前候选人，并满足沟通模块定义的资源与授权前置条件 | 前置条件不足返回 `ErrorCode.PRECONDITION_NOT_MET (409)`；归属不符返回安全的 `ErrorCode.RESOURCE_NOT_FOUND (404)` |

各下游模块如返回 `missing_requirements`，仅可使用该模块定义的枚举标识，不得返回简历原文、解析失败详情或其他敏感资料。该字段不是候选人资料准备模块的统一就绪状态契约。

### 数据一致性与安全约束

- 所有资料、画像和目标均必须由各自的 Repository 按当前 `candidate_id` 校验归属；Service、Agent 和 Workflow 不得直接访问 ORM Session 或编写 SQL。
- 候选人画像只能由已成功解析的简历在同一解析工作流中确定性派生；`target_job_titles` 必须来自通过 Pydantic 与业务规则校验的简历结构化结果，规范化为至少包含一个去除首尾空白的非空字符串列表；单个职位也必须保存为单元素列表，不得由画像模块推荐或推断。
- 简历解析等异步任务必须幂等、可重试、可追踪；重复回调不得产生重复画像或改变已完成简历的终态。
- 解析错误与资料状态不得在日志、Prompt、LangSmith 追踪或 API 响应中暴露简历原文、联系方式或其他个人敏感信息。

## 简历解析模块

### 模块职责与边界

- 负责将已上传的正式简历异步解析为经校验的结构化信息，并维护资源的 `parse_status`；终态失败原因只由关联 `AsyncTaskRun.failure_code` 的 `parse_failure_code` 表达。
- 适用资源仅为正式简历（`resumes`）。`candidate_documents` 是原始附件资源，不进入解析状态机或异步任务；岗位 JD 的启动导入不属于本模块；消息附件直接引用候选人明确选择的、归属一致的资料。
- 本模块不负责文件上传、对象存储实现、岗位匹配或投递；简历解析成功时在同一工作流中原子写入确定性画像，随后发出可被下游模块消费的状态变化。
- `parse_status` 是资源自身的持久化状态，当前只允许 `processing`、`succeeded`、`failed` 三种值；不得在代码或任务中自行增加 `queued`、`retrying` 等未建模状态。

### 解析前置条件

| 前置条件 | 验收标准 | 不满足时 |
| --- | --- | --- |
| 资源记录与归属 | 资源记录已创建；候选人资源可通过当前 `candidate_id` 校验归属 | 上传或解析请求返回安全错误，不创建解析任务 |
| 对象存储文件 | 关联对象可受控读取，且已通过上传校验 | 标记 `failed`，并在关联任务运行中记录 `parse_failure_code` |
| 异步任务追踪 | 存在当前资源的有效任务运行记录 | 解析功能 blocked |
| 解析器与外部依赖 | 对应解析器、OCR/LLM（适用时）配置、权限、配额和超时设置均已验证 | 不入队或按故障策略重试，不写入半成品结果 |
| 结构化结果 Schema | 每种资源类型具有 Pydantic 输出模型与业务校验规则 | LLM 或解析器输出不得入库 |

解析资源状态与任务运行状态必须分离；`candidate_documents` 上传只创建原始附件资源，不创建 `AsyncTaskRun`。可靠入队、任务执行、重试和超时以 [异步任务技术方案](../04-technical-solutions/Async%20task%20technical%20design.md) 为准。

### 解析资源状态机

| 状态 | 含义 | 可执行动作 | 对下游模块的影响 |
| --- | --- | --- | --- |
| `processing` | 文件已接收，解析任务已提交或正在执行；尚未产生可消费的完整结果 | 查询状态；由系统执行或重试解析任务 | 不得用于生成画像、匹配、投递或作为已解析 Agent 上下文 |
| `succeeded` | 文件已成功读取，解析结果已通过结构化与业务校验并完整持久化；对简历还要求对应画像已原子写入 | 查询、由授权下游模块消费 | 可作为对应业务流程的输入；简历已具备可用的确定性画像，不另设画像成功状态 |
| `failed` | 解析任务已达到失败终态，未产生可消费的完整结果；对简历包括画像生成、校验或原子写入未完成 | 通过关联终态任务查询 `parse_failure_code`；用户可重新上传新文件 | 不得被任何下游模块消费；不另设画像失败状态 |

资源状态不包含“排队中”或“重试中”：任务处于队列、执行或重试期间，资源始终保持 `processing`。资源状态与任务运行状态必须在查询接口中清晰区分，避免前端将任务重试误解为解析成功。

### 合法状态迁移

| 触发事件 | 前置状态 | 后置状态 | 处理规则与审计要求 |
| --- | --- | --- | --- |
| 上传完成并提交解析任务 | 无 | `processing` | 创建资源及其任务运行；具体可靠入队机制见异步任务技术方案 |
| 任务处于队列、执行或可重试故障 | `processing` | `processing` | 不写入终态失败原因或半成品业务结果 |
| 任务解析并校验成功 | `processing` | `succeeded` | 先完成结构化结果和业务校验；对简历还须原子持久化画像，再更新状态；发布解析成功事件 |
| 任务不可重试或重试耗尽 | `processing` | `failed` | 包括简历画像生成、校验或原子写入未完成；在任务运行中持久化 `parse_failure_code` 后更新资源状态；发布解析失败事件 |
| 用户重新上传文件 | `failed`、`processing`、`succeeded` | 新资源的 `processing` | 创建新的资源记录和任务；原资源不可被覆盖或回写，以保留审计与幂等边界 |

当前接口契约未定义“对同一资源重新解析”操作，因此禁止直接将 `failed` 或 `succeeded` 回写为 `processing`。如后续需要支持人工重跑或解析器升级，必须先补充显式 API、版本字段、审计事件和幂等规则。

### 资源类型的成功条件与下游触发

| 资源类型 | `succeeded` 的最低条件 | 成功后的允许触发 |
| --- | --- | --- |
| 简历 | 文件解析结果通过简历结构化校验，包含必填目标职位，且来源、归属和解析版本可追溯；对应确定性画像已原子写入 | 可作为匹配和沟通模块在其自身前置条件校验后的授权输入 |

解析成功不等于自动执行下游副作用。确定性画像是简历解析成功的原子组成部分；Embedding、向量索引和 Agent 消费均须由各自模块通过显式任务、权限校验与幂等规则执行。

### 异步实现约束

解析任务必须幂等、可重试、可追踪；重试与超时不得造成资源状态误判、重复画像或半成品业务结果。具体并发、重试、超时和回调处理以 [异步任务技术方案](../04-technical-solutions/Async%20task%20technical%20design.md) 为准。

### 接口行为、错误处理与安全约束

| 场景 | API 或任务行为 |
| --- | --- |
| 简历上传成功 | 返回资源 ID 与 `parse_status: processing`；不得同步承诺已解析成功 |
| 查询解析中的资源 | 返回 `processing`，不得返回部分结构化内容 |
| 查询解析失败的资源 | 返回 `failed` 和面向用户的脱敏错误标识；原始异常仅保存在受控内部任务记录中 |
| 使用未成功解析的简历发起匹配或投递 | 返回 `409`，不触发下游任务；画像不提供独立生成接口 |
| 非资源所有者查询、重试或消费候选人资源 | 返回安全的 `404`，不得泄漏资源是否存在 |
| 解析器或 LLM 返回非结构化/不合规数据 | 视为解析失败或可重试故障；不得直接写入业务表或驱动流程 |

- 未经脱敏的简历原文、文件地址、联系方式、凭证、模型原始响应及含敏感内容的异常堆栈不得进入应用日志、Celery 日志、LangSmith 追踪或 API 响应；Prompt 仅可包含完成任务所需的已脱敏数据。日志与追踪仅记录关联 ID、处理阶段、状态、脱敏失败分类、耗时和重试次数等最小诊断信息。
- 外部解析器、OCR、LLM、对象存储调用必须设置超时、重试与错误分类；工具输入必须经过文件类型、大小、归属和资源状态校验。
- 对象存储访问应使用短期、最小权限凭证；解析任务只能读取其被授权资源，不得根据模型输出拼接文件路径、SQL 或外部请求。

## 岗位管理模块

### 受控启动导入与候选人可见性

- 岗位和 JD 是系统共享资源，不归属于候选人；候选人无创建、更新、删除或导入权限，仅可读取 `parse_status = succeeded` 的快照。
- 受控启动导入命令仅从固定专属目录读取 Markdown 文件，单文件不得超过 1 MB。文件名不参与岗位元数据或 JD 内容解析，也不得向候选人暴露。
- 第 4 步导入命令只负责受控读取、大小校验和归档边界。第 5 步必须在结构化抽取及其裁定的 Schema/业务校验全部成功后，才在同一岗位管理事务中创建 `Job`、`JobDescription` 与 `parse_status = succeeded`。失败输入归档到受控失败目录，不创建业务资源；全部输入成功前应用不得标记为就绪。
- MVP 中既有 JD 不可更新；新输入只能新增资源。成功输入保留在受控成功归档目录，`raw_content` 持久化于 JD 聚合；候选人 API 不返回导入路径、文件名或失败诊断。
- 岗位 JD 的具体结构化抽取方案（确定性规则或外部模型）、结果 Schema 和失败处理留待第 5 步岗位 JD 解析分支裁决；不得默认复用简历解析的 MinerU、Celery 或 Worker 实现。

### 候选人资料发送与消息附件规则

1. 候选人可在发送系统内消息时显式选择并授权 `candidate_document`；Agent 据此创建系统内候选人消息和 `message_attachment` 引用，不复制文件或资料正文。
2. Repository 必须原子校验消息所属候选人与候选人资料的 `candidate_id` 一致，且资料对象存在；不一致或资料不存在时返回安全的 `404`。
3. Agent 可在候选人明确选择和授权后创建系统内附件引用，但不得自行上传未知文件、代替候选人选择资料、读取资料正文作为上下文，或将资料发送至真实外部对象。
4. 附加资料不替代正式简历，不参与候选人画像生成、求职状态派生或下游准入判定。
