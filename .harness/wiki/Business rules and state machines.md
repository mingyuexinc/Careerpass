# 业务规则与状态机

## 认证与会话管理模块

### MVP Lite 适用性裁决

当前 MVP Lite 仅实施用户名密码注册、登录、`GET /api/v1/auth/me` 与短期 Access Token。Refresh Token、刷新、登出、服务端会话持久化及以下与其有关的状态机是后续增强设计；它们不得成为当前 MVP 的注册、登录或身份解析前置条件，也不得由当前 API 暴露。MVP 范围以 `.harness/wiki/MVP scope and development boundaries.md` 为准。

### 模块职责与边界

- 负责账户注册、用户名密码登录、Access Token 签发与校验、Refresh Token 刷新与撤销，以及当前用户身份解析。
- 注册成功时必须在同一数据库事务中创建 `users` 和与其一对一关联的 `candidates` 记录。
- 仅负责身份与会话有效性；候选人资料是否可用于匹配或投递由“候选人资料准备模块”定义。
- 不提供游客身份，不允许客户端提交或指定自己的 `user_id`、`candidate_id`。

### 开发前置条件

| 前置条件 | 验收标准 | 不满足时 |
| --- | --- | --- |
| `users` 表与密码哈希策略 | 用户名唯一；密码仅保存强哈希，绝不保存明文 | 认证模块不得开始实现 |
| `candidates.user_id` 一对一约束 | `uq_candidate_user_id` 已迁移且可用 | 注册功能 blocked |
| Refresh Token 持久化设计 | 可保存 Token 哈希、用户 ID、签发与过期时间、撤销时间及当前轮换状态 | 登录、刷新、登出功能 blocked |
| Access Token 配置 | JWT 签名密钥、签发方、受众和有效期已配置，生产环境密钥来自安全配置 | 受保护接口不得上线 |
| 统一认证依赖 | 可从有效 Bearer Access Token 解析并复核 `user_id` 与 `candidate_id` | 任何受保护业务接口 blocked |

### 接口前置条件

| 接口 | 调用前置条件 | 成功后的关键结果 |
| --- | --- | --- |
| `POST /api/v1/auth/register` | 用户名未被占用；用户名和密码通过 Pydantic 与密码策略校验 | 原子创建用户与候选人，签发会话令牌 |
| `POST /api/v1/auth/login` | 用户存在；密码校验通过；用户存在唯一关联候选人 | 创建新会话并签发会话令牌 |
| `POST /api/v1/auth/refresh` | Refresh Token 存在、未过期、未撤销且为当前有效 Token | 轮换 Refresh Token 并签发新的 Access Token |
| `POST /api/v1/auth/logout` | Access Token 有效；Refresh Token 属于当前用户且未撤销 | 撤销该会话的 Refresh Token |
| `GET /api/v1/auth/me` | Access Token 有效；用户与候选人的一对一关系有效 | 返回当前用户和候选人的最小必要信息 |

### 会话状态机

会话状态以服务端保存的 Refresh Token 会话为准；Access Token 是短期凭证，其过期不等同于会话终止。

| 状态 | 含义 | 是否可访问受保护业务接口 | 是否可调用刷新接口 |
| --- | --- | --- | --- |
| `unauthenticated` | 未建立有效会话，或请求未携带有效 Access Token | 否 | 否 |
| `active` | Refresh Token 有效，且当前 Access Token 未过期 | 是 | 是 |
| `refreshable` | Refresh Token 有效，但 Access Token 已过期或不可用 | 否 | 是 |
| `revoked` | 会话已登出、被管理员撤销，或检测到 Refresh Token 重放 | 否 | 否 |
| `expired` | Refresh Token 已到期 | 否 | 否 |

### 合法状态迁移

| 触发事件 | 前置状态 | 后置状态 | 处理规则与审计要求 |
| --- | --- | --- | --- |
| 注册成功 | `unauthenticated` | `active` | 在创建用户与候选人的同一事务提交后创建会话；失败时整体回滚 |
| 登录成功 | `unauthenticated`、`revoked`、`expired` | `active` | 新建会话；不得复用已撤销或过期的 Refresh Token |
| Access Token 到期 | `active` | `refreshable` | 不写入业务数据；受保护接口返回 `401` |
| 成功刷新 | `active`、`refreshable` | `active` | 轮换 Refresh Token，旧 Token 立即撤销；记录会话轮换审计事件 |
| 主动退出登录 | `active`、`refreshable` | `revoked` | 仅撤销当前用户所属会话；记录撤销原因 `logout` |
| 检测到旧 Refresh Token 重放 | `active`、`refreshable` | `revoked` | 撤销该 Token 家族的全部会话；记录安全事件，不记录 Token 明文 |
| Refresh Token 到期 | `active`、`refreshable` | `expired` | 不允许刷新，要求重新登录 |

### 统一当前用户解析规则

1. 受保护路由必须通过统一认证依赖读取 `Authorization: Bearer <access_token>`。
2. 认证依赖必须校验 Token 格式、签名、签发方、受众和过期时间。
3. 验证通过后，必须通过 Repository 复核 `user_id` 存在，并取得其唯一关联的 `candidate_id`。
4. Service 仅接收可信的当前身份上下文；不得解析 Token，不得接受请求体中的当前用户或候选人 ID。
5. Repository 对候选人资源的读取和修改必须同时以资源 ID 和 `candidate_id` 校验归属。

### 错误处理与安全约束

| 场景 | API 行为 |
| --- | --- |
| 用户名已存在 | 返回 `409` |
| 注册或登录参数不合法 | 返回 `400` |
| 用户名或密码错误 | 返回 `401`，不区分用户不存在和密码错误 |
| Access Token 缺失、无效或过期 | 返回 `401` |
| Refresh Token 无效、已撤销或过期 | 返回 `401`，要求重新登录 |
| Refresh Token 不属于当前用户 | 返回 `403` |
| 当前用户缺少唯一关联候选人 | 返回 `401`，并记录不含敏感信息的内部异常 |

- Access Token 默认有效期为 30 分钟；Refresh Token 默认有效期为 14 天，具体配置不得由客户端决定。
- Refresh Token 在存储、日志、Prompt、追踪平台和错误响应中不得以明文出现；数据库仅保存其哈希值。
- 密码、密码哈希及任意 Token 均不得写入日志或接口响应的非必要字段。
- 所有认证接口均须具备限流、防暴力破解和超时控制；登录失败审计不得包含密码或 Token。

## 候选人资料准备模块

### 模块职责与边界

- 定义候选人资料是否已满足后续求职操作的最低前置条件，并向认证接口和业务 Service 提供派生的 `profile_status`。
- `profile_status` 是派生业务状态，不在 `candidates` 表中持久化；每次应基于当前候选人已归属的简历、画像和求职目标计算。
- 正式简历是生成画像、岗位匹配和投递的唯一资料来源；`candidate_documents` 仅为补充材料或 Agent 上下文，不得替代简历或改变准备度判定。
- 本模块不负责简历文件解析、画像内容生成或求职目标的具体状态迁移；分别由文档解析、画像生成和求职目标管理模块负责。

### 准备度事实与判定规则

| 事实 | 判定规则 | 数据来源 |
| --- | --- | --- |
| 可用简历 | 至少存在一份归属当前候选人且 `parse_status = succeeded` 的简历 | `resumes` |
| 可用画像 | 存在一份通过 `resume_id` 关联到该候选人的可用简历的画像 | `candidate_profiles` → `resumes` |
| 活跃求职目标 | 至少存在一份归属当前候选人且 `status = active` 的求职目标 | `job_goals` |

`profile_status` 的计算顺序如下：

1. 同时满足“可用简历、可用画像、活跃求职目标”时，为 `ready`。
2. 不满足 `ready`，且不存在可用简历、没有处于 `processing` 的简历、但存在至少一份解析失败简历时，为 `blocked`。
3. 其余情况均为 `incomplete`，包括新注册、尚未上传简历、简历仍在解析中、已有可用简历但画像或活跃求职目标缺失。

候选人可能拥有多份简历、画像和求职目标；`ready` 仅表示其具备进行求职操作的基本能力，不代表任意指定的简历或目标都可使用。涉及 `resume_id`、`profile_id` 或 `goal_id` 的操作仍须逐项校验其归属与状态。

### 开发前置条件

| 前置条件 | 验收标准 | 不满足时 |
| --- | --- | --- |
| 当前身份解析 | 可取得可信的 `candidate_id`，且不信任客户端传入的候选人 ID | 所有候选人资源操作 blocked |
| 简历归属与解析状态查询 | Repository 可按 `candidate_id` 查询简历并读取 `parse_status` | 准备度计算 blocked |
| 画像归属查询 | Repository 可经 `candidate_profiles.resume_id → resumes.candidate_id` 原子校验画像归属 | 画像读取、匹配功能 blocked |
| 活跃目标查询 | Repository 可按 `candidate_id` 查询 `active` 求职目标 | 准备度计算 blocked |
| 资料状态重算入口 | 简历解析完成/失败、画像生成、求职目标变更后，可重新计算准备度 | `profile_status` 不得对外承诺 |

### 准备度状态机

| 状态 | 含义 | 允许操作 | 禁止操作 |
| --- | --- | --- | --- |
| `incomplete` | 资料尚未满足 `ready` 条件，但可通过继续上传、等待解析、生成画像或创建目标补齐 | 上传和查看资料、查看解析状态、创建或查看求职目标 | 发起匹配、创建投递、创建新的 AI 求职沟通会话 |
| `ready` | 存在可用简历、与其关联的可用画像和活跃求职目标 | `incomplete` 的全部操作，以及发起匹配、创建投递、创建新的 AI 求职沟通会话 | 无；具体业务操作仍须校验所指定资源 |
| `blocked` | 没有可用简历，且当前没有解析中的简历，已有简历均未成功解析 | 查看失败原因、重新上传简历、查看资料 | 发起匹配、创建投递、创建新的 AI 求职沟通会话 |

读取既有简历、目标、匹配结果、投递记录或会话时，不得仅因当前准备度不是 `ready` 而拒绝；只要当前候选人拥有该资源，即应按资源自身状态与归属规则返回。

### 合法状态迁移

| 触发事件 | 前置状态 | 后置状态 | 处理规则 |
| --- | --- | --- | --- |
| 注册并创建候选人 | 无 | `incomplete` | 新候选人尚无简历、画像与求职目标 |
| 上传新简历 | `incomplete`、`blocked`、`ready` | 重新计算 | 新简历初始为 `processing`；已有满足条件的资料仍存在时必须保持 `ready` |
| 简历解析成功 | 任意状态 | 重新计算 | 可触发画像生成；在关联画像与活跃目标均已存在前通常为 `incomplete` |
| 简历解析失败 | 任意状态 | 重新计算 | 记录脱敏失败原因；只有不存在可用简历且无解析中简历时才进入 `blocked` |
| 为可用简历生成画像成功 | `incomplete`、`ready` | 重新计算 | 画像必须经结构化校验后写入，且其来源简历必须归属当前候选人并已解析成功 |
| 创建或恢复活跃求职目标 | `incomplete`、`ready` | 重新计算 | 若其他条件已满足，可进入或保持 `ready` |
| 最后一个活跃求职目标变为 `achieved` 或 `abandoned` | `ready`、`incomplete` | `incomplete` | 既有匹配、投递与会话不删除；仅禁止新的依赖活跃目标的操作 |
| 删除或失去可用画像/简历 | `ready`、`incomplete` | 重新计算 | 若无可用简历且满足失败条件则为 `blocked`，否则为 `incomplete` |

“重新计算”必须在 Service 通过 Repository 读取全部事实后完成；不得仅根据一次异步任务回调或客户端传入状态直接更新候选人状态。

### 业务接口前置条件与错误行为

| 业务操作 | 需要的资料条件 | 不满足时 |
| --- | --- | --- |
| 上传简历、上传附加资料 | 已认证 | 不以 `profile_status` 限制；参数非法返回 `400` |
| 获取简历、画像、求职目标 | 已认证且资源归属当前候选人 | 无归属或不存在时返回安全的 `404` |
| 生成候选人画像 | 指定 `resume_id` 归属当前候选人且解析成功 | 不满足返回 `409`；不得为解析失败或他人简历生成画像 |
| 发起岗位匹配 | `profile_status = ready`；指定 `goal_id` 为当前候选人的 `active` 目标；指定 `resume_id` 已解析成功且存在对应可用画像 | 缺少资料或状态不合法返回 `409`，`data` 可返回不含敏感信息的 `missing_requirements` |
| 创建投递 | `profile_status = ready`；目标、简历及可选匹配结果均归属当前候选人且状态可用 | 前置条件不足返回 `409`；归属不符返回安全的 `404` |
| 创建 AI 求职沟通会话 | `profile_status = ready`；申请记录归属当前候选人 | 前置条件不足返回 `409`；归属不符返回安全的 `404` |

`missing_requirements` 仅可返回枚举标识，例如 `usable_resume`、`usable_profile`、`active_job_goal`，不得返回简历原文、解析失败详情或其他敏感资料。

### 数据一致性与安全约束

- 所有资料、画像和目标均必须由 Repository 按当前 `candidate_id` 校验归属；Service、Agent 和 Workflow 不得直接访问 ORM Session 或编写 SQL。
- 候选人画像只能由已成功解析的简历生成；LLM 输出必须经 Pydantic 结构化校验和业务规则校验后方可写入。
- 简历解析、画像生成等异步任务必须幂等、可重试、可追踪；重复回调不得产生重复画像或错误地降低已 `ready` 候选人的准备度。
- 解析错误与资料状态不得在日志、Prompt、LangSmith 追踪或 API 响应中暴露简历原文、联系方式或其他个人敏感信息。

## 文档解析模块

### 模块职责与边界

- 负责将已上传的文件异步解析为经校验的结构化信息，并维护资源的 `parse_status` 与脱敏后的失败原因。
- 适用资源为正式简历（`resumes`）、候选人附加资料（`candidate_documents`）、岗位 JD（`job_descriptions`）和消息附件（`message_attachments`）。
- 本模块不负责文件上传、对象存储权限、候选人画像生成、岗位匹配或投递；解析成功后仅发出可被下游模块消费的状态变化。
- `parse_status` 是资源自身的持久化状态，当前只允许 `processing`、`succeeded`、`failed` 三种值；不得在代码或任务中自行增加 `queued`、`retrying` 等未建模状态。

### 解析前置条件

| 前置条件 | 验收标准 | 不满足时 |
| --- | --- | --- |
| 资源记录与归属 | 资源记录已创建；候选人资源可通过当前 `candidate_id` 校验归属 | 上传或解析请求返回安全错误，不创建解析任务 |
| 对象存储文件 | 文件存在、可在受限超时内读取，且 MIME 类型、文件大小和扩展名符合白名单 | 标记 `failed` 并记录脱敏失败原因 |
| 异步任务追踪 | 每次解析任务具备可查询的任务 ID、资源类型、资源 ID、尝试次数、状态和失败原因 | 解析功能 blocked |
| 解析器与外部依赖 | 对应解析器、OCR/LLM（适用时）配置、权限、配额和超时设置均已验证 | 不入队或按故障策略重试，不写入半成品结果 |
| 结构化结果 Schema | 每种资源类型具有 Pydantic 输出模型与业务校验规则 | LLM 或解析器输出不得入库 |

异步任务追踪是实现前置条件：资源表中的 `parse_status` 仅描述资源状态，不能替代 Celery 任务的任务 ID、重试次数和执行失败记录。该追踪模型须在具体实现前补充到数据模型与迁移方案中。

### 解析资源状态机

| 状态 | 含义 | 可执行动作 | 对下游模块的影响 |
| --- | --- | --- | --- |
| `processing` | 文件已接收，解析任务已提交或正在执行；尚未产生可消费的完整结果 | 查询状态；由系统执行或重试解析任务 | 不得用于生成画像、匹配、投递或作为已解析 Agent 上下文 |
| `succeeded` | 文件已成功读取，解析结果已通过结构化与业务校验并完整持久化 | 查询、由授权下游模块消费 | 可作为对应业务流程的输入；简历可触发画像生成 |
| `failed` | 解析任务已达到失败终态，未产生可消费的完整结果 | 查询脱敏失败原因；用户可重新上传新文件 | 不得被任何下游模块消费 |

资源状态不包含“排队中”或“重试中”：任务处于队列、执行或重试期间，资源始终保持 `processing`。资源状态与任务运行状态必须在查询接口中清晰区分，避免前端将任务重试误解为解析成功。

### 合法状态迁移

| 触发事件 | 前置状态 | 后置状态 | 处理规则与审计要求 |
| --- | --- | --- | --- |
| 上传完成并提交解析任务 | 无 | `processing` | 在同一事务中创建资源记录与可靠入队记录；不得出现资源已提交但任务永久丢失的情况 |
| 任务遇到可重试故障 | `processing` | `processing` | 记录任务尝试与脱敏原因，按有限退避策略重试；不写入部分解析结果 |
| 任务解析并校验成功 | `processing` | `succeeded` | 先完成结构化结果和业务校验，再原子持久化结果并更新状态；发布解析成功事件 |
| 任务不可重试或重试耗尽 | `processing` | `failed` | 持久化脱敏失败原因与任务失败状态；发布解析失败事件 |
| 用户重新上传文件 | `failed`、`processing`、`succeeded` | 新资源的 `processing` | 创建新的资源记录和任务；原资源不可被覆盖或回写，以保留审计与幂等边界 |

当前接口契约未定义“对同一资源重新解析”操作，因此禁止直接将 `failed` 或 `succeeded` 回写为 `processing`。如后续需要支持人工重跑或解析器升级，必须先补充显式 API、版本字段、审计事件和幂等规则。

### 资源类型的成功条件与下游触发

| 资源类型 | `succeeded` 的最低条件 | 成功后的允许触发 |
| --- | --- | --- |
| 简历 | 文件解析结果通过简历结构化校验，且来源、归属和解析版本可追溯 | 候选人资料准备度重算；可创建或更新对应画像生成任务 |
| 候选人附加资料 | 解析结果通过资料类型对应 Schema 校验 | 可作为授权 Agent 的补充上下文；重算资料展示状态 |
| 岗位 JD | 结构化岗位信息通过岗位 Schema 与字段校验 | 可生成岗位画像或进入匹配候选池 |
| 消息附件 | 解析结果通过附件类型 Schema 校验，且附件归属会话和消息均有效 | 在授权范围内作为沟通 Agent 上下文 |

解析成功不等于自动执行下游副作用。画像生成、Embedding、向量索引和 Agent 消费均须由各自模块通过显式任务、权限校验与幂等规则执行。

### 幂等、重试与并发规则

- 解析任务的幂等键必须至少包含资源类型和资源 ID；同一资源的重复投递、重复回调或 Celery 至少一次投递不得生成重复结构化记录、重复画像或重复索引。
- 同一资源同一时刻只允许一个有效解析执行权。任务领取、状态写入和完成回调必须使用原子条件更新或等价的并发控制。
- 可重试错误仅限网络超时、依赖暂不可用、限流等临时故障；文件损坏、格式不支持、Schema 校验失败等确定性错误应直接失败或在有限次数后失败。
- 重试次数、退避间隔和总超时必须可配置。超过总超时的 `processing` 任务须由监控任务标记为 `failed` 并写入脱敏原因。
- 任务成功回调仅在资源仍处于 `processing` 且归属链有效时生效；对 `succeeded`、`failed` 或已失效资源的重复回调必须安全忽略并记录审计信息。

### 接口行为、错误处理与安全约束

| 场景 | API 或任务行为 |
| --- | --- |
| 上传成功 | 返回资源 ID 与 `parse_status: processing`；不得同步承诺已解析成功 |
| 查询解析中的资源 | 返回 `processing`，不得返回部分结构化内容 |
| 查询解析失败的资源 | 返回 `failed` 和面向用户的脱敏错误标识；原始异常仅保存在受控内部任务记录中 |
| 使用未成功解析的简历生成画像、匹配或投递 | 返回 `409`，不触发下游任务 |
| 非资源所有者查询、重试或消费候选人资源 | 返回安全的 `404`，不得泄漏资源是否存在 |
| 解析器或 LLM 返回非结构化/不合规数据 | 视为解析失败或可重试故障；不得直接写入业务表或驱动流程 |

- 解析原文、文件地址、联系方式和其他个人敏感信息不得进入应用日志、Celery 日志、Prompt、LangSmith 追踪或 API 响应。
- 外部解析器、OCR、LLM、对象存储调用必须设置超时、重试与错误分类；工具输入必须经过文件类型、大小、归属和资源状态校验。
- 对象存储访问应使用短期、最小权限凭证；解析任务只能读取其被授权资源，不得根据模型输出拼接文件路径、SQL 或外部请求。
