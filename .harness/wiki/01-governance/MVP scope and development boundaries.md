# MVP 范围与开发边界

## 1. 文档目的与适用范围

本文件是 Careerpass MVP 的范围裁决基线，用于判断需求、设计、数据模型变更和开发任务是否进入当前版本。

- MVP 的唯一目标：验证候选人可在系统内完成“简历 → 画像 → 岗位匹配 → 投递记录 → 进度与沟通”的 Agent 核心求职闭环。
- 本文件优先于未明确范围的实现细节：需求未列入“本期范围”时，不得因技术完整性或未来生产需要而纳入 MVP。
- 已列入“延期范围”的能力可以保留设计记录，但不是 MVP 开发任务的前置条件，也不得阻塞核心闭环交付。
- 本文件不替代业务模型、数据模型、接口协议和状态机规范；这些文档仅对已进入 MVP 范围的能力进行细化。

## 2. MVP 用户、环境与成功标准

### 2.1 目标用户与运行环境

| 项目 | MVP 裁决 |
| --- | --- |
| 目标用户 | 开发者本人 |
| 使用规模 | 仅用于开发者本人测试，或向单个可信 VIP 进行受控演示；不面向公开用户，不以高并发、多租户运营或公开注册增长为目标 |
| 数据类型 | 仅允许测试用户主动上传已脱敏的候选人文件，包括正式简历和候选人附加资料；不得包含真实姓名、联系方式、证件号码、精确住址等直接身份信息。MVP 不建设脱敏确认、自动识别、自动脱敏或修复隐私信息的能力；上传前脱敏不替代系统侧受控访问与最小化暴露责任。 |
| 岗位来源 | 由受控启动导入命令从专属目录导入测试人员手工维护的岗位 JD；不依赖公开网络爬取、第三方平台同步或候选人侧录入 |
| 沟通对象 | 系统内模拟 HR 或测试数据；不直接向真实招聘方发送消息 |
| 外部投递 | 不执行真实投递；仅创建和管理系统内投递记录 |

### 2.2 MVP 成功标准

对任一已认证候选人，系统应支持以下完整闭环，并可在测试环境重复验证：

1. 注册或登录后取得当前候选人身份。
2. 上传简历；异步解析成功即代表结构化候选人画像已在同一工作流中原子生成。
3. 创建至少一个活跃求职目标，并查询至少一个已导入且已解析的岗位 JD。
4. 使用指定简历和求职目标发起岗位匹配，获得结构化、可解释的匹配结果。
5. 基于候选人拥有的岗位、目标、简历和可选匹配结果创建系统内投递记录。
6. 按合法状态更新投递进度，并创建与该投递记录关联的 AI 沟通会话。
7. 候选人不能读取或修改其他候选人的资料、匹配、投递、会话或消息。

## 3. 本期范围

### 3.1 模块最小交付边界

| 交付单元 | 规范模块 | 模块类型 | 技术能力交付 | 业务能力交付 | MVP 明确不要求 |
| --- | --- | --- | --- | --- | --- |
| G1 | 认证与用户初始化 | 业务模块（身份域，含公共基线） | 密码安全存储、短期 Token 签发与验证、可信 `CurrentIdentity`、Repository/事务边界和统一安全响应 | 用户名密码注册、登录、`/auth/me`，并在注册时原子创建 User 与 Candidate | Refresh Token、设备管理、长期会话、Token 轮换、密码找回、第三方登录、管理员账号管理 |
| G2 | 候选人资料准备 | 业务模块（候选人资料域） | 文件类型与大小校验、受控对象存储、内容摘要去重、归属校验、受控读取和无引用对象清理 | 本人正式简历与附加资料的上传、列表和解析状态查询；上传简历后提交 `ResumeParseRequest` | 求职状态/就绪状态派生、候选人画像生成或查询、匹配/投递/沟通准入、手工编辑复杂画像、跨简历画像版本管理、资料完整度评分体系、目标职位推荐 |
| G3 | 简历解析 | 技术能力模块（简历解析能力） | 受控资源读取、Dispatcher/Worker、租约、幂等、有限重试、超时与安全失败分类、MinerU 文档提取、Qwen 结构化输出、Pydantic 与业务规则校验 | 对正式简历执行受控异步解析，并原子生成候选人画像和简历终态 | 自动脱敏、人工脱敏确认或修复、OCR 优化、批量解析、人工标注后台、复杂文档格式全覆盖 |
| G4 | 岗位 JD 解析与入库闭环 | 跨模块集成闭环（岗位 JD 解析能力 + 岗位目录领域） | 从指定目录读取开发者准备的 JD、结构化抽取、Schema 与业务规则校验、岗位/JD 聚合持久化、只读查询与状态校验 | 根据指定目录中的岗位 JD 文件完成解析；解析成功后持久化岗位/JD，并提供已解析成功的 JD 快照 | HR 侧岗位管理系统、岗位爬取、第三方平台同步、自动去重、企业/招聘方管理 |
| G5 | 求职目标 | 业务模块（求职目标域） | 归属校验、Repository/事务边界、状态机校验和 `ActiveGoalSnapshot` 契约 | 创建和获取当前活跃求职目标、维护基础过滤条件，并执行 `active / achieved / abandoned` 合法状态迁移 | 多目标优先级、目标协作、复杂策略推荐 |
| G6 | 岗位匹配 | 业务模块（匹配域） | 已解析画像/JD/目标的版本化输入快照、R0 结构化过滤与可解释评分、异步执行与结果追踪 | 基于候选人画像、简历、活跃目标与已解析岗位发起匹配，并查询结构化、可解释的匹配结果 | 差距诊断或补齐建议、生产级召回体系、个性化在线学习、A/B 实验、全量向量索引运营 |
| G7 | 投递与进度 | 业务模块（投递域） | 资源前置校验、投递状态机、`Progress Event` 持久化与审计记录 | 创建系统内投递记录，并按合法状态更新投递进度 | 向招聘平台真实投递、自动跟进、Offer 文件处理、提醒系统 |
| G8 | AI 求职沟通 | 业务模块（沟通域） | 代码注册工作流、授权闸门、结构化 LLM 输出校验、会话/消息持久化与审计 | 基于已授权投递记录创建系统内会话，生成候选人回复草稿或模拟回复 | 真实外部消息发送、自动代投递、无人确认的对外承诺、跨平台 IM 接入 |

#### 模块耦合裁决（开发前置检查）

本 MVP 中，**内部耦合**指一个模块为了完成自身交付，必须调用、读取、写入或编排另一个业务模块的内部实现、Repository、持久化模型或任务生命周期。仅将已校验的请求、资源引用或不可变结果快照作为输入，或仅返回已声明的响应、事件或结果，不构成内部耦合。共享认证、Repository、对象存储、异步任务和工作流运行能力属于技术使能能力；业务模块只能使用其公开抽象和契约，不得依赖其实现细节。

| 模块 | 审阅结论 | 边界裁决 |
| --- | --- | --- |
| 认证与用户初始化 | 无内部耦合 | 只输出可信 `CurrentIdentity`；不创建或判断其他业务资源。 |
| 候选人资料准备 | 原文存在两处内部耦合风险：将解析流程写为模块内部步骤，以及由本模块创建沟通消息附件。 | 上传后只提交 `ResumeParseRequest`；不接收或查询画像。附件引用只由 AI 求职沟通模块在候选人授权后创建。 |
| 简历解析 | 简历解析与画像是同一条结构化处理链路。 | 仅接收带受控读取授权和幂等键的 `ResumeParseRequest`；在同一事务中写入已校验画像和简历终态。解析执行状态由异步任务运行记录追踪；对外不发起下游业务动作。 |
| 求职目标 | 无内部耦合 | 只维护当前候选人的目标及状态，向下游输出 `ActiveGoalSnapshot`。 |
| 岗位 JD 解析与入库闭环 | 闭环内部从指定目录取得开发者准备的源文件，完成解析并形成可供下游消费的共享岗位快照。 | 不接受候选人请求、外部路径或模型指令；解析成功后在岗位目录领域事务中写入岗位/JD 和 `succeeded` 终态，失败输入不得形成可用岗位/JD 业务事实。 |
| 岗位匹配 | 依赖身份、画像、活跃目标和已解析 JD，但这些均可作为输入快照，不构成内部耦合。 | 匹配用例仅接收已校验的 `MatchInput`；不得查询或驱动资料解析、目标状态变更或岗位管理内部流程。 |
| 投递与进度 | 依赖简历、目标、岗位和可选匹配结果，但应为创建投递时的校验输入。 | 用例接收并复核已声明的资源引用/快照；不得触发匹配或修改上游资源。 |
| AI 求职沟通 | 依赖投递记录和候选人明确授权的附加资料，但应为会话或消息命令的输入。 | 仅在本域创建会话、消息和附件引用；不得读取附加资料正文、修改投递状态或自行选择资料。 |

上述裁决适用于后续任务拆分：模块间只能依赖版本化的输入/输出契约、明确的授权和资源归属校验。若一个任务需要进入其他模块的 Service、Repository、数据库事务、异步任务状态或 Agent 工具实现才能完成，即判定为内部耦合，必须先拆分职责或新增契约，不得以“共同完成闭环”为由绕过边界。

#### 3.1.1 认证与用户初始化

##### 3.1.1.1 MVP 交付目标

为后续所有候选人业务模块建立唯一、可信的当前身份上下文。用户完成注册或登录后，系统能够识别其 `user_id` 与唯一关联的 `candidate_id`，并以该身份作为所有受保护资源的归属校验起点。

##### 3.1.1.2 MVP 内部交付裁决

| MVP 版本需要交付的内容 | 具体内容 | MVP 版本不需要交付的内容 | 具体内容 |
| --- | --- | --- | --- |
| ✅ 用户名密码认证 | 支持用户名和密码注册、登录及当前身份查询。 | ❌ Refresh Token 与会话持久化 | 不签发 Refresh Token，不保存服务端会话，不支持 Token 轮换或会话重放检测。 |
| ✅ 原子用户初始化 | 注册成功时，在同一数据库事务中创建唯一的 `User` 与 `Candidate`。 | ❌ 账号扩展能力 | 不支持邮箱/手机验证、第三方登录、设备管理、密码找回、账号禁用或管理员账号管理。 |
| ✅ 统一当前身份解析 | 受保护请求通过 Bearer Access Token 和 Repository 复核得到唯一 `CurrentIdentity(user_id, candidate_id)`；请求不得自行指定当前身份 ID。 | ❌ 资料业务处理 | 不创建简历、画像、求职目标或其他业务资源，不计算资料准备度。 |
| ✅ 最小安全响应 | 注册、登录和 `/auth/me` 仅返回当前身份所需最小信息；密码、哈希、凭证和内部错误不进入响应、日志或追踪。 | ❌ 长期登录体验 | 不实现跨刷新保持登录、多终端会话同步或会话安全运营能力。 |
| ✅ 最小身份输出 | 新注册或首次登录仅返回认证与当前身份所需字段。 | ❌ 资料与求职状态管理 | 不负责生成候选人画像，不返回或计算 `profile_status`，也不决定简历、画像或求职目标是否可用于匹配。 |

##### 3.1.1.3 模块输入、输出与下游边界

| 项目 | MVP 裁决 |
| --- | --- |
| 输入 | 注册或登录时的用户名、密码，以及可选候选人姓名；受保护请求携带 Bearer Access Token |
| 输出 | Access Token、最小用户/候选人身份；统一响应格式为 `{code, msg, data}` |
| 向下游提供 | 可信 `CurrentIdentity(user_id, candidate_id)`，供资料、目标、匹配、投递和沟通模块执行资源归属校验 |
| 不负责 | 简历可用性、画像生成、资料准备度计算、求职目标与任何业务资源的创建或状态变更 |

##### 3.1.1.4 验收口径

- 验收时应能证明：注册原子创建唯一 User 与 Candidate；登录和 `/auth/me` 解析同一身份；缺失、无效或过期 Token 被安全拒绝；任意候选人资源均不能由其他候选人通过伪造 ID 访问。
- 接口字段、密码策略、错误码和认证状态机的具体定义以接口协议、业务规则与状态机、数据模型文档为准；本小节只裁决 MVP 范围与模块边界。

#### 3.1.2 候选人资料准备

##### 3.1.2.1 MVP 交付目标

让候选人管理本人正式简历和补充资料，完成受控上传、存储、列表与解析状态查询。该模块只提供候选人资料资源及其状态，不生成、不持久化或查询候选人画像；不计算求职状态，不读取或依赖求职目标，也不负责任何下游业务准入。

##### 3.1.2.2 MVP 内部交付裁决

###### 第一部分：候选人资料数据模型

| MVP 版本需要交付的内容 | 具体内容 | MVP 版本不需要交付的内容 | 具体内容 |
| --- | --- | --- | --- |
| ✅ 正式简历管理 | 候选人可上传和查询本人正式简历及其解析状态。简历是画像、岗位匹配和投递的唯一基础资料。 | ❌ 用附加资料替代简历 | 证书、作品集、求职策略等附加资料不得生成正式画像，不得单独用于匹配或投递。 |
| ✅ 候选人附加资料 | 支持候选人上传、查询本人已脱敏附加资料，并向 AI 求职沟通模块提供候选人明确选择和授权后的最小附件元数据；附加资料不进入简历解析，正文也不自动进入 Agent/LLM 输入。 | ❌ 无授权的 Agent 上传/发送、HR 直接读取 | Agent 不得自行上传、选择或读取资料正文；不建设 HR 直接读取、下载或真实外发能力。 |
| ❌ 候选人画像 | 候选人画像的生成、持久化和查询属于简历解析模块，不属于资料资源管理。 | ❌ 独立画像任务、重复解析结果与画像推荐 | 不创建独立的画像生成任务、处理中/失败状态或目标职位推荐能力；`resumes` 不保存重复的 `parse_data`。后续需要新字段时，先扩展画像 Schema，再用原始简历重新解析，不以未校验中间结果补写。 |
| ✅ 资料事实边界 | 仅提供本人简历、附加资料及其解析状态的受控查询；资料模块不拥有候选人画像或求职目标事实。 | ❌ 求职状态与下游准入 | 不派生 `incomplete / blocked / ready`，不实现资料完整度评分，不阻断匹配、投递或 AI 沟通会话；这些规则由各下游模块依据自身前置条件裁定。 |

###### 第二部分：对象存储与受控文件访问

| MVP 版本需要交付的内容 | 具体内容 | MVP 版本不需要交付的内容 | 具体内容 |
| --- | --- | --- | --- |
| ✅ 本地对象存储实现 | MVP 仅使用可配置根目录下的本地对象存储适配器；存储目录不得作为 Web 静态目录暴露。业务模块仅依赖对象存储抽象，不得直接操作本地文件路径，为后续迁移其他对象存储实现保留替换边界。 | ❌ 云对象存储与通用文件中心 | 不接入 MinIO、S3、OSS 等外部对象存储，不建设跨业务资源复用的通用文件中心。 |
| ✅ 不透明文件定位 | 每次上传生成由服务端控制的、不含原始文件名和候选人身份的 `storage_key`；物理路径只能由对象存储适配器根据受控根目录和 `storage_key` 解析。数据库不得保存或向客户端返回绝对路径、`file://` 地址、静态 URL 或可直接访问的文件地址。 | ❌ 客户端指定或猜测文件路径 | 客户端、Agent、解析器和 LLM 均不得传入、拼接或根据模型输出推导本地路径、对象键或下载地址。 |
| ✅ 文件类型白名单 | 正式简历仅接收 PDF；`candidate_documents` 可接收 PDF、Markdown、JPG/JPEG。上传时必须同时校验文件扩展名、声明 MIME 类型和文件特征，三者不一致或不在白名单时安全拒绝。文件格式仅决定上传校验，不决定是否解析。 | ❌ Markdown 等非 PDF 简历及其他文档和图片格式 | 正式简历不支持 Markdown、DOC/DOCX、图片、压缩包、可执行文件及其他未列入白名单的格式；附加资料不支持 PNG、HEIC、压缩包、可执行文件及其他未列入白名单的格式。 |
| ✅ 图片仅作沟通附件 | JPG/JPEG 作为 `candidate_documents` 保存，并仅在候选人明确选择和授权后，向 AI 求职沟通模块提供附件引用所需的最小元数据；不作为正式简历，不生成画像，其正文不自动进入 Agent/LLM 输入。 | ❌ 图片 OCR 或简历解析 | MVP 不对 JPG/JPEG 做 OCR、文字提取或结构化解析；`candidate_documents` 无论文件格式均不进入简历解析生命周期。 |
| ✅ 单文件大小硬上限 | 所有上传入口的单个文件最大为 **10 MB（10,000,000 bytes）**；服务端必须在写入正式对象前执行限制校验，超限安全拒绝且不创建资源记录、解析任务或消息附件。 | ❌ 按类型或用户维度的配额策略 | 不按 PDF、Markdown、JPG/JPEG 分别配置大小上限，不实现单候选人文件数量上限、总存储配额、配额展示、预警或超额治理。 |
| ✅ 上传去重与资源审计 | 以文件内容摘要进行去重：相同内容仅保存一份底层对象，但每次上传仍创建独立、归属明确的简历或附加资料资源记录；不得因底层对象复用而合并候选人资源、授权、审计或简历解析任务幂等边界。 | ❌ 以文件名去重或覆盖既有资源 | 不以文件名、客户端路径或资源 ID 判断重复；重新上传必须创建新资源，不能覆盖或回写既有资源。 |
| ✅ 受控读取 | 文件只可由已通过当前候选人归属校验的业务流程读取；简历解析任务仅能读取其资源记录绑定的对象。读取必须经 Repository 校验资源归属、状态与用途。 | ❌ 原始文件下载与预览 | MVP 不提供原始文件下载、在线预览、公开链接、预签名 URL 或静态文件服务；列表和消息接口仅返回所需的脱敏元信息，不返回文件地址或正文。 |
| ✅ 去重引用与清理闭环 | 内部对象目录以内容摘要唯一约束管理底层对象，简历和附加资料仅通过外键引用对象；清理前必须在事务内确认对象无任何资源引用，避免删除共享对象。临时文件、写入中对象和无引用对象超过 1 小时宽限期后由幂等清理任务处理。 | ❌ 用户删除与保留策略运营 | MVP 不提供候选人删除简历或附加资料的接口，不实现回收站、恢复、保留期限配置、批量删除或历史资源物理清理策略。 |

MVP 仅裁决统一的单文件大小硬上限为 10 MB（10,000,000 bytes）。单候选人文件数量、总存储配额、配额展示、告警和超额治理均为后续规划；不得将其作为 MVP 上传功能的开发依赖或验收条件。

`candidate_documents` 是候选人拥有的已脱敏原始附件资源，不持有 `parse_data`、`parse_status` 或解析任务；候选人明确选择并授权后，AI 求职沟通模块可基于最小附件元数据在本域创建对该资料的附件引用，而不复制文件或正文。MVP 中，Agent 仅可使用完成授权所需的最小附件元数据，资料正文不自动进入 Agent/LLM 输入；后续若需读取资料内容、供 HR 直接读取或真实外发，必须另行引入按次授权的受控内容理解能力、审计规则和类型适配方案。

底层对象目录是仅供存储适配器和 Repository 使用的内部技术数据，不构成面向用户的通用文件中心。上传先写入受限临时目录并完成大小、类型和内容摘要校验；同摘要对象在事务锁保护下复用，只有对象已就绪时资源记录才能引用它。资源建档或解析入队失败遗留的无引用对象，以及上传中断遗留的临时文件，均由清理任务在 1 小时宽限期后安全清理。

###### 第三部分：正式简历解析范围

| MVP 版本需要交付的内容 | 具体内容 | MVP 版本不需要交付的内容 | 具体内容 |
| --- | --- | --- | --- |
| ✅ 可提取文本 PDF 简历解析 | 仅对正式简历 PDF 使用 MinerU MCP 提取文本，再进入结构化画像链路；PDF 必须可提取有效机器文本。 | ❌ 扫描版 PDF 与 OCR | 不启用扫描 PDF 识别、OCR、图像文字提取或相应的质量调优；可打开但无法提取有效机器文本的 PDF 以 `file_unreadable` 终态失败。 |
| ✅ 固定解析规则 | MVP 以单一固定规则集处理所有正式简历；解析任务内部使用固定值 `v1` 维持既有幂等约束。 | ❌ 解析规则版本管理 | 不提供规则升级、多版本并存、历史简历自动重解析、版本选择或版本对比能力。 |

##### 3.1.2.3 模块输入、输出与下游边界

| 项目 | MVP 裁决 |
| --- | --- |
| 输入 | 当前候选人身份、候选人上传的正式简历或附加资料 |
| 输出 | 本人简历和附加资料的查询结果，以及受控解析状态 |
| 向下游提供 | 已认证、归属明确的资料资源和候选人明确选择、授权且归属一致的附加资料最小元数据；候选人画像由下游向简历解析模块查询 |
| 不负责 | 简历的文件读取、文本提取、解析重试、画像生成/持久化/查询与失败分类由简历解析模块负责；岗位 JD 解析与入库闭环由后续独立变更单元负责；创建消息及其附件关联、回复草稿和模拟发送由 AI 求职沟通模块负责 |

##### 3.1.2.4 验收口径

- 已认证候选人可上传和查询归属自己的正式简历、附加资料及简历解析状态；其他候选人不能通过资源 ID 读取或使用这些资源。
- 一份简历只有在结构化解析通过、`target_job_titles` 存在且确定性画像原子写入后，才可成为可用简历画像；画像生成、校验或写入失败均按简历解析失败处理，不得留下半成品画像或独立画像失败状态。
- 岗位匹配、投递和 AI 沟通仅读取 `candidate_profiles` 中已校验的简历结构化字段；新增下游字段须完成画像 Schema 扩展和原始简历重解析验证，不能读取或引入 `resumes.parse_data`。
- 附加资料可在候选人明确选择和授权后，由 AI 求职沟通模块创建系统内消息附件引用，但不得替代正式简历；MVP 中其正文不自动进入 Agent/LLM 输入，也不提供 HR 直接读取或真实外发。
- 候选人资料准备不返回、存储或计算 `profile_status`，也不对匹配、投递和沟通会话实施 `409` 准入；各下游模块必须在自己的业务边界内定义并校验所需的简历、画像和求职目标前置条件。
- 具体文件格式、大小限制、解析 Schema、接口字段、异步状态机和附件模型以接口协议、数据模型、业务规则与状态机文档为准；本小节只裁决 MVP 范围与模块边界。

#### 3.1.3 简历解析

##### 3.1.3.1 MVP 交付目标

将已授权的正式简历转换为经结构化和业务规则校验的候选人画像。候选人画像是简历解析成功的组成部分：同一事务内持久化画像和简历终态。岗位 JD 解析与入库闭环不属于本模块，留待对应变更单元裁决。

##### 3.1.3.2 模块输入、输出与边界

| 项目 | MVP 裁决 |
| --- | --- |
| 输入 | 带简历资源 ID、受控读取授权和幂等键的 `ResumeParseRequest`。 |
| 输出 | 已校验的 `CandidateProfile`、简历终态和有限安全失败分类；异步任务运行状态由通用任务记录追踪。 |
| 查询 | 仅提供已认证候选人可访问的、已校验候选人画像查询；资料资源列表和原始文件查询仍归候选人资料准备。 |
| 不负责 | 文件上传、附加资料管理、岗位 JD 解析与入库、求职目标、匹配、投递、沟通以及任何下游业务动作。 |

候选人画像不提供独立生成任务、处理中/失败状态、手工复杂编辑、跨简历版本管理或目标职位推荐。`target_job_titles` 是简历中显式“求职意向/目标岗位”栏目的必填解析事实，以至少含一个非空字符串的列表表示；它不是系统推荐结果，也不根据经历、技能或市场信息补全。

### 3.2 模块交付顺序与启用门禁

本节定义 MVP 的**强制交付顺序**。编号不是代码目录、团队分工或并行排期的名称；每一项均是后续编号模块开始真实依赖实现、集成验收或声明 MVP 完成前必须满足的启用门禁。前置模块只需完成此处列出的最小可用边界，不要求提前建设延期能力。

1. **G1 认证与用户初始化（含公共持久化边界）**
   - 门禁：可获得可信 `CurrentIdentity`；所有受保护资源均可执行候选人归属校验；Repository、事务、迁移、统一响应和脱敏诊断可用。
   - 向后续提供：身份、归属校验、数据访问与安全响应基线。
2. **G2 候选人资料准备与受控对象存储**
   - 前置：1。
   - 门禁：候选人只能上传和查询本人的正式简历；文件对象受控存储、去重、受控读取和清理可验证；上传可提交版本化简历解析请求。
   - 向后续提供：归属明确的简历资源、受控读取授权和 `ResumeParseRequest`。
3. **G3 简历解析与候选人画像**
   - 前置：1、2。
   - 门禁：解析执行底座、Dispatcher/Worker、租约、有限重试、超时与安全失败分类可用；简历可经受控读取、结构化校验后原子写入 `CandidateProfile` 与简历终态。
   - 向后续提供：已解析简历、已校验候选人画像。
4. **G4 岗位 JD 解析与入库闭环**
   - 前置：1。
   - 门禁：从指定目录取得开发者准备的岗位 JD 文件，完成结构化抽取、结果 Schema 与业务校验；仅在解析成功后于岗位目录领域事务中写入岗位/JD 和 `parse_status = succeeded`，失败输入不得形成可用岗位/JD 业务事实。Demo 不建设独立 HR 录入、复杂输入治理或高可用导入平台，不得因简历解析使用 MinerU/异步工作流而默认复用该实现。
   - 向后续提供：归属明确、已解析且可查询的 JD 快照。
5. **G5 求职目标**
   - 前置：1。
   - 门禁：候选人可维护至少一个 `active` 求职目标，且目标状态迁移受约束。
   - 向后续提供：已校验的 `ActiveGoalSnapshot`。
6. **G6 岗位匹配**
   - 前置：3、4、5。
   - 门禁：仅以已解析画像、已解析 JD 和活跃目标的版本化快照发起匹配；产生可解释、可追踪的异步结果。
   - 向后续提供：候选人可访问的匹配结果。
7. **G7 投递与进度**
   - 前置：3、4、5；可选使用 6 的匹配结果。
   - 门禁：可创建系统内投递记录；所有进度更新均受状态机约束并写入 `Progress Event`。
   - 向后续提供：归属明确、已授权的投递上下文。
8. **G8 AI 求职沟通**
   - 前置：7。
   - 门禁：仅基于已授权投递上下文创建系统内会话，并生成经校验的回复草稿或模拟回复；不得产生真实外发副作用。
9. **F1 前端闭环验收（非业务模块）**
    - 前置：1–8 的对应 API 契约稳定。
    - 门禁：前端逐段覆盖注册/登录、简历与 JD、目标、匹配、投递和沟通路径；只显示当前候选人有权访问的数据，并正确呈现异步终态和安全错误。
10. **R1 受控部署与发布门禁（非业务模块）**
    - 前置：1–9。
    - 门禁：在拟运行拓扑中完成迁移、后端与前端部署、环境变量/凭证注入、健康检查、核心闭环和失败路径验证；CI 质量工作流及本变更相关发布门禁均通过。

前端可在对应 API 契约稳定后并行实现页面，但不得以 Mock 或未启用的后端能力作为该步骤的 MVP 验收证据。简历解析执行底座仅服务于简历解析；第 4 步岗位 JD 解析与入库闭环应按其自身裁定的技术路线交付，不得因已有简历解析实现而跳过岗位目录领域边界。

### 3.3 核心用户路径

```text
注册 / 登录
  → 上传简历
  → 解析成功（已原子生成候选人画像）
  → 创建活跃求职目标 + 受控导入岗位 JD 源文件、解析并入库

```

任何不服务于上述闭环的功能，默认不在 MVP 范围内。

## 4. 关键实现裁决

### 4.1 认证裁决

- MVP 使用短期 Access Token 识别当前用户，默认有效期可配置，建议为 8 至 24 小时。
- 密码必须使用成熟算法进行哈希保存；禁止明文保存、记录或返回密码。
- 所有候选人资源必须通过当前 `candidate_id` 做归属校验；这是 MVP 不可降级的安全边界。
- `auth_sessions`、Refresh Token 轮换和会话重放检测已完成设计，但标记为后续试运行/生产增强项，不是 MVP 阻塞项。

### 4.2 Agent 与模型能力裁决

- MVP 的 Agent 核心能力是：结构化简历/岗位信息处理、可解释岗位匹配、基于已授权上下文的沟通草稿生成。
- 所有 LLM 输出必须通过 Pydantic 结构化校验和业务规则校验后，才能入库或进入下一流程。
- Agent 根据活跃求职目标生成结构化计划，并只能调度已注册、受策略控制的工作流；计划、调度与运行必须可审计。MVP 不建设可视化编排或动态工作流发布。
- 向量库、Embedding、Rerank 和混合检索按 R0-R4 分层启用；仅在质量评估确认某个匹配任务需要时才成为该任务的条件依赖或可选优化，不得作为整个 MVP 的统一阻塞项。
- LLM 不得直接执行 SQL、Shell、未经校验的网络请求，或直接触发真实投递和外部消息发送。

### 4.3 异步与副作用裁决

- 简历解析和岗位匹配可使用 Celery 异步执行，必须具备状态追踪、有限重试和幂等处理。岗位 JD 解析与入库闭环按 Demo 需求采用其自身裁定的解析执行方式，不默认复用简历解析的异步链路。
- 异步失败不得写入半成品画像、匹配结果或投递记录。
- 投递、进度和会话仅在系统内变更；所有状态变更必须遵守状态机并记录领域事件。
- 对外发送、真实投递和不可逆副作用均不属于 MVP，后续纳入时必须补充明确用户授权、审计和失败回滚设计。

## 5. 已知延期项

以下能力允许在文档中保留设计，但不得被列为 MVP 的开发依赖、验收条件或上线阻塞项：

| 类别 | 延期能力 | 进入后续阶段的触发条件 |
| --- | --- | --- |
| 认证安全 | Refresh Token、会话持久化、Token 轮换、设备管理、密码找回、账号禁用与风控 | 对外试运行、需要跨刷新保持登录，或出现多设备安全管理需求 |
| 账号体系 | 邮箱/手机验证、第三方登录、管理员与运营角色 | 用户规模扩大或需要运营管理 |
| 岗位数据 | 爬虫、外部平台同步、自动去重与来源治理 | 手工录入无法满足测试岗位数量或质量 |
| 投递自动化 | 自动投递、真实 HR 消息发送、日程同步、邮件发送 | 获得明确用户授权、第三方平台权限及审计方案后 |
| AI 能力 | 长期记忆、持续学习、复杂检索评估、线上模型实验 | 基础匹配和沟通闭环已验证并有明确优化数据 |
| 工作流平台 | 可视化编排、动态流程配置/发布、工作流运营台 | 需要非研发人员调整流程，且已有多个稳定流程需复用和运营 |
| 平台能力 | 多租户运营、限流风控、完备监控告警、灾备与高可用 | 从受邀测试进入公开服务或商业化运行 |

## 6. MVP 不可降级约束

即使功能仅用于 MVP，以下规则不得因“演示便利”被绕过：

1. 数据访问必须经过 Repository 层；Service、Agent、Workflow 不得直接访问 ORM Session 或编写 SQL。
2. 所有候选人资源必须校验当前候选人的归属，禁止仅凭资源 ID 读取或修改。
3. 密码、密码哈希、Token、未经脱敏的简历原文、联系方式、完整内部文件定位、模型原始响应及含敏感内容的异常堆栈不得进入日志、LangSmith 追踪或非必要接口响应；Prompt 仅可包含任务所需的已脱敏数据。日志与追踪仅记录关联 ID、处理阶段、状态、脱敏失败分类、耗时和重试次数等最小诊断信息。
4. LLM 结果必须经结构化和业务规则校验；不得直接成为事实或副作用指令。
5. 异步任务必须可追踪、有限重试且幂等；失败不得产生重复或半成品业务数据。
6. 投递进度等业务状态变更必须符合状态机并记录 Progress Event。
7. API 必须遵守 `{code, msg, data}` 统一响应格式。

## 7. 范围变更规则

- 新需求先与本文件的“本期范围”和“已知延期项”比对；不在本期范围内时，默认延期。
- 任何将延期项提前到 MVP 的请求，必须先更新本文件，并同时说明用户价值、影响模块、新增依赖、数据/API/状态机变更和排期影响。
- 任何提升技术能力层级或将 `延期`、`MVP 可选优化` 能力作为模块必需项的请求，必须同时更新技术使能与工作流治理文档及变更包影响分析。
- 任何会产生对外副作用、处理新增敏感数据或削弱不可降级约束的变更，必须单独评审，不得以 MVP 名义直接纳入。
- 开始模块任务拆分前，应以本文件为依据标记每项任务为“本期必需”“本期可选”或“延期”。
