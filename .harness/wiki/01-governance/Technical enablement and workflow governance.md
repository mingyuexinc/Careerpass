# 技术使能能力与工作流治理

## 1. 目的、适用范围与裁决关系

本文件定义 Careerpass MVP 中技术能力的分类、启用条件、首次交付边界和验收门槛。它位于业务 MVP 范围与具体工程实现之间：

- `.harness/wiki/01-governance/MVP scope and development boundaries.md` 裁决用户价值、业务闭环和版本范围；
- 本文件裁决为交付该闭环所需的技术能力及其演进层级；
- `.harness/wiki/02-domain/Business rules and state machines.md` 定义业务状态、授权与合法迁移；
- `.harness/rules/Engineering structure.md` 定义代码边界和依赖方向；
- 单个变更包记录本次实际启用的能力、实现方案和验证证据。

本文件不要求预先建设通用技术平台。技术能力应采用“最小公共底座 + 业务闭环纵向切片 + 按触发条件演进”的方式交付。

## 2. 能力状态

| 状态 | 定义 | 开发与验收要求 |
| --- | --- | --- |
| `MVP 基线` | 任何 MVP 闭环或其安全边界都依赖的能力 | 必须在首次相关业务模块前或随其交付；是 MVP 验收门槛 |
| `MVP 条件能力` | 仅在已纳入 MVP 的某个模块实际采用时必需的能力 | 必须与该模块在同一变更中最小可用地交付和验证 |
| `MVP 可选优化` | 改善质量、成本或效率但不阻断闭环的能力 | 可在 MVP 内择机实现；未启用不得阻塞模块验收 |
| `延期` | 已知但不属于当前 MVP 的能力 | 可保留设计，不得成为当前任务依赖、验收条件或上线阻塞项 |

“首次交付模块”仅表示能力最早在该模块实现并验收，不限制后续模块复用该能力。

| R0：结构化条件过滤与可解释评分 | MVP 基线 | 岗位匹配 | 投递 | 发起岗位匹配 | 基于目标和已解析资料产出可解释结果 | 大规模检索运营 |
| R1：语义向量召回 | MVP 条件能力 | 岗位匹配 | 无 | R0 无法满足候选池召回质量且评估确认启用 | 向量写入、召回、版本和失败处理可追踪 | 将向量库设为全部模块前置依赖 |

| R4：多路召回、在线学习、A/B 实验 | 延期 | 无 | 无 | 基础匹配闭环已验证并取得优化数据 | 后续另行裁决 | MVP 实现 |

## 4. Agent 规划与工作流编排治理

Agent 规划、工作流注册、调度和编排状态属于 MVP 基线能力；MVP 只允许代码注册的静态工作流。可视化编排、动态流程配置/发布、工作流版本运营和人工运营后台均为延期能力。

具体的计划 Schema、注册表、编排状态、授权闸门、幂等和审计机制以 [Agent 工作流编排技术方案](../04-technical-solutions/Agent%20workflow%20orchestration%20technical%20design.md) 为准。Celery 的投递、执行、重试和超时状态以 [异步任务技术方案](../04-technical-solutions/Async%20task%20technical%20design.md) 为准。

### 4.1 资源类型启用依赖

技术能力的“首次交付模块”不等于所有资源类型分支已完成。资源类型分支必须满足以下启用依赖，并与 [MVP 范围与开发边界](MVP%20scope%20and%20development%20boundaries.md) 第 3.2 节的编号顺序一致：

1. **简历解析分支**：候选人资料准备先提供归属明确的简历资源、受控读取授权和 `ResumeParseRequest`；随后启用解析执行与结构化校验，并在同一工作流中原子写入画像和简历终态。
2. **岗位 JD 启动导入分支**：岗位管理从固定受控目录读取 Markdown JD 并建立输入、归档和持久化边界；候选人不参与导入，也不访问失败输入。结构化抽取是否采用确定性规则或外部模型、何时发布共享快照，均留待岗位 JD 解析分支裁决；不得默认复用简历解析实现。
3. **岗位匹配分支**：仅在已解析简历画像、已解析 JD 和活跃求职目标均可作为版本化输入快照时启用；不得由匹配流程反向触发或修复上述前置资源。

任何资源类型分支的前置领域接口未达到门禁时，该分支状态为 `blocked`；这不否定已完成且可复用的技术能力，也不得以 Mock、手工数据库写入或跨层访问替代前置门禁。

## 5. 开发与范围变更规则

1. 一个模块的任务必须同时描述用户可见业务结果和实际需要的技术能力；禁止先完成所有空壳业务接口，再补技术能力。
2. 首次启用异步任务、LLM、对象存储、检索或外部服务时，必须在同一变更中交付最小实现、超时/错误分类、幂等或重试策略（适用时）及真实依赖连通性验证。
3. 已有能力被复用时，变更包必须说明其版本、输入输出契约和可用性检查；不得假设能力天然可用。
4. 将能力从 `延期` 或 `MVP 可选优化` 提升为必需项时，必须同时更新本文件、MVP 范围文档和变更包影响分析，并说明用户价值、质量证据、影响模块及新增依赖。
5. 模块任务必须遵守 MVP 范围文档第 3.2 节的编号顺序。只有前置门禁已通过，后续模块才可将该前置能力作为真实依赖进行实现或验收；尚未满足时应标记对应资源类型分支为 `blocked`，不得错误扩大为整项可复用技术能力未完成。
