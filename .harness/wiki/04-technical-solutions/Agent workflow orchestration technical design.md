# Agent 工作流编排技术方案

## 1. 定位与边界

本方案定义 Agent 规划、已注册工作流选择与编排运行的技术边界。它与 [异步任务技术方案](Async%20task%20technical%20design.md) 分离：本方案处理“应当执行什么工作流及其业务编排状态”，异步任务方案处理“Celery 如何可靠投递和执行一次后台任务”。

MVP 仅允许代码注册的静态工作流；不支持可视化编排、动态流程发布、工作流运营台或模型自主创建工具调用。

## 2. 最小编排模型

- Agent 只生成 Pydantic 校验的结构化计划，不直接写入业务数据、不拼接 SQL、Shell 或外部请求。
- 工作流注册表必须声明名称、版本、输入/输出 Schema、触发条件和执行边界。
- 调度前必须校验注册状态、输入、当前候选人归属、资源状态、业务前置条件与授权。
- 计划只能产生：调度已注册工作流、要求用户补充资料、拒绝不合法动作或报告已完成。

## 3. 编排状态与 Celery 状态的分离

| 编排状态 | 含义 |
| --- | --- |
| `planned` | 已产生计划，尚未校验 |
| `validated` | 计划、输入、归属、策略和业务前置条件均通过 |
| `waiting_for_user` | 缺少资料、授权或其他用户输入 |
| `rejected` | 计划不合法、无权或工作流未注册 |
| `scheduled` | 已决定调度已注册工作流 |
| `completed` | 编排目标已获得完整、已校验的业务结果 |
| `failed` | 编排无法继续，且不满足自动重试条件 |

这些状态描述 Agent 决策和业务编排，不等同于 Celery 的 `queued / running / succeeded / failed`。一个 `scheduled` 工作流可创建一个或多个异步任务运行；其投递、执行尝试、重试、超时和 Worker 状态均以异步任务技术方案为准。

## 4. 安全与审计

- 涉及投递、进度、会话或任何副作用时，仍必须通过对应业务状态机和授权规则；计划或调度成功不构成副作用授权。
- 计划、校验、拒绝、调度和终态只记录最小必要的脱敏元数据、版本和关联 ID，不记录简历正文、联系方式、Token 或提示词敏感内容。
- 幂等键至少包含工作流名称、版本、候选人归属锚点和业务输入资源标识；重复计划或队列投递不得造成重复业务写入或副作用。

具体工作流清单、状态持久化模型和跨工作流编排能力不属于当前 MVP；首次启用某个工作流时，应在变更包中补充其输入输出契约、依赖检查和验收证据。
