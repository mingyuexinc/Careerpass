## 模块级串行门禁（强制）

十一阶段不是建议性清单，而是每个正式模块或跨模块闭环的串行状态机。模块必须从阶段 1 开始；在阶段 8–11 因 MVP 未部署而暂不执行时，仍必须完成阶段 1–7。任何代码、测试或实现任务均不得以“已有任务列表”“并行开发”或“后续补文档”为由跳过前置阶段。

### 阶段状态与流转

- 每个模块只能有一个 `in_progress` 阶段；后续阶段仅当前置阶段为 `passed` 后才能开启。
- 合法状态为 `not_started`、`in_progress`、`passed`、`blocked` 和 `not_applicable`。正常流转为 `not_started → in_progress → passed`；`blocked` 只能在阻塞解除后回到 `in_progress`。
- `not_applicable` 仅适用于确实不触发的阶段性条件，例如阶段 2 没有首次进入 MVP 关键路径的外部依赖；必须记录理由、影响和开发者确认。阶段 1、3、4、5、6、7 不得标记为 `not_applicable`。
- 阶段 8–11 在未进入部署范围时可保持 `not_started`，并在阶段 7 记录“本期未启用”的范围裁决；不得伪造为已通过。
- 只有开发者可将阶段标记为 `passed` 或 `not_applicable`。大模型可起草、检查证据和提示阻塞，但不得代替开发者批准门禁。

### 阶段台账

每个新建或继续开发的正式模块变更包必须包含 `00-governance/stage-gates.yaml`，作为唯一阶段状态来源。开始任何阶段前先读取该台账；台账缺失、前置门禁未通过或存在影响当前阶段的 `blocked` 项时，不得开始工作。

```yaml
module: {模块名称}
current_stage: 1
stages:
  1:
    status: in_progress
    evidence:
      - 01-analysis/requirements.md
      - 01-analysis/impact-analysis.md
    approved_by: null
    approved_at: null
    notes: ""
  2:
    status: not_started
    evidence: []
    approved_by: null
    approved_at: null
    notes: ""
  3:
    status: not_started
    evidence: []
    approved_by: null
    approved_at: null
    notes: ""
```

台账必须为阶段 1–11 保留同样结构；`evidence` 必须指向变更包内的实际交付物或可审计验证记录，`notes` 必须说明 `blocked`、`not_applicable`、范围裁决或回退原因。阶段 4 开始前，台账还必须列出依赖的前置模块及其所需门禁状态。

### 各阶段开启与通过门禁

| 阶段 | 开启条件 | 通过条件 |
| --- | --- | --- |
| 1. 需求分析 | 模块已立项 | 需求模板、影响分析和开发者关键裁决完整；无关键未决项 |
| 2. 外部技术能力预验证 | 1 `passed` | 每项首次使用的关键外部依赖已有真实 `passed` 证据，或已合法记录 `not_applicable` |
| 3. 方案设计 | 1、2 `passed`/合法不适用 | 边界、数据/API、状态机、技术路线、失败处理和回滚已评审 |
| 4. 任务拆分 | 1–3 `passed` | 模块边界表、技术能力地图、依赖图和不超过 4 小时的任务清单完整 |
| 5. 编码实现 | 1–4 `passed` | 仅执行已批准任务，且不违反红线与架构边界 |
| 6. 单元测试 | 5 `passed` | 核心逻辑覆盖、整体覆盖率和测试报告达到规范要求 |
| 7. 代码评审 | 6 `passed` | 评审完成，不存在未解决的 P0/P1 问题 |
| 8–11. 集成、预发、部署、观测 | 对应前一阶段 `passed` 且本期范围启用 | 各阶段的既定验收证据完整 |

### 代码与任务操作约束

- 阶段 1–4 只允许编写需求、预验证、设计、迁移草案和任务规划文档；不得开始业务运行时代码、数据库迁移执行、接口实现或测试实现。
- 阶段 5 只能实现阶段 4 已批准的任务。发现新的业务决策、外部依赖、数据字段或跨模块契约需求时，立即将任务标记为 `blocked`，不得在代码中临时补决定。
- 阶段 6 只能为已实现任务补充或修复测试；测试发现设计、范围或契约问题时，按下方回退规则处理，不得只用测试替身掩盖问题。
- 阶段 7 之前不得宣称模块“完成”或将其作为后续模块的稳定前置能力。

### 变更回退与门禁失效

下列变化会使已经通过的后续阶段失效。必须在台账中记录回退原因、将 `current_stage` 回退到对应阶段，并重新通过受影响的阶段后继续：

| 变化 | 最低回退阶段 |
| --- | --- |
| MVP 范围、用户角色、授权、资源归属或外部副作用变化 | 1. 需求分析 |
| 新增或替换 LLM、第三方 API、队列、对象存储等关键依赖 | 2. 外部技术能力预验证 |
| 数据模型、接口契约、状态机、领域边界或失败处理变化 | 3. 方案设计 |
| 任务依赖、任务粒度、执行顺序或验收拆分变化 | 4. 任务拆分 |
| 单元测试或代码评审发现上述任一问题 | 按问题类型回退至 1–4 |

### 执行与校验

- 开始阶段 3、4、5、6、7 前，开发者或执行 Agent 必须检查 `stage-gates.yaml` 的前置状态和证据路径；检查失败即停止并报告 `blocked`。
- 变更包校验工具和 CI 应校验：阶段台账存在、状态流转合法、阶段 4 前阶段 1–3 已通过、代码实现前阶段 1–4 已通过、阶段 7 前测试与评审证据存在。
- 现有未完成模块应在下一次继续开发前补建阶段台账，并根据已有证据如实登记；不得将未发生的阶段补记为 `passed`。

## 阶段 1：需求分析

需求分析是模块开发的首个强制门禁，必须先于外部技术预验证、方案设计和任务拆分完成。Careerpass 当前是**受控 Demo 演示项目**：需求分析的目标是固定能够被重复演示的核心闭环、授权、范围和不可逆规则，而不是提前满足公开运营、规模化或生产运维要求，避免开发人员在编码或拆分任务时临时决定产品策略。

Demo 需求的完成标准是“以受控测试数据和既定演示路径，可信地证明本模块对核心闭环的价值”；不是“具备未来生产化能力”。若移除一项能力后仍能完成该证明，则该能力默认延期。抽象边界仅在本期已有明确消费者时保留；不得为不确定的未来场景建设通用平台、运营体系或高可用方案。权限、归属校验、敏感信息最小化、LLM 输出校验、状态合法性和必要的异步可靠性仍是不可降级约束，不因 Demo 定位而省略。

需求分析文档可由开发者与大模型共同完成，但标记为 **【开发者填写】** 的内容必须由开发者明确裁决；大模型只能协助发现遗漏、提出选项和生成草案，不能替代开发者作出业务、授权、合规、成本或发布风险决策。标记为 **【共同补全】** 的内容可由大模型先生成，开发者负责复核和确认。

### 阶段门禁与交付物

- 每个正式模块必须提交一份按下方模板编写的需求分析文档，以及关联模块、数据、接口和运行时依赖的影响分析。
- 所有【开发者填写】项必须有明确内容，不能以“待开发时决定”“默认处理”或未验证假设替代。
- 涉及用户资源时，必须已经裁定资源所有者、访问授权链和越权行为；涉及状态变化、外部副作用或敏感数据时，必须已经裁定授权、审计和失败处理原则。
- “待裁决问题”可以保留，但每项必须有候选方案、决策责任人、截止时间和未决影响；影响本模块关键路径、数据模型、接口、权限或技术选型的未决项，模块状态为 `blocked`，不得进入阶段 3 或阶段 4。
- 阶段通过条件：业务价值和 Demo 范围可验证，边界与责任主体明确，关键数据和生命周期已裁定，关键依赖已识别，验收标准可执行，且不存在未处理的关键阻塞项；每项本期能力均能说明其演示证据和明确非目标。

## 外部技术能力预验证

本阶段适用于首次进入 MVP 关键路径的第三方 API、MCP、LLM、Embedding、对象存储、消息队列及其他外部运行时能力。其目的不是交付业务功能，而是在技术方案定稿前消除“方案可用性”这一不确定性。仅阅读文档、发现环境变量、编写 Mock 或通过单元测试，均不得作为选型通过证据。

### 强制门禁

1. 在方案设计前，必须对每个 MVP 关键路径外部依赖完成最小真实验证；不得将“待排查接入方式”拆为正式实现任务。
2. 验证必须确认官方接入契约：Client/Server 拓扑、认证方式、凭证注入到实际运行进程的路径、工具或 API 的真实输入 Schema，以及超时和成本边界。
3. 先执行不含业务数据、无副作用的连接验证，例如健康检查、`initialize`、`tools/list` 或等价操作；随后对受控脱敏样本执行一次最小真实业务调用。没有可调用的最小业务操作时，必须记录原因及替代证据。
4. 验证必须使用项目拟运行的拓扑与凭证注入方式。例如 Worker 需要启动子进程或容器时，不得仅在交互式终端验证凭证存在。
5. 验证全过程不得记录、返回或持久化凭证、原始业务数据、内部路径、模型/供应商原始响应或异常堆栈；应设置显式开关、有限超时、受控样本和成本上限。
6. 预验证结果只能是 `passed`、`blocked` 或 `rejected`：
   - `passed`：可作为 MVP 首选方案进入方案设计和任务拆分；
   - `blocked`：不得进入依赖该能力的实现，应先补齐权限、环境或外部条件，或采用已验证备选方案；
   - `rejected`：该方案不得再次作为当前 MVP 的实现前提。

### 预验证记录

每项预验证必须在变更包的分析或设计材料中留下可审计记录，至少包括：依赖名称和业务用途、官方文档/契约来源、拟运行拓扑、凭证注入边界、受控样本、连接验证结果、最小真实调用结果、超时/成本控制、安全结论、最终状态及首选/备选裁定。记录只保存脱敏事实和关联 ID，不保存敏感原值。

## 单个功能模块开发任务模板

本模板适用于正式功能模块中的每个开发任务，并作为阶段 4“任务拆分”的最小描述单元。每项任务预计纯开发时间不得超过 4 小时；跨任务依赖必须在任务开始前明确。

功能模块的交付单位是“业务闭环纵向切片”：范围裁决 → 领域/API/状态设计 → 本模块所需技术能力 → 业务流程实现 → 集成验证。禁止先实现所有空壳业务接口，再在后续阶段补齐使其可用的技术能力；也禁止为未经触发的未来需求预建通用平台。

### 模块识别与能力先行拆分策略

阶段 4 的任务拆分必须先完成模块识别与技术能力拆分，再形成业务子任务流程；不得从完整业务流程直接拆到实现任务。拆分按以下顺序执行：

1. **识别模块类型与拥有边界**：每个模块必须先裁定为业务模块、技术能力模块或跨模块集成闭环。业务模块拥有业务资源、归属、状态机、领域规则和用户可见结果；技术能力模块提供受控、可复用的技术服务，不拥有业务聚合或业务终态；跨模块集成闭环只通过版本化契约连接双方，不得由任一模块越界访问另一方内部实现。
2. **建立技术能力地图**：对模块目标逐项列出所需能力，并为每项标注能力类别、提供者、状态（首次交付/复用/不启用）、输入输出契约、首个真实消费者、运行时依赖、预验证状态和启用门禁。能力应细分到可独立验证的粒度，例如受控资源读取、异步执行与租约、MinerU 文档提取、Qwen 结构化输出、Pydantic 校验和结果回传契约；不得以“文档解析”或“岗位匹配”等笼统模块名称掩盖缺失能力。
3. **先拆缺失技术能力任务**：能力地图中未交付、未预验证或契约未稳定的能力，必须先拆为独立任务。每项任务应交付最小可用实现、版本化契约、超时/错误分类、幂等或重试策略（适用时）和与首个真实消费者的验证证据。首次进入 MVP 关键路径的外部能力仍必须先满足阶段 2 的真实预验证门禁。
4. **再拆业务模块编排任务**：技术能力已交付或明确可复用后，业务模块只能依赖其公开契约，拆分资源创建与归属、业务规则、状态机、结果应用、查询/API 和用户可见闭环任务；不得在业务任务中重新实现或绕过既有技术能力。
5. **单列跨模块集成与资源类型分支任务**：当技术能力服务于多个业务资源类型时，分别拆出资源类型接入和端到端验收任务。例如 JD 解析接入依赖岗位管理先提供 JD 聚合、受控读取授权和结果应用接口；此前置未满足时，只将 JD 解析分支标记为 `blocked`，不得将已完成的解析执行底座误判为未完成。
6. **按依赖图确定执行顺序**：任务列表必须先列能力任务及其启用门禁，再列业务编排和跨模块验收任务；顺序须遵守 MVP 范围文档的模块交付编号。技术能力的独立交付不等于预建通用平台：没有已声明首个消费者、明确契约和本期启用条件的能力不得实现。

技术能力模块的完成以其声明的能力契约、首个真实消费者和自身验收为准；某个后续业务资源类型尚未具备领域前置条件，只能阻塞该资源类型接入或跨模块闭环，不能倒推否定已完成的可复用能力。业务模块的完成则必须以其所依赖能力均已启用、并完成用户可见闭环验收为准。

**阶段 4 变更包级必填输出**：在任何 `T{编号}` 任务列表之前，必须先附上以下两张表；缺失任一表时，不得进入编码实现。

| 模块/闭环 | 模块类型 | 拥有边界 | 上游契约 | 下游契约 | MVP 交付顺序与门禁 |
| --- | --- | --- | --- | --- | --- |
| {模块名称} | {业务模块 / 技术能力模块 / 跨模块集成闭环} | {资源、状态或技术职责；明确不拥有项} | {版本化请求、授权或快照} | {版本化结果、事件或快照} | {范围文档第 3.2 节编号及前置条件} |

| --- | --- | --- | --- | --- | --- | --- |

### 使用规则

- **数据校验是通用硬门禁**：开始开发前，必须确认当前任务所需的输入数据存在、格式正确、字段完整、业务状态可用且归属关系合法。任一必需数据不满足时，任务状态为 `blocked`，应先提示补齐数据，不进入实现。
- 数据前置条件应以任务自身为准。例如“生成候选人画像”要求可用的已解析简历；“上传简历”则以用户上传的文件为输入，不要求数据库中预先存在简历。
- **必需依赖是开发前门禁**：认证、Repository、数据库、接口契约等通用依赖，以及本任务声明为必需的 LLM、对象存储、向量库、异步队列等条件依赖，均须完成可用性检查。首次进入 MVP 关键路径的外部工具还必须已有阶段 2 的 `passed` 预验证记录；配置存在或仅连通不构成通过。
- 异步任务、LLM、Embedding、向量库、对象存储和第三方平台均为条件依赖；仅在任务实际使用时填写，不得将其作为所有任务的固定前置条件。
- 测试替身仅用于单元测试和故障分支覆盖，不得替代正式功能任务的必需依赖检查。
- 未通过预验证的外部技术方案只能作为调研/排障事项，不得被命名为业务实现子任务或被计入该子任务的验收完成。
- 涉及用户资源的任务，必须同时通过身份认证和资源归属校验；涉及状态变更或外部副作用的任务，必须定义合法迁移、明确授权与审计记录。
- 首次使用异步任务、LLM、检索、对象存储或第三方服务时，必须在同一变更中完成最小可用实现、故障处理、幂等/重试策略（适用时）及真实依赖验证。
- 技术能力的状态、首次交付和启用条件以 `.harness/wiki/Technical enablement and workflow governance.md` 为准；每个任务必须声明本次是首次交付还是复用。

## 回滚路线表

|  Stage |  Rollback  Strategy  |  Trigger  |
|- - - - - |- - - - - - - - - - - - - -| - - - - - -| 
|   编码实现 | git checkout - - 丢弃变更  | 编译失败 | 
|   单元测试 | 修复测试或回退代码 | 测试失败率 > 20% | 
|   代码评审 | 修改评审意见  | 🔴问题未解决 | 
|   集成测试 | 回退到上一个稳定版本  |  接口不通  | 
|   预发验证 | 回退到生产版本  | 功能异常 | 
|   上线部署 | 回滚到上一版本镜像 | 冒烟失败 | 
|    线上观测 | 紧急回滚 + 降级  | 错误率 > 1% | 





## 变更管理目录结构

```

├── .harness/changes/
│   ├── {feature-name}/                 
│   │   ├── summary.md              # 变更概述
│   │   ├── db-migrations.sql       # 数据库变更
│   │   ├── rollback.sql            # 回滚脚本
```

每个变更必须包含`summary.md`，记录：

- 变更概述
- 影响模块
- 数据库变更
- API变更
- Redis变更
- 关键约束
- 回滚方案

凡涉及数据库 Schema、约束、函数或触发器的变更，除 `summary.md` 外，必须同时提供：

- `db-migrations.sql`：可重复安全执行的正向迁移脚本。
- `rollback.sql`：仅移除本次新增数据库对象的回滚脚本，并按依赖的反向顺序执行。
