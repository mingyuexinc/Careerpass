# 开发前数据库契约收口

## 变更概述

在开始正式开发前，收口数据模型、业务模型和接口协议中的六项不一致：投递创建请求补充归属锚点；画像经简历确定候选人归属；匹配结果强制保存完整的可复现信息；全部表声明物理表名；接口画像字段和岗位业务字段统一。

## 影响模块

- 岗位匹配与结果查询
- 求职者画像
- 投递管理
- 岗位管理
- 数据库迁移

## 数据库变更

- `candidate_profiles` 删除冗余 `candidate_id`，通过 `resume_id → resumes.candidate_id` 确定归属。
- `match_results` 的评分、推荐解释和 `algorithm_version` 调整为非空，禁止持久化不完整结果。
- 所有表在数据模型中以小写复数 snake_case 名称作为唯一物理表名；首次建库与后续 Alembic 迁移必须使用这些名称。

本变更附带可重复安全执行的迁移与回滚脚本。迁移在执行非空约束前会检查历史空值；发现空值时主动失败，要求先补齐或删除不完整结果，避免静默篡改历史评分。

## API 变更

- `POST /api/v1/applications` 请求新增必填 `goal_id`，可选 `match_result_id`；创建成功状态为 `created`。
- `GET /api/v1/profile` 响应统一为 `target_job_titles`、`years_of_experience`。

## Redis 变更

无。

## 关键约束

- Repository 在同一事务中校验投递简历、可选匹配结果和求职目标的候选人归属一致。
- Repository 只能在完整匹配结果生成后写入 `match_results`。
- 迁移前先由 Alembic revision 绑定本目录 SQL；禁止手工绕过迁移执行生产 Schema 变更。

## 回滚方案

先执行 `rollback.sql`。它仅恢复本次移除的画像冗余列和放宽的非空约束；恢复的 `candidate_id` 会由关联简历回填。回滚不会删除既有业务数据。
