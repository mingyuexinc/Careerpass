# 任务拆分

## 分层实施原则

11 项原子任务不同时开发。它们被组织为 6 个能力层：只有当前层的验收门禁通过，下一层才可开始；同一层内仅允许没有依赖关系的任务有限并行。每项原子任务的预计纯开发时间仍不超过 4 小时，且合并前必须完成对应的单元测试。

```text
L0 变更治理与契约确认
  ↓
L1 应用内核（可独立启动、可稳定返回）
  ↓
L2 可观测性与安全边界（可追踪、无敏感泄露）
  ↓
L3 持久化能力（可迁移、但尚无业务数据）
  ↓
L4 异步依赖与运行态（可探测、可失败）
  ↓
L5 质量与交付（可重复验证、可发布/回滚）
```

## 能力层与阶段门禁

| 层级 | 能力目标 | 包含任务 | 允许并行 | 阶段验收门禁 | 失败处理 |
| --- | --- | --- | --- | --- | --- |
| L0 治理与契约 | 变更可追溯，外部响应契约唯一 | T0 | 无 | 变更校验通过；确认采用 `{code,msg,data}`，记录已解决的字段差异 | 修订文档，不进入编码。 |
| L1 应用内核 | 在无外部依赖模式下可启动，并对所有路径统一响应 | T1、T2、T3 | T2 与 T3 可在 T1 完成后并行 | 应用工厂可导入；配置校验正确；成功/验证/未知错误均为统一协议 | 回退本层提交；不影响 DB 或队列。 |
| L2 安全可观测性 | 每个请求可关联，且基础层不泄露敏感信息 | T4 | 无 | 请求 ID 在日志和响应一致；脱敏测试完整通过 | 禁止进入 L3；修复中间件或日志策略。 |
| L3 持久化基座 | 数据库迁移可重复执行，Session 只能由基础设施/Repository 使用 | T5 | 无 | 新库和重复执行均可 `upgrade head`；无业务 DDL；架构边界测试通过 | 回退应用变更；空基线无需 DDL 回滚。 |
| L4 异步与运行态 | 外部依赖可控接入、健康状态可安全报告 | T6、T7 | T7 的 liveness 部分可先于 T6；完整 readiness 必须在 T6 后完成 | Redis/Celery 可关闭或故障；ready 在超时内安全返回 503；探针无业务副作用 | 关闭异步配置/路由并回退应用。 |
| L5 质量与交付 | 工程可在隔离环境重复验证、发布并恢复 | T8、T9、T10 | T8 中的 fixture 可与 L4 收尾并行；T9、T10 串行 | 覆盖率和集成测试达标；发布、健康、回滚演练留痕 | 不发布；回到失败能力层修复。 |

## 质量门禁映射

| Harness 阶段 | 本变更产物/门禁 |
| --- | --- |
| 1 需求分析 | `01-analysis/impact-analysis.md` 经产品与技术确认。 |
| 2 方案设计 | `02-design/design.md` 经架构评审；确认非目标和安全边界。 |
| 3 任务拆分 | 本文件；任务均 <= 4h，依赖明确。 |
| 4 编码实现 | 仅实现设计列出的基础设施；红线零违反。 |
| 5 单元测试 | 核心逻辑 100%，总体 >=80%。 |
| 6 代码评审 | 无红色问题；重点审查配置、日志、Session 边界和健康检查。 |
| 7 集成测试 | 用隔离 Postgres/Redis 验证启动、ready 与 Alembic。 |
| 8-10 发布与观测 | 按 `07-release/release-plan.md` 演练、发布并观察。 |

## 后续业务变更的准入条件

只有当 L0-L5 全部完成并进入 `released` 后，才可启动“简历上传与异步解析闭环”变更。后续变更必须通过 Repository 使用数据库、复用响应/异常/日志组件，并单独提供数据迁移审阅文件。
