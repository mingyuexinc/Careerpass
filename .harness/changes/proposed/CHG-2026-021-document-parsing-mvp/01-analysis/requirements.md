## 1. 背景与业务价值【开发者填写】

- 要解决的用户问题：已认证候选人上传的简历需要经过简历解析环节，抽取得到简历文本内容，并按照已确定的业务规则生成候选人画像。
- Demo 成功标准（可重复演示的输入、动作和可观察结果）：
  - 上传前已脱敏、可提取机器文本的 PDF 简历后，接口快速返回“已受理，正在解析”，并创建可追踪的解析任务。
  - 固定异步工作流完成 MinerU 文本提取、Qwen 结构化画像、Pydantic/业务规则校验，并在成功时原子写入候选人画像和简历成功终态。
  - 前端自动协调查询简历列表状态；解析成功时自动进入后续可用路径，解析失败时按脱敏 `failure_code` 展示固定提示，不要求用户手动刷新。

- 不实现本模块对核心闭环的影响：
  - 简历数据无法被处理利用，后续的候选人画像生成环节无法开始
  - 候选人画像信息无法生成，后续的岗位匹配等环节无法开始

- 本模块优先级与原因：MVP 基线能力。它为核心求职闭环提供基础的数据加工和处理能力。

## 2. 用户、角色与授权【开发者填写】

- 使用者/触发者：候选人资料准备模块在正式简历上传、归属校验和对象 `ready` 后，通过固定的 `ResumeParseRequestV1` 完成跨模块契约交接；G2 在同一 PostgreSQL 事务中创建或复用对应的 queued `AsyncTaskRun`。该交接不调用本模块 Service、Dispatcher 或 Worker；G3 的 Dispatcher/Worker 只消费 G2 已创建或复用的 queued 任务。Agent workflow 不作为触发决策者，也不得传入路径、URL、MCP 参数或模型指令。

- 资源所有者：`Resume` 与 `CandidateProfile` 均归属上传该正式简历的当前候选人；简历解析模块仅拥有解析处理、任务终态与画像原子生成的职责，不拥有候选人资源。

- 各角色的读取、创建、更新、删除、执行权限：

  - 候选人仅可通过受保护接口查询归属本人的简历解析状态和已校验画像。
  - 简历解析 Worker 仅可在任务执行时，经 Repository 校验资源归属、解析状态和读取用途后，受控读取关联的正式简历。
  - 岗位匹配等下游模块仅可消费已校验的候选人画像契约，不得读取简历原文、内部对象或解析模块内部实现。

- 资源归属或访问授权链：`CurrentIdentity.candidate_id` → 归属该候选人的 `Resume` → G2 创建或复用的 queued `AsyncTaskRun` → Dispatcher/Worker → G3 Repository 重新校验候选人归属、简历状态和对象 `ready` → 受控读取对象 → MinerU MCP / 结构化校验 → 原子写入归属同一候选人的 `CandidateProfile` 与简历终态。

- 越权访问、未认证访问的预期行为：缺失、无效或过期访问令牌时返回安全 `401`；简历或画像不存在、或不归属当前候选人时返回不泄露资源存在性的安全 `404`。不得仅凭资源 ID 读取或修改资源。



## 3. MVP 范围裁决【开发者填写】

- 本期必须交付：基于 Dispatcher/Worker 的受控异步简历解析、简历解析失败的有限重试与安全终态处理，以及与简历成功终态原子生成并持久化候选人画像的能力。选择异步执行的原因是 MinerU MCP 属于可能暂时不可调用的第三方服务；在上传 HTTP 请求已结束后，系统仍需完成受控重试并提供可查询的最终状态。
- 本期明确不做：OCR/扫描 PDF、非 PDF 简历、自动脱敏、人工脱敏确认或修复、人工画像编辑、同一资源重解析、画像独立状态或独立生成任务、跨简历画像版本管理、目标职位推荐、岗位 JD 解析、匹配/投递自动触发、原始文件下载/预览、SSE、WebSocket、Webhook、通用任务运营后台和用户手动重跑接口。
- 延期能力：复杂文档格式全覆盖、OCR 质量优化、批量解析、人工标注后台、解析规则多版本、历史简历自动重解析、画像运营和通知推送能力。
- 与核心用户路径的关系：本模块承接 G2 已完成的“上传、归属校验、对象 `ready` 和 queued 任务交接”，完成“queued 任务 → 解析 → 已校验画像和终态”的下游步骤。
- 上游前置模块与下游消费者：上游为候选人资料准备模块（CHG-020），下游为岗位匹配模块；本模块不重新实现上传，也不调用 G2 内部实现。
- 最小实现（删减后仍可完成演示的边界）：消费 G2 已创建或复用的 queued 简历解析任务，受控读取归属当前候选人的可提取 PDF，完成 MinerU/Qwen 结构化解析、Pydantic/业务校验，并原子生成候选人画像和简历/任务终态。
- 不纳入理由（为未来生产、运营、规模或通用性而提出的能力）：本模块仅证明受控单份 PDF 简历可可靠完成解析和画像原子生成；上述能力不影响 MVP 核心闭环，且会引入额外的文档覆盖、运营、版本、通知或平台治理范围。
- 跨开发包依赖与契约登记：生产者为 CHG-020，消费者为本模块；契约为 `.harness/contracts/resume-parse-request-v1.yaml` 的 `ResumeParseRequestV1@v1`；联合评审标识为 `JCG-2026-020-021-RESUME-PARSE-V1`；本模块不创建第二个 queued 任务。进入阶段 4 前必须满足 CHG-020 阶段 3 `passed`、CHG-021 阶段 3 `passed`、契约 `locked`、双方批准和 `contract_hash` 一致。

## 6. 安全、隐私与模块边界【开发者填写】

- 敏感数据、凭证、路径、原文和模型输出的处理边界：原文、内部对象键、绝对路径、凭证、模型原始输出和异常堆栈不得进入 API 响应、普通日志、追踪或 Prompt。
- 日志、追踪、Prompt 和 API 响应的最小化要求：仅记录关联 ID、处理阶段、状态、脱敏失败分类、耗时和重试次数；不得记录简历正文、Markdown、路径、对象键、联系方式、凭证、模型原始响应或异常堆栈。Prompt 仅接收完成结构化画像所需的内存文本。
- 不得跨越的模块、Service、Repository、事务或数据访问边界：资料准备模块只通过固定版本化 `ResumeParseRequestV1` 完成契约交接，不调用解析模块内部 Service、Dispatcher 或 Worker；解析模块只能通过 Repository 和对象存储抽象读取资源，Service/Agent/Workflow 不得直接访问 ORM Session、SQL 或本地文件系统；解析成功的画像、简历终态和任务终态必须在同一事务中写入。
- 审计、授权或合规要求：所有资源操作校验当前 `candidate_id`；Dispatcher、Worker、重试、租约、成功和失败均记录脱敏审计；未认证请求返回 `401`，越权或不存在资源返回安全 `404`；任何失败不得产生半成品画像或重复业务结果。

## 7. 验收与演示【共同补全】

> 仅记录证明 Demo 核心路径成立的成功用例及其可观察结果。开发中出现的异常、重复、依赖或环境问题由开发者解决，不预先扩展为生产级故障、回滚、幂等或运维测试矩阵；不可降级安全边界仍以第 6 节的裁决为准。

> 本模块演示以认证候选人上传符合要求的脱敏 PDF 作为端到端起点，但上传动作属于已通过门禁的 G2 候选人资料准备模块。本变更不重新实现上传，也不要求 G2 调用 G3 内部实现；G2 在资源提交后通过固定 `ResumeParseRequestV1` 完成契约交接并创建/复用 queued `AsyncTaskRun`，G3 从已有 queued 任务开始执行。验收覆盖 G2→G3 的真实跨模块契约联调。G3 自身的模块边界从已归属、已受控存储并已完成交接的任务开始，至已校验 `CandidateProfile`、简历终态和异步任务终态结束。

- 演示用例与可观察结果：
  - 已认证候选人上传符合要求的脱敏 PDF，接口返回 `201 / UPLOAD_ACCEPTED` 和 `parse_status=processing`；数据库创建归属明确的简历、对象引用和异步任务。
  - 前端自动查询简历列表；解析成功后观察到 `succeeded`，并可通过画像接口获取已校验的 `CandidateProfile`；解析中的简历不返回部分画像。
  - MinerU 超时/临时不可用、对象读取暂不可用等临时故障按有限策略重试；重试耗尽后观察到 `failed` 和允许暴露的脱敏 `failure_code`，前端显示固定提示。
  - PDF 损坏、无有效机器文本、缺少目标职位或结构化校验失败不重试，观察到 `file_unreadable` 或 `schema_validation_failed`，且不存在半成品画像。
  - 重复上传请求、重复投递、Worker 重投递或迟到消息不会创建重复画像；非认证或非当前候选人访问返回安全 `401/404`。


## 8. 影响分析与发布策略【共同补全】

- 受影响模块、接口、数据表、迁移和前端：上游候选人资料准备模块通过固定 `ResumeParseRequestV1` 完成契约交接，不调用本模块内部实现；本模块涉及 `POST /api/v1/resumes` 的受理语义、`GET /api/v1/resumes` 的自动状态协调和 `GET /api/v1/resumes/{resume_id}/profile` 的成功画像查询；涉及 `stored_file_objects`、`resumes`、`candidate_profiles` 和 `async_task_runs`；前端增加上传受理、自动状态协调、成功画像入口和固定失败提示。
- 兼容性、数据迁移与回滚方案：沿用既有 `parse_status`、`parse_failure_code`、对象引用和画像唯一约束；不新增中间解析文本字段，不迁移或覆盖既有原始简历；运行异常时按任务/资源终态条件安全停止，不回写已成功资源，不删除仍被引用的对象。
- 发布、就绪检查和观测要求：确认 PostgreSQL、受控对象存储、Redis Broker、Dispatcher、Celery Worker、MinerU MCP 和 Qwen 凭证/配置在拟运行拓扑可用；验证健康检查、可靠入队、租约、重试、超时、重投递、失败映射和前端自动状态协调；观测仅记录脱敏关联 ID、状态、耗时、失败分类和重试次数。
- 演示证据与非生产化声明（如何重复演示；明确未覆盖的规模、运营和可用性能力）：使用受控脱敏 PDF 重复演示上传受理、自动状态协调、成功画像和确定性失败；不覆盖 OCR、复杂文档、批量解析、人工重跑、推送通知、通用任务运营后台、生产级高可用或大规模并发。
- 风险、假设与缓解措施：MinerU/Qwen/Redis 或 Worker 暂时不可用可能导致解析失败；通过有限重试、安全失败终态、无半成品原子写入和前端自动状态协调降低影响。假设上传文件已在进入系统前完成脱敏，MVP 不负责自动识别或修复敏感信息。
