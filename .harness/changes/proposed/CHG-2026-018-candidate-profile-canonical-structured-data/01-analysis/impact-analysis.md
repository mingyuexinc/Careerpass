# 影响分析

## 受影响模块与边界

| 模块 | 影响 | 约束 | 备注 |
| --- | --- | --- | --- |
| 候选人资料准备 | 明确简历与画像的结构化数据边界 | 简历解析成功时原子写入画像 | `resumes` 不保存重复 `parse_data` |
| 文档解析 | 为字段演进提供重解析路径 | 从已归属的原始文件重新解析 | 解析输出必须完成 Schema 校验 |
| 岗位匹配、投递、AI 沟通 | 统一读取画像中的已校验字段 | 不得读取中间解析结果 | 新字段成为依赖前先完成画像演进 |
| 数据模型 | 规定目标职位为非空字符串数组 | `target_job_titles` 使用 PostgreSQL 数组类型 | 实现时随候选人画像表一并创建 |

## 契约与数据影响

- API：无变更。
- 数据库与 Alembic：当前仅更新目标 Schema 约定；候选人资料准备实现时，随画像表创建 `VARCHAR(128)[] NOT NULL` 与非空数组检查约束，不存在存量数据迁移。
- Redis/Celery：无即时变更；重解析复用已有异步任务运行和版本化约束。
- 隐私：不持久化重复的简历中间解析 JSON，减少敏感结构化数据副本。

## 风险与缓解

| 风险 | 等级 | 缓解措施 |
| --- | --- | --- |
| 下游新增字段遗漏画像 Schema 演进 | medium | 将画像 Schema 扩展与原始文件重解析作为接入前置条件 |
| 解析中间结果被错误当作业务事实 | high | 明确下游只读取 `candidate_profiles`，并禁止引入 `resumes.parse_data` |
| 重解析覆盖现有可用画像 | medium | 按新任务版本执行、校验成功后原子更新；失败不得产生半成品画像 |
