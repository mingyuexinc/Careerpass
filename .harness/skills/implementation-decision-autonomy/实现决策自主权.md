# 实现决策自主权

## 目标

控制开发讨论边界，避免把局部实现选择升级为人工决策。开发者负责定义产品意图、业务边界、输入输出、核心约束和关键技术方向；Coding Agent 负责在这些约束内完成局部实现设计并继续推进。

除非决策会改变用户可观察行为、核心业务语义、已确定范围、关键架构或不可逆风险，否则不得因等待人工确认而阻塞开发。

## 责任边界

### 开发者必须裁决

**产品与范围**  
产品目标、用户价值、版本定位、业务边界，以及能力的新增、删除和延期。

**业务语义**  
核心业务规则、业务对象含义与关系、资源归属、权限含义、生命周期和状态语义。

**外部可观察契约**  
业务输入、业务输出、用户可感知的失败语义、重复操作的业务语义。

**跨 Slice 业务不变量**  
Slice 之间必须传递、产生或保留的业务信息、数据义务和业务约束。

**关键技术方向**  
是否采用某类模型、存储、队列、外部服务、Agent 范式、部署方式等方向性技术选择。

**质量与风险约束**  
有业务意义的性能、时延、可靠性、成本、安全、隐私、合规、数据保留及不可逆副作用要求。

**兼容性与演进约束**  
是否允许破坏已有接口、数据或公共契约，以及是否要求兼容、迁移和保留历史行为。

**交付与验收目标**  
明确当前 Slice 必须完成到什么范围、经过哪些真实链路验证、产生什么可验证结果，才允许认定为交付成功。

### Coding Agent 自主决策

在上述内容已经明确的前提下，Coding Agent 自主决定：

- 文件放置、函数/类拆分、命名和局部模块组织；
- 在既定分层内选择调用顺序和数据转换方式；
- Repository 内的查询写法、Service 内的编排细节和 API 层的适配代码；
- DTO、Schema、内部对象和响应组装方式，只要不改变已确定的对外契约；
- 局部异常处理、日志字段、超时、重试和幂等实现，只要符合全局约束；
- 测试夹具、测试组织、覆盖方式和验证顺序；
- 多个等价技术方案中的具体实现。

## 是否阻塞的判断

遇到需要选择的技术问题时，按以下顺序执行：

1. 用一句话写清楚当前决策，不把多个问题混成一个问题。
2. 阅读根入口、子工程入口、当前 Slice 文档、相关事实源和现有代码。
3. 判断该决策是否会改变以下任一内容：
   - 用户可观察行为或接口输出；
   - 核心业务语义、权限、归属或状态迁移；
   - 已确认的范围、验收条件或跨 Slice 交接；
   - 关键架构方向、公共基础设施或外部能力边界；
   - 安全、隐私、数据完整性或不可逆副作用；
   - 需要开发者承担的成本、风险或产品取舍。
4. 若全部不会改变，标记为“局部实现决策”，直接选择方案并继续。
5. 若至少会改变一项，标记为“产品或架构决策”，暂停受影响的实现，提出最小必要问题，等待开发者裁决。

不得因为“有多个写法”“未来可能变化”“开发者可能有偏好”或“希望确认实现细节”而自动阻塞。

## 等价方案选择规则

当多个方案在产品行为、业务语义、已确定范围和关键架构上等价时，按以下优先级选择：

1. 与当前代码和既有分层最一致；
2. 改动范围最小；
3. 复杂度、依赖和维护成本最低；
4. 最容易测试、回滚和解释；
5. 最少引入新的抽象、配置或基础设施。

选择后记录一句简短理由即可，不等待人工确认，不展开无收益的方案比较。

## 执行与记录

自主决策时：

- 先查找现有代码中的同类实现并优先复用；
- 遵守 Repository、统一响应、权限归属、状态机、敏感信息和异步可靠性红线；
- 将必要的局部决策记录在当前 Slice 的技术方案或实现说明中；
- 只有当该决策形成稳定的跨 Slice 事实时，才同步对应全局文档；
- 在最终说明中报告重要假设、选择的方案和验证结果，不把局部选择包装成待开发者批准的事项。

自主决策不等于越过 Gate。若实现中发现原设计无法满足既定产品约束，应停止受影响的实现并按影响回退到 Slice Select、Slice Design 或 Readiness Check。

## 输出格式

完成判断后，使用以下最小格式记录，不把局部实现问题包装成待审批事项：

### 可以自主决策

```text
结论：局部实现决策
方案：<选择的实现方式>
理由：<与现有代码一致、改动最小或复杂度最低等，一句话说明>
验证：<已完成或将执行的检查>
```

### 必须请求裁决

```text
结论：需要开发者裁决
决策点：<唯一需要裁决的问题>
影响：<会改变的产品行为、业务语义、范围、架构或风险>
选项：<必要时列出选项及其差异>
```

请求裁决前，先完成能够独立完成的代码阅读、事实核对和局部分析；不要把可自主决策的命名、拆分、调用顺序或测试写法放进问题中。

## 必须暂停并请求裁决的信号

出现以下任一情况时暂停，不自行猜测：

- 需求同时允许和禁止同一行为，且无法由现有事实源消解；
- 需要新增产品能力、改变已有范围或删除已承诺能力；
- 需要改变用户看到的字段、状态、流程、权限结果或错误语义；
- 需要改变已锁定的 API、任务、数据或跨 Slice 交接契约；
- 需要选择新的全局架构、存储、队列、模型或外部服务；
- 方案会引入不可逆数据迁移、外部副作用、隐私风险或明显成本；
- 验收条件不足以判断实现是否正确，且现有文档和代码无法补足。

提问时只描述：决策点、受影响的产品或架构语义、可选项及其差异。不要把已经可以自主完成的局部实现细节夹带进问题。

## 示例

| 情况 | 处理 |
| --- | --- |
| 已确定使用 Repository，但查询使用 `select` 还是封装一个已有查询方法 | 自主选择与现有代码一致且改动最小的方式 |
| 已确定登录返回 `user_id` 和角色，内部使用 dataclass 还是普通字典 | 自主选择，不阻塞开发 |
| 是否增加 `hr_profile_id` 字段并返回给前端 | 若改变已确定输出或身份语义，请求开发者裁决 |
| 两种重试次数都不改变产品行为，但一个方案复用现有任务基类 | 选择复用现有任务基类的方案并继续 |
| 发现当前设计无法区分“无权访问”和“资源不存在”，而契约要求统一错误语义 | 按既定契约实现；若需要改变对外错误语义，再回退并请求裁决 |
| 需要把同步接口改成异步任务才能完成需求 | 这会改变架构和运行语义，暂停并请求裁决 |
