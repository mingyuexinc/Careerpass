# Careerpass 前端开发规范

> 版本：v0.1
>
> 适用范围：`careerpass-frontend/src/` 正式前端源码
>
> 技术栈：TypeScript + React

## 1. 文档定位

本文档约束正式前端的代码组织、组件开发、数据与视图分离、状态处理、样式实现、测试以及 AI/Codex 修改代码的方式。

本文档不约束 `prototypes/` 下的 HTML 原型实现。原型只提供流程、视觉和交互参考，正式源码必须遵守本规范。

## 2. 基本原则

| 原则 | 要求 |
| --- | --- |
| 组件化 | 页面由业务组件和通用组件组合，不复制大段 HTML 结构 |
| 类型优先 | 领域对象、状态值、组件 Props 和数据访问结果使用明确 TypeScript 类型 |
| 数据视图分离 | 页面负责展示和交互，数据访问和状态迁移由业务层负责 |
| 单一来源 | 状态值、显示文案和状态颜色集中维护 |
| Mock 解耦 | 页面不直接读取或修改 Mock Fixture |
| 状态完整 | 正常、加载、空、失败、成功和禁用状态都要设计和实现 |
| 适度抽象 | 只抽取有复用价值或有明确业务语义的代码 |
| 可替换 | 后续替换真实 API 时尽量不改页面结构 |
| 先保证可读 | 优先选择清晰直观的实现，不为了减少文件数量压缩业务逻辑 |

## 3. 工程目录规范

```text
src/
├── app/                 # 应用入口、路由和全局 Provider
├── layouts/             # 应用外壳和角色布局
├── pages/               # 页面入口
├── features/            # 按业务域组织的组件、Hook 和行为
├── components/          # 跨业务域通用组件
├── api/                 # 数据访问接口、Repository 和 Mock 实现
├── domain/              # 领域类型、状态和映射
├── stores/              # 跨页面共享状态
├── styles/              # 全局样式和设计令牌
├── lib/                 # 无业务含义的通用工具
└── test/                # 测试辅助工具和公共 Fixture
```

| 内容 | 放置位置 |
| --- | --- |
| 页面组件 | `pages/` |
| 求职者资料相关业务 | `features/resumes/` |
| 求职目标相关业务 | `features/job-goals/` |
| 投递和进度相关业务 | `features/applications/` |
| 沟通和消息相关业务 | `features/conversations/` |
| 岗位相关业务 | `features/jobs/` |
| 登录和用户状态 | `features/auth/`、`stores/auth-store.ts` |
| 按钮、卡片、空状态 | `components/` |
| Mock Fixture | `api/mock/fixtures/` |
| 状态映射 | `domain/mappings.ts` 或对应业务域 |
| 设计变量 | `styles/tokens.css` |

禁止在 `src/` 之外新增正式前端运行代码。原型运行代码和原型资源仍放在 `prototypes/`。

## 4. 命名规范

| 类型 | 命名方式 | 示例 |
| --- | --- | --- |
| React 组件 | PascalCase | `ProgressTimeline.tsx` |
| 页面 | PascalCase + `Page` | `CandidateProgressPage.tsx` |
| Hook | camelCase + `use` 前缀 | `useResumeUpload.ts` |
| Store | kebab-case + `-store` | `auth-store.ts` |
| 类型文件 | `types.ts` 或业务名 + `types.ts` | `application-types.ts` |
| 工具函数 | camelCase | `formatDate.ts` |
| 样式文件 | 与组件同名 `.module.css` | `ProgressTimeline.module.css` |
| Fixture | 业务名复数 | `applications.ts` |

代码命名规则：

- 变量和函数使用 `camelCase`。
- 组件、类型和接口使用 `PascalCase`。
- 布尔值使用 `is`、`has`、`can`、`should` 前缀。
- 事件处理函数使用 `handle` 前缀。
- 异步数据访问函数使用明确动词，如 `listApplications`、`uploadResume`、`sendMessage`。
- 不使用 `data`、`item`、`temp` 等无法表达业务含义的长期变量名。

## 5. 页面和组件规范

### 5.1 页面组件

页面组件负责组织页面布局、组合业务模块、读取页面状态、触发业务操作和选择状态视图。

页面组件不得：

- 直接读取或修改 Mock Fixture。
- 直接拼接数据访问地址。
- 重复实现状态迁移。
- 承担跨页面共享状态。
- 复制其它页面的大段 JSX 和样式。

### 5.2 业务组件

业务组件放在对应的 `features/` 下，可以理解简历、求职目标、投递记录和会话等领域对象，但不应依赖具体页面路径。

```text
features/applications/
├── ApplicationCard.tsx
├── ApplicationStatusSelect.tsx
├── useApplications.ts
└── application-types.ts
```

### 5.3 通用组件

通用组件放在 `components/` 下，只依赖通用 Props，不包含岗位、简历或 Agent 等具体业务规则。

优先复用或沉淀：`Button`、`Card`、`StatusBadge`、`LoadingState`、`EmptyState`、`ErrorState`、`FileUpload`、`Modal`、`Toast` 和 `ProgressBar`。

不要为了形式统一，将只使用一次且没有稳定业务语义的代码强行抽成通用组件。

## 6. TypeScript 规范

- 默认开启严格类型检查。
- 禁止使用无理由的 `any`。
- 外部数据、Mock 数据和用户输入都应经过类型约束或运行时校验。
- 组件 Props 使用明确的接口或类型定义。
- 领域状态使用联合类型，不使用任意字符串。
- 可空数据显式表达，例如 `Resume | null`。
- 数据访问函数声明明确的返回类型。

示例：

```ts
type AgentStatus = "not_started" | "ready" | "running" | "finished";

interface AgentStatusCardProps {
  status: AgentStatus;
  canStart: boolean;
  onStart: () => void;
}
```

## 7. 数据与视图分离

正式前端遵循以下调用链：

```text
页面 → 业务组件或 Hook → Repository 接口 → Mock Repository → Demo Fixture
```

### 7.1 页面层

- 页面只调用业务 Hook 或状态 Action。
- 页面不直接 import `api/mock/fixtures/`。
- 页面不直接修改数组、对象或嵌套业务字段。
- 页面不重复计算同一业务状态。
- 页面只负责将业务状态映射成布局和组件。

### 7.2 Repository 层

- Repository 暴露业务动作，不暴露 Fixture 内部结构。
- 参数和返回值使用明确类型。
- Mock Repository 模拟必要的延迟、失败和重复提交场景。
- 后续接入真实 API 时，优先替换 Repository 实现。
- Repository 不负责页面跳转和 Toast 展示。

### 7.3 Fixture 层

- Fixture 按业务域集中存放。
- Fixture 使用固定、脱敏、可解释的数据。
- 不写入真实密码、Token、联系方式或完整简历原文。
- 返回数据时优先返回副本，避免组件污染初始数据。
- 不同页面状态使用明确的数据集或场景配置，不复制隐含数据。

## 8. 状态管理规范

| 状态 | 管理方式 |
| --- | --- |
| 输入框内容、弹窗开关 | 组件局部状态 |
| 当前选中岗位或会话 | 页面或业务 Hook，必要时进入 Store |
| 当前登录身份 | `auth-store` |
| 简历、目标、投递和会话 | `demo-store` 或业务状态模块 |
| 上传、解析、发送中 | 对应业务 Hook |
| 状态文案和颜色 | `domain/mappings.ts` |

Store 规则：

- Store 只保存需要跨页面共享的数据。
- Store 通过方法暴露状态变化，不暴露任意字段写入。
- 每个 Action 负责一个清晰的业务动作。
- Action 内校验必要的前置条件。
- Action 返回成功或失败结果，页面负责展示反馈。
- 不创建包含所有页面数据和所有操作的巨型 Store。

状态迁移统一遵循：

```text
用户操作 → Action 校验前置条件 → 更新状态 → 返回结果 → 页面展示反馈
```

例如，HR 修改投递状态时，只能修改当前岗位下当前候选人的一条投递记录，不能修改候选人全局状态。

## 9. 异步操作规范

所有异步操作至少考虑以下状态：

```ts
type AsyncState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success" }
  | { status: "error"; message: string };
```

操作要求：

- 提交前校验输入和前置条件。
- 开始操作后立即进入处理中状态。
- 处理中禁止重复提交。
- 成功后更新受影响数据并展示成功反馈。
- 失败后保留可恢复的输入和页面上下文。
- 错误信息使用受控文案，不展示堆栈或内部路径。
- 页面卸载或切换时避免将过期结果写回当前状态。

重点覆盖简历上传、简历解析、资料上传、岗位上传、Agent 启动、消息发送和投递状态更新。

## 10. 状态值和文案规范

状态值、文案、颜色和是否终态集中维护，页面不得自行改写：

| 状态值 | 统一文案 |
| --- | --- |
| `processing` | 解析中 |
| `succeeded` | 解析成功 |
| `failed` | 解析失败 |
| `submitted` | 已投递 |
| `screening` | 初筛中 |
| `written_test` | 笔试 |
| `interview_1` | 一面 |
| `interview_2` | 二面 |
| `interview_3` | 三面 |
| `hr_interview` | HR 面 |
| `offer` | 获得 Offer |
| `terminated` | 流程终止 |

状态不能只靠颜色区分，必须同时提供文字或结构表达。

## 11. 样式和表单规范

- 使用 CSS Modules 编写组件局部样式。
- 全局颜色、字体、圆角、阴影和间距使用设计令牌。
- 颜色基准遵循浅灰背景、白色卡片和橙色品牌主题。
- 不在 JSX 中大量堆叠内联样式。
- 不在业务页面重复定义相同的颜色和间距。
- 组件状态通过明确的 class 或变体表达。
- 长文本、文件名和岗位名称必须处理截断或换行。
- 表单控件使用明确标签、受控状态和字段级错误反馈。
- 提交期间禁用重复提交，成功后清理不再需要的临时输入。

文件规范：

- 文件输入只负责选择文件，处理由业务层完成。
- 文件名称使用脱敏或 Demo 名称。
- 不展示真实存储地址、内部路径和原始文件正文。
- 简历和其它资料使用不同的业务状态展示。
- Agent 运行中或已结束时，当前轮次简历替换入口禁用。

## 12. 路由和访问体验

- 路由配置集中维护。
- 未登录用户访问业务页时返回登录页。
- 求职者不能进入 HR 页面，HR 不能进入求职者页面。
- 页面访问限制用于前端体验，不能被视为真实安全边界。
- 登录身份变化后清理不属于新角色的页面状态。
- 页面跳转使用路由，不通过手工修改 DOM 或隐藏区域实现。

## 13. 可访问性规范

- 表单控件具备可见标签或等价可访问名称。
- 图标按钮提供 `aria-label` 或可见文本。
- 所有可交互元素支持键盘访问。
- 聚焦状态清晰可见。
- 进度条提供当前值、目标值和可访问名称。
- 加载、成功和失败状态不仅依赖颜色表达。
- 禁用控件在必要时说明禁用原因。
- 对话消息列表和发送区域在键盘操作下保持可用。

## 14. 测试规范

| 测试层级 | 内容 |
| --- | --- |
| 类型检查 | TypeScript 编译和类型约束 |
| 单元测试 | 状态映射、状态迁移、数据访问和格式化函数 |
| 组件测试 | 上传卡片、进度条、消息列表、状态标签 |
| 页面测试 | 登录、资料、任务、进度、沟通和投递页面 |
| 流程测试 | 从登录到 Agent 结束的完整 Demo 路径 |
| 构建测试 | 生产构建、路由和静态资源加载 |

测试要求：

- 测试用户行为和页面结果，不测试组件内部实现细节。
- Mock Repository 应可替换为测试实现。
- 状态迁移和状态映射必须有单元测试。
- 每个新增业务状态至少补充一个对应展示测试。
- 修复 Bug 时优先增加能够复现问题的测试。

## 15. AI/Codex 修改代码规范

### 15.1 修改前

1. 阅读与任务直接相关的产品、架构、设计和 Demo 数据文档。
2. 确认修改属于 `src/` 正式前端，而不是 `prototypes/` 原型包。
3. 找到现有页面、组件、状态和数据访问边界，优先复用已有能力。
4. 明确本次修改影响的页面、状态、Mock 数据和测试。

### 15.2 修改中

- 优先进行小范围、可验证的修改。
- 不把固定数据直接写进页面组件。
- 不为了视觉效果绕过组件或数据层边界。
- 不引入架构文档未确定的新框架或状态管理方式。
- 不改变状态值、页面范围或主流程而不更新相关文档。
- 不删除用户已有的非相关修改。
- 不把调试输出、敏感数据或完整异常写入页面和日志。

### 15.3 修改后

至少执行与改动匹配的检查：

- TypeScript 类型检查。
- ESLint 和格式检查。
- 相关组件或页面测试。
- 关键流程手动验证或自动化验证。
- 检查加载、空、失败、成功和禁用状态。

## 16. 禁止事项

- 禁止在页面组件中直接维护岗位、简历、投递或消息的长期业务数据。
- 禁止从 `prototypes/html-demo/index.html` 直接复制整套单文件业务逻辑作为正式实现。
- 禁止在多个页面分别定义同一个状态值和中文文案。
- 禁止使用 `any` 掩盖领域类型问题。
- 禁止通过隐藏按钮或前端显示控制替代业务状态判断。
- 禁止在代码中写入真实密码、Token、联系方式或敏感文件内容。
- 禁止把内部路径、调试堆栈和原始异常直接展示给用户。
- 禁止为尚未进入本期范围的多轮投递、实时推送或通用 Agent 平台预先堆建复杂架构。
- 禁止未经确认修改品牌主色、核心页面布局和状态语义。
