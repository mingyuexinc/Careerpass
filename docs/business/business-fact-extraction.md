# 业务事实提取与维护机制

## 1. 机制目标

本机制用于从前端产品文档中提取稳定、可复用、跨前后端的业务事实，形成 [`business-baseline.md`](business-baseline.md)。

它解决两个问题：

- 前端事实分散在流程、页面、决策和本地数据文档中，Slice 开发前无法快速判断哪些业务语义已经确定；
- 前后端分别重复解释目标、规则和状态，导致同一事实出现多种表述或在技术细节讨论中反复重新裁决。

业务基线只定义业务语义，不替代 API、数据库、代码、视觉规范或前端本地数据实现。

## 2. 来源文档与职责

### 2.1 主要提取来源

| 来源 | 提取内容 | 不直接提取为业务事实的内容 |
| --- | --- | --- |
| `careerpass-frontend/docs/product/frontend-acceptance-flow.md` | 角色、主流程、用户可观察结果、业务状态和交互规则 | 页面布局、测试勾选状态和原型限制 |
| `careerpass-frontend/docs/product/frontend-product-flow.md` | 页面承载的业务动作、页面关系和用户可见结果 | 组件形态、视觉表现和页面组织 |
| `careerpass-frontend/docs/decisions/frontend-development-decisions.md` | 已裁决的产品范围、非目标和核心交互决策 | Mock、前端工程实现和技术选型 |
| `careerpass-frontend/docs/development/local-data-spec.md` | 业务对象关系、状态候选和主流程所需的最小数据语义 | 固定 ID、展示文本、Mock 数量和本地字段名 |

### 2.2 校验和落地来源

| 来源 | 用途 |
| --- | --- |
| `careerpass-backend/docs/product/backend-delivery-scope.md` | 校验当前版本范围是否已经被后端范围决策承接 |
| `careerpass-backend/docs/product/business-rules.md` | 校验跨 Slice 后端规则是否与业务事实一致 |
| `careerpass-backend/docs/domain/domain-model.md` | 校验领域对象、关系和状态实现是否承接业务语义 |
| 当前代码、迁移、测试和具体 Slice 文档 | 证明实现状态，不自动改变业务事实 |

后端实现证据不能反向把未裁决的实现提升为产品事实；产品语义变化必须由开发者或产品负责人裁决。

## 3. 什么可以进入业务基线

一条事实必须满足以下条件中的至少一项，并且能够用一句话独立表达：

- 影响用户可以执行的操作或用户可以观察到的结果；
- 影响角色、资源归属、授权边界或跨角色协作；
- 影响业务状态、状态迁移、终态或流程结束条件；
- 影响当前版本范围、非目标、延期能力或不可逆业务副作用；
- 被两个或以上 Slice 使用，或者需要前后端共同遵守。

以下内容不进入业务基线：

- API 路径、请求/响应字段、HTTP 状态码、数据库表、字段和索引；
- 类、方法、Repository、任务队列、框架、部署和存储实现；
- 页面布局、颜色、组件、Mock ID、固定展示文本和测试夹具；
- 只有一个 Slice 的局部实现选择；
- 尚未确认的未来实体、接口、状态或技术方案。

## 4. 提取步骤

### 4.1 收集候选事实

读取四类主要来源，提取角色、对象、流程、前置条件、业务规则、状态、范围和验收结果。每条候选事实必须保留来源文档路径。

### 4.2 原子化和去重

- 一条记录只表达一个事实，不把目标、规则和实现混在同一句中；
- 删除页面文案、Mock 字段和技术字段，只保留业务含义；
- 合并不同文档对同一事实的重复表述；
- 为稳定事实分配不可复用的事实编号，例如 `BF-RULE-006`；
- 后续文档引用事实编号，不复制整段规则。

### 4.3 事实分类

每条事实归入以下类别之一：

| 类别 | 说明 |
| --- | --- |
| `scope` | 当前版本包含、排除或延期的能力 |
| `role` | 角色职责和可见范围 |
| `object` | 业务对象及其业务用途，不代表数据库实体 |
| `flow` | 用户操作、前置条件和主要业务结果 |
| `rule` | 跨 Slice 业务约束 |
| `state` | 用户可观察业务状态和合法迁移 |
| `relation` | 业务对象之间的归属、关联和交接关系 |

### 4.4 冲突登记和裁决

当来源文档存在不一致时：

1. 不自动选择篇幅更长、更新时间未知或实现成本更低的表述；
2. 将冲突登记到业务基线的“待裁决事项”中；
3. 说明冲突来源、影响的业务语义和受影响的 Slice；
4. 由开发者或产品负责人作出唯一裁决；
5. 将裁决后的事实写入基线，并在来源文档或下游文档中改为引用该事实；
6. 未裁决事实不得作为当前 Slice 的已确认验收条件。

只有影响当前 Slice 的未裁决事实阻塞该 Slice；与当前 Slice 无关的冲突记录在案，但不阻塞无关工作。

本次 S-02 问题记录：原始 HTML 原型的岗位 JD 区域采用“选择文件后立即上传”，正式页面却增加了原型不存在且流程不需要的“确认上传”按钮；同时原型和前端说明曾允许 PDF、DOCX 等多种格式，而当前受控演示实际只需要 Markdown（`.md`）岗位 JD。该冲突已裁决为：选择一份或多份 `.md` 文件后立即上传，不设置额外确认按钮；结果语义仍由 `IC-S02-JD-UPLOAD` 约束。裁决已写入业务基线 `BF-FLOW-009`，并影响 S-02 页面、后端文件校验、Integration Contract 和 Integration Scenario。

### 4.5 发布和同步

业务基线发布后：

- 根入口和前后端入口指向业务基线；
- Slice Design 先阅读业务基线，再定义 Slice 专属范围和技术设计；
- 后端业务规则、领域模型和数据库设计只记录各自职责范围内的事实；
- 前端产品文档保留页面和流程证据，但不再作为 Slice 开发者寻找跨工程业务规则的唯一入口。

## 5. 业务事实状态

| 状态 | 含义 | Slice 是否可以直接使用 |
| --- | --- | --- |
| `confirmed` | 已由产品/开发者明确确认，来源和影响范围清晰 | 可以 |
| `derived` | 从多个来源归纳而来，尚未发现冲突，但仍需在下一次基线评审中确认 | 仅可作为设计线索，不可作为不可逆裁决依据 |
| `pending` | 存在未裁决冲突、缺失或范围不清 | 影响该事实的 Slice 不可以 |
| `superseded` | 被新的业务裁决替代，仅用于追溯 | 不可以 |

当前业务基线只把 `confirmed` 事实作为跨前后端默认依据；`derived` 和 `pending` 必须显式标注。

## 6. 切片使用协议

### 选择切片

- 阅读业务基线，确认候选 Slice 的主要业务结果、前置条件、角色和 Non-goals；
- 列出依赖的事实编号；
- 若主要结果或边界依赖 `pending` 事实，保持 blocked 并请求裁决。

### 设计切片

- `slice-spec.md` 只描述本 Slice 的业务应用，不复制全局事实；
- 在 `Business Rules`、`Preconditions` 或 `Scope / Non-goals` 中引用相关事实编号；
- 仅记录本 Slice 新增、细化或例外的业务规则；
- `technical-design.md` 不重新定义业务事实，只说明 API、数据和实现如何承接事实。

### 就绪检查

- 确认所有影响当前 Slice 的事实为 `confirmed`，或已经完成开发者裁决；
- 确认业务基线、Slice 规格、技术设计和后端事实源没有语义冲突；
- `derived` 事实如果被当作对外行为、状态或数据边界使用，必须先升级为 `confirmed`。

### 实现、验证与关闭

- Implement 不得通过代码选择改变 `confirmed` 业务事实；
- Verify 按业务基线验收用户可观察结果、规则和状态；
- Close 前确认实现没有产生新的未记录业务事实；如产生，回退到 Slice Design 或更新业务基线后再关闭。

## 7. 更新触发条件和检查清单

出现以下变化时必须重新提取或评审业务基线：

- 前端新增、删除或改变用户操作、页面流程或状态表现；
- 产品范围、角色、核心对象、资源归属或跨角色协作发生变化；
- Slice 发现现有事实无法支持验收，或两个事实源出现冲突；
- 后端实现需要改变用户可观察行为、状态语义或外部副作用；
- 前端 Mock 数据被误认为后端业务事实，需重新归类。

更新完成前检查：

- 每条新增事实有来源和事实编号；
- 事实不包含 API、数据库或局部实现细节；
- 重复事实已经合并，冲突已经登记；
- 受影响的 Slice、领域、业务规则和范围文档已经检查；
- `confirmed`、`derived`、`pending` 和 `superseded` 状态使用正确；
- 业务基线和入口导航链接可访问。
