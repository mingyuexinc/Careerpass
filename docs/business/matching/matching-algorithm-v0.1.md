# S-08 岗位 JD 匹配算法 v0.1

> 状态：算法方向和演示边界已裁决，具体权重、阈值和归一化参数待 S-08 Technical Design 由 Coding Agent 生成并通过测试锁定。
>
> 本文档是跨前后端共享的岗位匹配业务规则事实源；S-08 技术设计和实现只引用本文件，不在技术 Slice 文档中重复定义算法业务规则。
>
> 本文档定义 v0.1 的完整算法边界：岗位过滤、匹配评分、结果状态和推荐理由。API、数据库表结构、异步任务实现和前端 Contract 不在本文定义。

## 1. 版本边界

- `v0.1` 表示完整的“过滤 + 匹配 + 推荐理由”流程版本。
- 当前 Demo 只验证一个版本；过滤器、岗位族识别、层级判断和技能匹配不单独维护版本号。
- Match 结果必须记录使用的算法版本；算法升级不在当前版本范围内。
- 当前演示岗位池最多包含 20 个可用结构化岗位 JD；S-08 在 S-07 启动事务提交后同步执行。

## 2. 匹配输入

S-08 只使用已解析并校验的业务语义摘要，不读取 JD 或简历原文。

### 2.1 岗位输入

只使用 S-03 形成的五项核心字段：

- 岗位名称；
- 工作地点；
- 薪资；
- 岗位职责；
- 任职要求。

公司简介、优先条件、加分项和其他非核心标题不解析，不进入过滤、评分或推荐理由。

### 2.2 候选人输入

使用 S-04 已校验的候选人简历业务语义摘要，包括岗位经历、项目经历、技能、工作年限及可用于能力层级判断的结构化信息。工作经历和项目经历的 `highlights` 属于技能证据；联系方式等仅用于匹配资格校验，不进入推荐理由。

### 2.3 求职目标输入

只使用其中可识别的硬过滤条件。`offer_target` 不参与匹配分数，也不限制本轮投递数量。

## 3. 处理流程

```text
硬过滤
  → 岗位名称归一化和岗位族识别
  → 能力层级判断
  → 技能项提取和技能匹配
  → 三维加权总分
  → 阈值判断
  → Match 持久化
  → 匹配成功后创建 Application
```

同一 Agent 运行上下文中，同一 Job 只允许执行一次上述流程。

S-08 同步执行完成后，启动请求才返回；前端不展示匹配过程，求职者进入求职进度页查看已创建的 Application。

## 4. 硬过滤

### 4.1 用户过滤条件

- “不考虑北京”等排除地点条件属于硬排除；岗位命中后进入 `filtered_out`。
- “薪资不低于 20K”等明确薪资条件属于硬排除；岗位不满足后进入 `filtered_out`。
- “优先某地”等软偏好不纳入 v0.1，属于延期能力。
- 自由文本只有在识别出明确过滤业务语义时才生效；未识别出业务语义时，视为没有过滤条件。

### 4.2 当前岗位范围

当前版本只支持 AI 软件开发岗位族。无法归入当前支持范围的岗位不进入 v0.1 评分，并记录为 `filtered_out`，原因标记为超出当前岗位族范围。

## 5. 岗位名称和岗位族

- 岗位名称完全一致时，名称匹配通过。
- 名称不一致时，使用受控岗位族体系判断，不使用无限制的字符串模糊匹配作为最终结论。
- AI 应用开发、大模型开发属于 AI 软件开发岗位族。
- 普通后端开发不属于 AI 应用开发岗位族。
- 混合岗位先拆分为子岗位，再对每个子岗位分别判断；当前版本按属于 AI 软件开发方向的子岗位进入后续计算。

岗位名称相似性用于岗位族归一化和岗位画像评分，不单独替代三维评分结果。

## 6. 三维匹配评分

三个维度分别计算并保存，但允许通过加权总分互相补偿。岗位画像不设置独立硬性否决。

### 6.1 维度一：岗位画像

判断岗位本质类型和候选人经历体现的岗位方向是否相近。当前版本假设 JD 岗位名称与正文描述一致，因此主要依据受控岗位族和候选人经历进行评分。

### 6.2 维度二：能力层级

岗位和候选人分别归一化为低、中、高三个层级：

- 同级得分最高；
- 相差一级，保留部分得分；
- 相差两级，该维度得分为 0。

岗位层级依据岗位名称、职责范围和 JD 业务语义判断；候选人层级依据简历职位、工作经历、项目复杂度和工作年限等结构化信息判断。

### 6.3 维度三：技能匹配

岗位胜任度不再逐项匹配全部任职要求，只提取技能相关描述进行匹配。

纳入范围包括：

- 编程语言；
- AI、大模型、RAG、Agent 等技术能力；
- 框架、数据库、中间件、云平台和开发工具；
- 软件工程方法和与岗位直接相关的技术能力。

候选人技能证据统一来自顶层 `skills`、项目 `technologies`、工作经历 `highlights` 和项目 `highlights`，以及工作/项目标题和摘要中的明确技术事实。技能章节存在但解析后仍为空时，简历解析不得静默形成可匹配画像。

不纳入技能匹配的内容包括：

- 工作年限；
- 初级、中级、高级等层级描述；
- 管理职责和责任范围；
- 学历、证书等非技能要求。

岗位技能项和候选人技能项进行归一化后计算覆盖情况。候选人没有明确技能证据时，该技能项得分为 0；技能项不设置单独的硬性淘汰规则。

## 7. 总分和匹配结论

三维得分按 Coding Agent 在 S-08 Technical Design 中锁定的权重计算：

```text
total_score =
  role_score × role_weight
  + level_score × level_weight
  + skill_score × skill_weight
```

当总分达到版本阈值时，Match 结论为匹配成功；否则为 `not_matched`。

具体权重、分值范围、阈值和技能归一化参数属于 v0.1 的实现参数，不在本方向文档中预先写死。

## 8. Match 结果状态

同一 `run_id + job_id` 只保存一条 Match 评估结果：

| 状态 | 含义 | 评分结果 |
| --- | --- | --- |
| `filtered_out` | 被用户硬过滤条件或当前岗位族范围排除 | 不计算评分 |
| `not_matched` | 已进入评分，但总分未达到阈值 | 保存三维得分和总分 |
| `matched` | 总分达到阈值 | 保存完整评分结果 |
| `application_created` | 已根据匹配结果创建系统内投递记录 | 保存完整评分结果 |

求职进度页只查询已创建的 Application，不展示 `filtered_out`、`not_matched` 或未形成投递记录的 Match。

Application 的安全展示结果包括对应 Match 的推荐匹配得分和推荐理由。

当至少一个有效岗位进入本轮算法、全部有效岗位均已筛选且 Application 数量为 0 时，Agent 以 `no_match` 原因结束；未准备好的岗位不参与算法，也不触发 `no_match`。

## 9. 推荐理由

推荐理由由确定性规则模板生成，不依赖大模型。理由至少覆盖：

- 岗位画像匹配情况；
- 能力层级比较结果；
- 技能匹配覆盖情况；
- 过滤或未匹配原因（适用时）。

推荐理由在 Match 生成时创建并持久化，查询时不重新调用模型或重新计算。

## 10. 非目标

- 不解析公司简介、优先条件、加分项及其他非核心 JD 内容；
- 不支持“优先某地”等软过滤；
- 不引入向量召回、重排序或 LLM 匹配；
- 不区分任职要求中的“必须”和“优先”；
- 不单独判断学历、证书和管理经历；
- 不支持算法子模块独立版本管理；
- 不在本版本处理多轮匹配和算法升级。
- 不在本版本处理匹配任务失败、Application 创建失败或无可用 JD 的业务分支。
