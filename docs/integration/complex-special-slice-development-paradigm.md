# 复杂/特殊切片开发范式

## 1. 适用范围

本范式用于一个 Slice 包含多个相互关联的演示场景，且场景共同依赖 Agent、工具调用、动态状态、跨角色协作或较多失败/副作用边界的情况。

S10 AI 求职沟通属于典型适用对象。它可以拥有多个 Integration Scenario，但仍必须先确认这些场景共同服务于一个清晰的 Slice 主结果；如果场景之间是相互独立的业务结果，应拆分为多个 Slice。

本范式是六阶段 Slice 门禁的执行细化，不新增或替代 `Slice Select`、`Slice Design`、`Readiness Check`、`Implement`、`Verify`、`Close`。项目级业务事实、Slice 规格、技术设计、Integration Contract 和 Integration Scenario 仍以既有事实源为准。

## 2. 核心判断

提出的顺序是合理的，但需要做三点调整：

1. 在“关键演示场景”之前先锁定 Slice 边界、主结果、非目标和场景集合，防止多个场景无边界地汇总成一个大 Slice。
2. “统一 Agent 执行骨架”只统一编排、校验、授权、状态、幂等、失败和审计边界，不预建脱离场景的通用 Agent 平台，也不让模型直接写业务数据或触发副作用。
3. 场景验收既是每个场景的交付门，也是最终 Slice 验收的输入；任一场景的契约、权限、状态或数据边界变化，都要按六阶段回退规则重新设计。

因此，复杂切片采用以下主流程：

```text
Slice 边界与场景地图
  → 关键演示场景
  → 场景能力拆解
  → 按场景补业务事实
  → 统一 Agent 执行骨架与契约设计
  → 逐场景纵向实现
  → 场景验收与回归
  → 最终 Slice 验收
```

## 3. 阶段与产物

### 3.1 Slice 边界与场景地图

对应 `Slice Select`。先记录：

- Slice ID、触发条件、唯一主要业务结果和稳定结束点；
- 场景 ID、角色、用户操作、前置 Slice、演示数据和用户可观察结果；
- 场景之间的共享上下文、差异点、依赖关系和实施顺序；
- 当前范围、非目标、跨 Slice Handoff 和至少一个 Integration Scenario。

场景地图是组织开发的索引，不是新的业务事实源。每个场景仍需落到对应的 Integration Scenario 文档。

### 3.2 关键演示场景

从真实前端或稳定内部入口出发，优先选择能够代表业务价值的最小场景集合。每个场景至少说明：

| 项目 | 必须回答的问题 |
| --- | --- |
| 触发与角色 | 谁在什么上下文中发起什么动作？ |
| 输入与前置 | 已存在什么资源、状态和授权？ |
| Agent 目标 | Agent 需要生成什么结构化业务候选结果？ |
| 可用能力 | 允许使用哪些已注册 Tool 或固定业务能力？ |
| 用户结果 | 用户看到什么成功、空、失败或等待结果？ |
| 副作用 | 是否创建消息、改变状态、追加事件或产生其它可审计变化？ |

演示场景不应只写“聊天成功”；必须能说明可验证的业务结果和结束条件。

### 3.3 场景能力拆解

对每个场景建立能力矩阵，区分以下边界：

| 能力类别 | 处理方式 |
| --- | --- |
| 确定性业务规则 | 由 Service、状态机或固定流程负责，不交给模型判断 |
| Agent 推理 | 只负责受约束的分类、规划或草稿生成，并输出结构化结果 |
| Tool | 只暴露场景需要的固定能力和 Pydantic 输入 Schema |
| 持久化与查询 | 通过 Repository，Service 负责归属、权限、事务和规则复核 |
| 异步与重试 | 记录任务状态、幂等键、失败分类和终态 |
| 用户可见结果 | 由 API/前端 Contract 明确字段、状态和错误映射 |

同时标记能力的资源拥有者、状态拥有者、读写者、下游消费者和是否产生副作用。发现多个能力没有明确拥有者时，停留在 `Slice Design`，不得靠实现补齐边界。

### 3.4 按场景补业务事实

先引用已有业务基线，再按场景检查事实是否足够。至少核对：角色和授权、会话与消息的业务主体、输入上下文、状态和合法迁移、消息可见范围、Agent 结束条件、幂等、失败语义以及副作用授权。

- 已确认的跨前后端事实引用编号，不在本范式中重复定义；
- 新增的跨 Slice 事实写入业务基线；
- 仅属于当前 Slice 的业务细节写入 `slice-spec.md`；
- 技术实现细节写入 `technical-design.md` 或对应后端事实源；
- 存在冲突或缺失的 `pending` 事实必须标记阻塞，不能由 Coding Agent 用模型行为或数据库字段自行裁决。

### 3.5 统一 Agent 执行骨架

在场景事实清楚后，抽取最小共享骨架。骨架只规定执行边界，场景能力仍由具体场景注册和实现：

```text
加载已授权上下文
  → 固定输入快照与脱敏
  → 结构化规划/生成
  → Pydantic Schema 校验
  → 业务规则与权限复核
  → 调用已注册 Tool 或 Service
  → 复核 Tool 结果与副作用授权
  → 持久化结果、状态和事件
  → 返回用户可观察结果
```

骨架必须明确：

- Agent、Workflow、Tool、Service、Repository 的责任边界；
- 模型输出不能直接成为事实、状态迁移或执行指令；
- Tool 输入校验、超时、重试、错误处理和资源归属复核；
- 同一请求、同一消息或同一任务的幂等策略；
- 运行状态、业务资源状态、任务状态和消息状态的状态拥有者；
- 日志、追踪、Prompt 和响应中的脱敏边界；
- 失败、重试耗尽、人工确认或等待状态的可观察结果。

若场景用普通 Service 或固定任务即可稳定完成，不应强行接入 Agent。

### 3.6 接口 / Tool / 状态契约

对应 `Slice Design`。统一骨架和具体场景同时锁定以下契约：

| 契约 | 最小内容 |
| --- | --- |
| API Contract | 调用方、输入、成功结果、错误语义、状态、幂等和副作用 |
| Tool Contract | 固定名称、输入 Schema、输出 Schema、授权范围、超时、重试和失败分类 |
| Agent 输出 Contract | 结构化字段、枚举、校验失败处理和不可直接执行的限制 |
| 状态 Contract | 状态拥有者、合法迁移、终态、重复提交和事件记录 |
| Handoff Contract | Producer、Consumer、触发条件、结果、归属、版本和重复交接规则 |
| 场景验收约定 | 场景入口、固定 Fixture、用户可观察结果和 Acceptance Artifact |

前端 Mock、HTTP 适配器、后端 API、Tool 实现和测试 Fixture 必须使用与其职责对应的已锁定 Contract；任何一方新增未定义字段或状态都算契约变化。

### 3.7 逐场景纵向实现

对应 `Implement`。按场景逐个完成从真实入口到用户可观察结果的完整链路，建议顺序为“最小主路径 → 失败/权限/幂等分支 → 后续变体”。每个场景的实现应同时覆盖：

- 前端入口、加载/空/失败/成功/禁用状态；
- API、Service、Repository、任务或 Agent Workflow 的完整调用链；
- 数据、消息、状态和事件的正确归属；
- Tool 调用、模型输出校验和副作用授权；
- 固定演示 Fixture、错误恢复和重复提交保护。

先实现共享骨架的最小可用版本，再在真实场景中抽取稳定共性；不得先构造无法独立验收的“通用框架”。后续场景不得破坏已通过场景，发现共享边界变化时按影响回退。

### 3.8 场景验收

对应 `Verify`，每完成一个场景立即验收，不等到所有场景完成后才发现边界错误。场景验收至少包括：

- 真实前端路径，或已声明的稳定内部入口；
- 成功、空结果、非法输入、资源不存在、无权访问、依赖失败和重复请求；
- 状态迁移、幂等、数据一致性、消息可见范围和副作用审计；
- 与前端 Mock、真实 API、Contract 和演示 Fixture 的一致性；
- 脱敏的 `report.md` 和 `actual.json` 等 Acceptance Artifact（适用时）。

开发者填写 Integration Scenario 的实际演示结果；Coding Agent 依据其中记录的问题逐项整改并回归，不代替开发者填写最终验收结论。

场景验收通过后，记录场景状态和证据，再进入下一个场景。场景失败的回退位置按六阶段规则决定：契约/业务/权限/状态变化回退 `Slice Design`，依赖或环境变化回退 `Readiness Check`，普通实现缺陷回退 `Implement`，验证记录缺失回退 `Verify`。

### 3.9 最终 Slice 验收

对应 `Close`。所有场景通过后，执行一次 Slice 级检查：

- 所有场景共同的主结果、范围、非目标和 Handoff 仍然一致；
- 统一 Agent 骨架未绕过 Service、Repository、状态机、授权或审计边界；
- 各场景 Contract、代码、前端展示、Fixture 和 Acceptance Artifact 一致；
- 跨场景状态、消息可见性、幂等、重试和失败终态没有互相矛盾；
- 共享数据、公共基础设施、跨 Slice 交接和完整用户流程由相应测试层补足；
- 全局业务、领域、数据、架构和集成文档已同步，延期项和已知限制已记录；
- Integration Scenario 均达到 `integration_delivered`，且没有未决阻断项。

最终 Slice 验收不是重复逐场景演示，而是证明场景集合能够作为一个边界清晰、可回归、可交付的 Slice 共存。

## 4. S10 执行时的最小文档集合

S10 开始前至少应具备：

1. S10 的 `slice-spec.md`：主结果、场景集合、范围、非目标、业务事实引用和验收标准；
2. S10 的 `technical-design.md`：统一执行骨架、API、Tool、状态、数据、授权、失败、幂等和验证方案；
3. 每个关键演示场景各自的 Integration Scenario；
4. 场景需要的 Integration Contract，或在明确版本下引用已有 Contract；
5. 涉及 Agent/Workflow 的架构边界和首次外部模型能力的真实 Readiness 证据；
6. 场景 Fixture、验收命令和 Acceptance Artifact 位置。

以上文档是 Slice 六阶段门禁的具体落点，不构成新的全局契约注册表。任何尚未进入事实源或已锁定契约的内容，不得以“演示需要”为理由直接写入代码。
