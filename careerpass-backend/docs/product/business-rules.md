# 业务规则

> 本文档只记录跨 Slice 持续有效的业务规则；实体字段、状态集合和单个接口行为分别由领域模型和 Slice 文档负责。

本文档中的规则是业务基线在后端的可执行承接；跨前后端业务语义以项目级 [`../../../docs/business/business-baseline.md`](../../../docs/business/business-baseline.md) 为准，新增或冲突规则必须先更新业务基线或登记待裁决事项。

## 1. 文件与资料

- 上传文件必须校验大小、类型和内容摘要后才能建立 ready 文件对象。
- 正式简历只接受 PDF 文件并进入解析链路；当前版本不处理扫描件、图片型 PDF、加密 PDF 或密码保护 PDF。CandidateDocument 当前只保存原始资料，不触发解析。
- 对象存储位置、临时路径和文件正文不得进入公开响应、日志或任务契约。
- S-11 对简历、CandidateDocument 和 Job 统一执行逻辑移除；资源从当前可用列表和后续业务检索中移除，物理文件按有效引用关系异步清理。当前版本不提供回收站或恢复入口。

### S-11 业务资料删除

- 简历只有在解析任务进入 `succeeded` 或 `failed` 终态且 Agent 尚未启动时允许逻辑移除；`processing`、Agent 运行中和 Agent 已结束时不得移除。
- `matching_ready` 表示解析成功且姓名、简历内手机号或邮箱、有效教育经历，以及工作经历或项目经历至少一项齐全；`matching_not_ready` 表示解析成功但缺少至少一项必需字段。二者都属于解析完成，且不改变简历删除资格。
- 一个 Candidate 可以拥有多份 Resume；Agent 尚未启动时，新上传的不同内容简历自动成为当前简历，解析未完成时仍不能启动 Agent；Agent 启动后当前简历绑定，不得替换或移除。S-11 的用户删除操作只针对当前简历。
- CandidateDocument 成功保存后可在 Agent 未启动、运行中或已结束时逻辑移除；移除后不得用于新的资料检索。
- 已创建的 MessageAttachment 不因来源 CandidateDocument 被逻辑移除而失效；附件自创建时间起 7 天内继续可下载。删除先于资料检索提交时不得创建新附件，附件创建先于删除提交时不影响有效期内下载。
- 已逻辑移除的 CandidateDocument 不参与重复上传幂等判断；相同内容再次上传时创建新的业务资料。
- 三类资源删除均保留最小审计记录，不记录删除原因、文件正文、联系方式、对象定位或原始异常；重复删除按幂等结果处理，不重复产生删除事件。

### 求职者附加资料

- S-05 接受求职者手动批量上传附加资料；PDF、Markdown、JPG 和 PNG 为当前支持格式，单文件不超过 10 MB。
- 批量上传按文件独立处理；单个文件失败不得回滚同批次已经成功保存的文件。
- 同一求职者重复上传同一附加资料时按内容幂等，返回既有资料的成功结果，不重复创建业务资料；请求级幂等字段由 S-05 Integration Contract 锁定。
- 附加资料上传状态由 S-05 负责：点击上传至完成数据存储前为 `ready`，数据存储成功后为 `success`；格式不支持或大小超限为 `failed`。
- 附加资料列表只返回前端展示所需的安全元数据，例如名称、文件格式、上传时间和上传状态；不得返回原文件或内部存储定位。
- S-05 负责上传和资料创建，S-11 负责删除；S-05 不实现删除。
- 附加资料不进入解析流程，也不由 S-05 主动暴露给 HR 或 S-10；后续 Agent 检索和授权交接由后续流程负责。

### 岗位 JD

- 受控演示中的岗位 JD 上传只接受 Markdown（`.md`）文件；其他格式不形成有效 Job。
- 一份新的 Markdown 文件创建一个新的 Job；一份文件对应一份岗位，不覆盖已有 Job，也不建立 JD 版本链。
- JD 使用固定标题提取业务字段；岗位名称、工作地点、薪资、岗位职责和任职要求是当前匹配所需的五项核心字段，额外固定标题不改变核心字段准入判断。
- S-08 只使用岗位名称、工作地点、薪资、岗位职责和任职要求五项核心字段；公司简介、优先条件、加分项及其他非核心内容不进入过滤、匹配评分或推荐理由。
- 当前构造 JD 数据保证五项核心字段有效；S-03 当前只定义临时技术失败、输入不可用和核心字段缺失三种失败语义。核心字段缺失时解析任务终止、标记 `matching_not_ready` 且不保留快照；结构校验失败不纳入当前受控演示分支。
- Job 归属于创建它的 HrProfile，并关联一个 StoredFileObject；资源读取、修改和删除必须校验当前 HR 归属。
- 同一 HrProfile 对相同文件内容的顺序重复上传按内容摘要去重，返回已有 Job 的幂等成功结果；不同 HR 相同内容的业务复用规则不属于当前 Demo。
- 岗位名称、公司、地点、薪资和摘要等展示字段不保存在 Job 中，由 S-03 结构化 JD 快照提供。
- 岗位匹配开始前允许删除 Job；匹配流程一旦发起，不得删除 Job。匹配发起事实由 S-08 的匹配运行记录确认，具体删除处理由 S-11 负责。
- 岗位 JD 只有在 S-03 任务进入 `succeeded` 或 `failed` 终态后才进入删除资格判断；`queued/running` 时不得删除。
- 删除成功后，岗位从当前可用岗位列表移除，并删除其可供当前业务读取的 S-03 解析快照；物理文件由对象清理流程按引用关系处理。
- 匹配已开始或解析尚未完成时，前端删除操作禁用并显示原因；服务端必须独立复核并拒绝不符合条件的请求。
- 删除不展示为用户可见的业务时间线事件，但保留最小审计信息，且不得记录 JD 正文、对象定位或原始异常。

## 2. 简历解析

- 解析只处理 Candidate 所有、关联对象为 ready 且状态允许的 Resume。
- 外部解析文本和 LLM 画像不是事实，必须经过结构化 Schema 和业务规则校验。
- 成功时 CandidateProfile、Resume 终态和 AsyncTaskRun 终态保持一致；解析成功与岗位匹配资格分开判断。
- 简历具备岗位匹配资格必须同时满足：姓名可解析、联系方式直接来自简历且至少有手机号或邮箱、教育经历有效，以及工作经历或项目经历至少一项有效；年龄可以缺失。
- 简历上传成功且解析成功但业务字段不完整时，画像标记为不可匹配；匹配资格只作为 S-07/S-08 的服务端条件，前端不展示字段缺失或画像详情。
- 简历上传页只展示上传和解析处理结果；`matching_ready/not_ready` 作为后端业务交接状态，不在本次页面展示。
- 姓名、手机号或邮箱、教育经历，以及工作经历或项目经历至少一项，是画像最小业务字段；其它画像字段均为可选字段，缺失不阻断解析成功。
- 工作年限按 `BF-RULE-019` 从已校验的非实习工作年月确定性派生，不采用模型估算；结果只使用 `unknown`、`x个月` 或 `x年`。
- 当前文本型 PDF 先使用原生嵌入文本形成事实主源；外部版面解析器只作为本地无文本时的技术回退，不能覆盖已验证的原生事实。
- 一个 Candidate 可以拥有多份 Resume；一次上传只接收一份 PDF；同一 Candidate 重复上传相同内容时复用已有 Resume 和解析结果，不创建新版本或新解析任务。
- 不可匹配的画像不得启动 Agent；前端提示不能替代后端对启动和匹配入口的校验。
- 临时故障可以有限重试；不可重试错误或重试耗尽进入受控失败终态。

## 3. 求职目标

- 当前版本每个 Candidate 只维护一个当前求职目标；Agent 未启动时可更新同一个目标，Agent 运行中或已结束后不可修改。
- 求职目标保存不绑定 Resume；S-07 启动 Agent 时绑定当时有效的当前 Resume，运行中不得替换本轮绑定的 Resume。
- Offer 数量必须为 1 至 10 的正整数；岗位名称必填；筛选条件可为空并按自由文本保存。
- 求职目标保存是目标的创建或更新，不是 Agent 启动提交；重复保存不得创建第二个当前目标。
- 求职目标状态由 `active`、`achieved` 和 `abandoned` 表达；S-06 创建或更新为 `active`，Offer 达标后由后续流程转为 `achieved`，当前版本不提供用户主动放弃入口。
- S-07 只负责启动条件校验、当前 Resume 绑定和运行上下文进入 `running`；同一运行上下文的重复启动按幂等成功处理，不创建新运行。

## 4. 岗位匹配

- 当前版本使用本地简化算法，不依赖外部匹配服务、向量召回或重排序服务。
- S-08 在匹配前检查可用结构化 JD；该检查不属于 S-07 的启动条件。
- 当前演示候选人的岗位候选集为关联 HR 已上传且可用的全部结构化 JD；演示只覆盖一个 HR 与一个 Candidate，不单独实现跨 HR 授权筛选。
- 只有具备匹配资格的候选人画像、已创建的当前求职目标和可供演示使用的岗位才能进入匹配。
- 当前演示岗位来自构造数据，主路径保证 JD 五项核心字段有效；核心字段缺失按不可匹配规则阻断 S-08 且不生成快照，结构校验失败不纳入当前演示分支。
- 当前演示岗位池最多包含 20 个可用结构化岗位 JD；本地匹配算法在该受控规模内同步执行。
- S-07 启动事务提交后，后端同步调用 S-08 完成岗位筛选、匹配结果持久化和通过岗位的系统内投递；前端不再次提交匹配命令，也不展示匹配过程。
- 匹配结果独立持久化，作为投递筛选和投递记录创建的依据；求职进度页只展示已创建的投递记录，不展示未通过投递筛选的结果。
- 当前版本对本轮可用岗位逐个执行筛选；通过筛选的岗位创建系统内投递记录，不采用只投递 Top-N 岗位的策略。
- `offer_target` 只表示目标 Offer 数量，与岗位筛选数量和投递数量完全解耦。
- 匹配输入只使用已解析并校验的岗位 JD 业务语义摘要和候选人简历业务语义摘要；具体字段权重、阈值、排序和推荐理由规则由 S-08 Contract 裁定。
- 同一 Agent 运行上下文中，同一岗位 JD 只筛选一次；重复触发或任务重试不得重复生成有效结果或投递记录。
- 本轮全部可用岗位均已筛选完成且 Application 数量为 0 时，Agent 以“当前没有可供匹配的岗位”结束；不要求 Offer 数量达到目标。
- Application 展示推荐匹配得分和推荐理由；未形成 Application 的 Match 不在求职进度页展示。

## 5. 投递进度更新

- S-09 查询当前 HR 所有未删除岗位下的当前首轮 Application；当前单 Candidate 受控演示以全局最新 AgentRunContext 作为当前首轮，不纳入历史 Candidate 的旧运行；当前演示不处理多 Candidate、多轮投递、历史轮次、跨 HR 查询或独立岗位授权配置。
- HR 投递进度视图只展示岗位名称、公司名称、候选人姓名和当前投递进度；联系方式、简历原文、匹配信息、沟通全文和其它候选人资料不得进入该视图。
- HR 只能更新当前 HR 有权访问的单条 Application；服务端必须同时校验 HR、Job、Candidate、Application 和 AgentRun 关系，不得仅凭 Application ID 授权。
- Application 状态只能向后推进或进入 `terminated`；`offer` 和 `terminated` 为终态；同状态重复提交幂等成功且不新增事件；非法回退和终态修改失败且保持原状态。
- 有效状态变化在同一事务中更新 Application、追加 `application_status_updated` ProgressEvent，并记录准确的前状态、后状态、`actor=hr` 和服务端时间。
- Application 进入 `offer` 后，系统统计当前首轮 AgentRun 的 Offer 数量；达到 `offer_target` 时，AgentRun 转为 `finished`、结束原因为 `offer_target_reached`，JobGoal 转为 `achieved`。
- AgentRun 结束后不能重新启动，但其它未终态 Application 仍可继续按状态机推进；已进入终态的 Application 不可修改。

## 6. 异步可靠性

- 同一简历和任务版本只能存在一个有效幂等任务。
- PostgreSQL 中的 AsyncTaskRun 是权威状态，Redis/Celery 结果不是业务事实源。
- Dispatcher、Worker 和迟到回调必须使用租约或令牌避免重复执行和旧结果覆盖。
- 岗位 JD 上传成功后，在同一事务内为每个新 Job 创建或复用 queued 的 JD 解析任务；生产者不直接调用下游 Service、Dispatcher 或 Worker。
- S-03 的临时技术失败自动重试，重试耗尽进入 `failed` 并记录 `retry_exhausted`；输入不可用和核心字段缺失立即进入 `failed`，核心字段缺失不创建快照。

## 7. 安全

- 密码、令牌、联系方式、简历原文、内部路径、模型原始响应和异常堆栈不得进入非必要响应、日志或追踪。
- 不可逆外部副作用必须有明确授权和审计；当前代码未实现真实外部投递或消息发送。
