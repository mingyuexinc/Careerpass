# Slice：岗位 JD 上传

> 当前阶段：Close
>
> 当前状态：S-02 已完成业务事实变更后的自动化验证和 `.md` 真实 Integration Scenario，达到最小联调交付条件。

## 1. 目标

交付场景：[`IS-S02-01`](../../../../../docs/integration/slices/slice-02-jd-upload/integration-scenario.md)。

HR 批量提供岗位 JD，系统按文件建立归属于当前 HR 的独立 `Job`，保存 JD 文件，并在上传事务内完成 S-03 解析任务交接。

S-02 的成功结果是“Job 和解析任务交接已建立”，不表示 JD 已完成结构化解析。真实解析和结构化 JD 快照由 S-03 负责，S-08 只消费 S-03 的成功快照。

## 2. 输入

| 输入 | 约束 |
| --- | --- |
| 当前 HR 身份 | 已登录，服务端确认 `active_role=hr`，并能解析 `HrProfile` |
| JD 文件集合 | 至少一份 `.md` 文件；支持批量上传；每个文件独立处理 |
| 文件内容 | 经过文件类型、大小、可读性和内容摘要校验；具体技术限制由技术设计锁定 |

## 3. 输出

| 文件结果 | 业务含义 |
| --- | --- |
| `created` | 创建新的 Job，并完成 queued S-03 任务交接 |
| `duplicate` | 当前 HR 已存在相同内容且未删除的 Job；返回已有 Job，不创建新 Job 或新任务 |
| `failed` | 文件未形成可供下游消费的有效 Job；当前 Demo 不验收失败展示和恢复流程 |

批量请求逐文件返回结果，允许部分成功。响应不得包含文件正文、内部存储位置或原始异常。

## 4. 前置条件

- S-01 已提供有效 `CurrentIdentity`；
- 当前 HR 的 `HrProfile` 已建立；
- 数据库和受控对象存储可用；
- 上传请求至少包含一份 JD 文件。

## 5. 业务规则

本 Slice 使用 `BF-ROLE-002`、`BF-OBJECT-003`、`BF-FLOW-001`、`BF-FLOW-005`、`BF-RULE-002`、`BF-RULE-009` 和 `BF-RULE-010`。

### 5.1 解析边界

| Slice | 业务结果 |
| --- | --- |
| S-02 | 上传文件、创建 Job、建立 queued 解析任务交接 |
| S-03 | 真实解析 JD，经过结构化和业务校验后生成 JD 快照 |
| S-08 | 消费成功 JD 快照，执行匹配与投递 |

S-02 不调用解析器、LLM、S-03 Service、Dispatcher 或 Worker。

### 5.2 Job 与重复上传

| 场景 | 规则 |
| --- | --- |
| 内容不同 | 创建新的独立 Job；不覆盖旧 Job，不建立 JD 版本链 |
| 同一 HR + 相同内容 + Job 未删除 | 返回已有 Job 的幂等成功结果 |
| 同一 HR + 相同内容 + Job 正在解析 | 返回已有 Job；不重复创建 Job 或解析任务 |
| 同一 HR + 相同内容 + Job 已解析成功 | 返回已有 Job；不重复创建 Job 或解析任务 |
| Job 已删除后再次上传 | 已删除 Job 不参与去重；按全新 Job 处理 |
| Job 解析失败后再次上传 | 解析失败和重试语义由 S-03 裁决；S-02 不定义新的失败处理规则 |
| 不同 HR 上传相同内容 | 当前 Demo 不处理跨 HR 业务复用 |
| 并发重复上传 | 当前 Demo 不纳入验收 |

S-02 不定义“当前岗位”或“最新岗位”语义；多个未删除 Job 是彼此独立的岗位资源。

### 5.3 删除

- 匹配流程发起前允许删除 Job；
- 匹配流程一旦发起，不得删除 Job，即使没有生成匹配结果或匹配失败；
- 删除动作、删除状态和对象清理由 S-11 实现；匹配发起事实由 S-08 提供；
- 已删除 Job 不参与后续重复上传判断。

## 6. 范围 / 非目标

### 当前范围

- 支持单次批量上传；
- 逐文件建立 Job 或返回重复结果；
- 为新 Job 建立 S-03 queued 解析任务交接；
- 保证 Job 归属于当前 HR；
- 保证上传结果与后续解析成功结果可区分。

### 非目标

- 不在 S-02 中真实解析 JD 或生成岗位摘要；
- 不执行岗位匹配、投递、沟通或真实外部招聘平台同步；
- 不建立 JD 版本链，不覆盖已有 Job；
- 不定义“当前岗位/最新岗位”或岗位历史版本关系；
- 不处理解析失败 Job 的再次上传和重试语义；
- 不验收跨 HR 相同内容复用和并发重复上传竞态；
- 不在 S-02 中实现岗位删除。

## 7. 技术约束

- 所有资源访问沿 `CurrentIdentity → HrProfile → Job → StoredFileObject` 校验归属；
- 数据访问必须经过 Repository；Service 不直接访问 ORM Session 或编写 SQL；
- 新 Job、文件关联和 queued S-03 任务交接在同一 PostgreSQL 事务内提交；
- 每个文件独立处理，单个文件失败不得回滚其他已成功文件；
- S-02 不直接调用 S-03 Service、Dispatcher 或 Worker；事务提交后由既有异步机制投递；
- Job 不保存岗位名称、公司、地点、薪资、摘要或 JD 解析状态；
- 文件正文、对象存储定位、凭证和原始异常不得进入响应、日志、追踪或任务契约。

## 8. 验收标准

- HR 可以批量提交 `.md` 岗位 JD；
- 每个文件分别返回 `created`、`duplicate` 或 `failed` 结果；
- 内容不同的文件分别创建独立 Job；
- 同一 HR 顺序重复上传相同内容时返回已有 Job；
- 正在解析的 Job 重复上传不创建第二个 Job 或解析任务；
- 已删除 Job 再次上传按新 Job 处理；
- 新 Job、文件关联和 queued S-03 任务交接原子提交；
- 单个文件失败不影响同批次其他文件的结果；
- 上传成功不被误显示为 JD 已解析成功；
- 不产生真实外部招聘副作用，不暴露敏感内部信息。

| 事项 | 决定 |

| 解析失败后重传 | 交由 S-03 裁决，S-02 不处理 |
