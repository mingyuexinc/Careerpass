# 后端现状差距分析

> 文档层级：版本能力差距分析（Gap Analysis）。
>
> 分析对象：正式前端当前版本主流程、后端能力映射、当前后端代码/测试/迁移证据，以及当前后端产品、领域、契约和架构文档。
>
> 历史开发包和旧契约不属于当前事实源；只有当前代码、测试、迁移或已锁定并实际接入的契约才能作为实现证据。

## 1. 分析目的与证据口径

### 1.1 分析目的

本文件回答以下问题：

- 当前版本要求的 G1–G9 业务模块，哪些已经有可复用实现；
- 已有实现与正式前端闭环之间还缺哪些业务、契约、集成和验收能力；
- 哪些差距是当前版本阻塞项，哪些属于条件能力或延期能力；
- 后续应按什么依赖顺序进入 Slice Select、Slice Design 和 Readiness Check。

本文不直接拆分代码任务，不直接设计数据库迁移，也不替代单个 Slice 的方案和验收文档。

### 1.2 分析时间点

本分析以当前工作区代码、测试和文档为准。后续实现、迁移、契约锁定或真实依赖验证发生变化时，应更新对应差距项的证据和状态，不得只修改“完成”标记。

### 1.3 证据优先级

| 优先级 | 证据 | 可证明内容 |
| --- | --- | --- |
| 1 | 当前正式代码与已执行迁移 | 当前工程实际存在的实现和持久化边界 |
| 2 | 当前测试结果 | 测试覆盖范围内的行为和边界 |
| 3 | 已锁定 API/异步契约且有参与方 | 约定的接口边界，不等于实现完成 |
| 4 | 当前后端产品、领域、契约和架构文档 | 已确认的范围、业务规则、接口目标和技术边界 |
| 5 | 前端页面、Mock、历史开发包和占位文档 | 需求线索，不证明后端能力 |

以下内容不单独构成实现证据：

- `careerpass-backend/docs/` 中仍未实现的占位文档；
- 历史开发包和旧契约；
- 前端已经完成的 Mock 流程；
- 仅有适配器单元测试、没有真实 MinerU/Qwen 或 Redis/Worker/Dispatcher 连通性验证。

## 2. 范围和判断规则

### 2.1 当前版本范围

`docs/product/backend-delivery-scope.md` 将当前版本裁决为：

```text
简历 → 画像 → 岗位匹配 → 系统内投递记录 → 进度与沟通
```

当前版本的业务模块顺序是：

```text
G1 认证与用户初始化
  → G2 候选人资料准备
  → G3 简历解析与候选人画像
  → G4 岗位 JD 解析与入库闭环
  → G5 求职目标
  → G6 岗位匹配
  → G7 投递与进度
  → G8 AI 求职沟通
  → G9 业务资料删除（按资源依赖进入）
  → F1 前端闭环验收
```

这个顺序是后续模块真实依赖实现和验收的门禁顺序，不是允许按代码目录横向开发的排期。

### 2.2 差距分类

| 分类 | 含义 | 处理方式 |
| --- | --- | --- |
| `implemented` | 当前代码、迁移和测试已覆盖，且没有当前版本关键缺口 | 进入前置能力复用清单，仍需前端接入验收 |
| `partial` | 有部分实现，但缺少完整业务边界、真实依赖、契约或前端闭环 | 保留现有能力，补齐差距后才能作为后续模块依赖 |
| `blocked` | 当前版本需要，但前置门禁或关键证据尚未满足 | 不得进入下游 Slice 的真实依赖验收 |
| `missing` | 当前版本需要，尚未发现可用实现 | 进入后续 Slice 设计和实现 |
| `conditional` | 只有在具体 Slice 的关键路径实际使用时才启用 | 随该 Slice 交付最小验证，不提前平台化 |
| `deferred` | 明确不属于当前 MVP | 不得作为当前版本任务依赖或验收阻塞 |
| `conflict` | 前端流程、当前后端文档或代码之间存在未裁决差异 | 回退到范围、Contract 或 Slice 方案裁决 |

### 2.3 成功标准

一个差距只有在以下条件同时满足时，才能从 `partial` 或 `blocked` 变为可复用：

- 业务结果和资源归属已确认；
- API 或命令边界已锁定；
- 数据、状态和事务责任已由对应事实源确认；
- Repository、权限校验和安全响应已实现；
- 适用的异步、幂等、重试和失败分类已验证；
- 至少有单元/接口/集成测试，并完成真实前端或受控运行拓扑验收；
- 不产生 MVP 明确禁止的真实外部投递或消息副作用。

### 3.2 已有能力与可复用边界

当前后端不是从零开始，以下能力可以作为后续 Slice 的技术基础，但不能直接等同于完整业务模块：

| 已有能力 | 可复用范围 | 不能据此推导 |
| --- | --- | --- |
| 认证、短期 Access Token、CurrentIdentity | 候选人身份解析和受保护请求的基础 | HR 角色、HR 岗位归属和 HR 查询权限已经完成 |
| Candidate Preparation | 当前候选人简历/附加资料上传、列表和归属校验 | 画像、求职目标、匹配准入或沟通附件发送已经完成 |
| Local Object Storage | 本地 Demo 的受控对象保存、摘要去重和清理基础 | 云存储、通用文件中心、用户删除和原始文件下载 |
| Resume Parse Worker/Finalization | 简历解析业务链路的部分实现 | 真实 MinerU/Qwen 已通过、所有异步故障路径已验证 |
| AsyncTaskRun、Dispatcher、Worker、租约 | 简历解析及未来必要异步任务的公共机制候选 | 任何业务任务可直接复用而无需重新确认输入、幂等和终态 |
| Pydantic Schema、统一响应、架构边界测试 | 后续模块的工程基线 | 业务状态机、资源权限和领域规则已经实现 |

## 4. 详细差距分析

### 4.1 G1：认证与用户初始化

#### 当前证据

- 当前代码有注册、登录、`/auth/me`、短期 Access Token 和 Candidate 初始化路径；
- `CurrentIdentity` 通过有效 Token 和 Repository 复核得到 `user_id`、`candidate_id`；
- 当前测试覆盖认证 Schema、注册、登录、身份解析和 Repository 边界；
- 当前迁移覆盖 User、Candidate 及其唯一归属关系；
- 当前认证方案只锁定短期 Access Token、当前身份解析和受保护请求；Refresh Token、服务端会话、Token 轮换、设备管理和第三方登录未进入当前交付范围。

#### 差距

| 差距 | 严重性 | 说明 | 关闭证据 |
| --- | --- | --- | --- |
| HR 身份模型未确定 | `high` | 前端有求职者/HR 两种角色，当前后端 CurrentIdentity 主要表达 Candidate；需要裁决 HR 是 User 角色、独立资源还是受控测试身份。 | 角色 Contract、资源归属规则和接口测试 |
| G1 与后续模块的身份输出未锁定 | `high` | 下游 G4–G8 需要岗位、投递、会话和候选人视图的授权锚点。 | 统一身份契约和至少一条跨角色接口测试 |
| 前端登录闭环未真实接入 | `medium` | 当前前端仍使用 Mock，后端认证通过不能替代真实前端验收。 | 真实前端登录、角色菜单隔离和错误状态验收 |

#### 当前裁决

Refresh Token 等设计记录保持 `deferred`，不阻塞 G1。HR 角色边界是后续业务模块开始前必须解决的 `blocked` 项，不能通过前端 Mock 身份绕过。

### 4.2 G2：候选人资料准备与对象存储

#### 当前证据

- 当前有简历上传/列表和候选人附加资料上传/列表接口；
- Service 不直接访问 ORM Session，资料数据访问经过 Repository；
- 已实现文件类型、大小、内容摘要、对象引用和候选人归属校验；
- 当前数据库有 `stored_file_objects`、`resumes`、`candidate_documents`；
- 当前对象存储为本地受控适配器，未暴露静态目录、绝对路径或下载地址；
- 当前后端能力映射将附加资料定义为可在候选人明确选择和授权后引用的资料，不自动进入解析、画像和匹配。

#### 差距

| 差距 | 严重性 | 说明 | 关闭证据 |
| --- | --- | --- | --- |
| 上传后真实异步交接未完成端到端证明 | `high` | 简历上传会创建解析交接，但 Dispatcher/Broker/Worker 的真实连通性和重复投递路径尚未完成验证。 | Compose/真实拓扑集成测试和故障路径记录 |
| 对象清理真实调度边界未完成 | `medium` | 当前有清理实现和测试，但清理触发器与解析 Dispatcher 的运行边界仍需按对象存储方案确认。 | 真实清理任务验证和脱敏运行记录 |
| 前端批量资料行为与后端当前接口需对齐 | `medium` | 前端产品文档允许多份或分批资料，部分验收规则又按单份资料描述；后端能力映射不能替代该产品裁决。 | 统一前端验收规则和 API Contract |

#### 当前裁决

G2 的核心上传、列表和受控存储能力可复用；业务资料删除进入 G9/S-11，原始下载、用户配额和通用文件中心仍不属于当前版本目标。

### 4.3 G3：简历解析与候选人画像

#### 当前证据

- 当前有解析任务创建、Worker、执行租约、Finalization 和画像查询代码；
- 当前有 MinerU MCP 适配器、stdio 客户端和 Qwen 画像适配器；
- 当前测试覆盖解析契约、Worker、Finalization、适配器和失败映射；
- 当前数据库有 `candidate_profiles` 和 `async_task_runs`，画像和简历终态设计为原子写入；
- 当前解析文档要求画像经过 Pydantic 和业务规则校验后才能形成成功终态；
- 异步任务基线已确定为 PostgreSQL 权威状态、Redis Broker、独立 Dispatcher、Worker、至少一次投递、有限重试和执行租约。

#### 差距

| 差距 | 严重性 | 说明 | 关闭证据 |
| --- | --- | --- | --- |
| 真实 MinerU/Qwen 能力未通过 | `closed` | S-04 固定 PDF 已完成真实解析调用、Schema/业务校验和开发者结果审阅。 | 成功 Capability Acceptance Artifact 和真实解析链路测试 |
| Redis/Dispatcher/Worker 真实拓扑未通过 | `closed for S-04` | S-04 真实解析任务、终态交接和画像持久化验证已通过；更广泛故障注入仍按基础设施专项维护。 | S-04 Slice Integration/Infrastructure 证据 |
| 解析链路与前端状态尚未闭环 | `closed for S-04` | S-04 已按 Contract 完成上传、解析状态交接和开发交付验收；后续页面能力不扩大本 Slice 范围。 | `IS-S04-01` 和 S-04 Contract |
| 解析输入和敏感信息边界需运行验证 | `closed for S-04` | Acceptance Artifact 只保留结构化字段，联系方式脱敏，不写入完整简历原文、内部路径或模型原始响应。 | 成功 Artifact、代码和测试检查 |

#### 当前裁决

G3/S-04 的当前开发交付已完成并标记为 `implemented`；S-04 的 `IS-S04-01` 已标记为 `integration_delivered`。该结论不提前实现 S-06 求职目标、S-07 Agent 启动或 S-11 资料删除。

### 4.4 G4：岗位 JD 解析与入库闭环

#### 设计目标

当前后端交付范围和能力映射将 G4 定义为由 HR 或受控流程提供岗位 JD，形成后续流程可使用的岗位输入。S-02/S-03 已锁定岗位归属、固定 Markdown 解析、结构化快照和失败边界；代码、迁移、任务运行和真实验证证据均已完成。

#### 差距与冲突

| 差距/冲突 | 严重性 | 说明 | 关闭证据 |
| --- | --- | --- | --- |
| 岗位/JD 代码链尚缺完整运行证据 | `closed` | S-02 Job、S-03 结构化快照、内部验证 API、Parser、任务执行和单元/API 测试已存在；真实 Compose 拓扑和 `IS-S03-01` 已通过。 | G4 Slice 的 Compose 运行记录和 `IS-S03-01` |
| 岗位来源与管理 Contract 尚未锁定 | `closed by design` | S-02 已锁定 HR 归属、受控 Markdown 上传、Job 去重和删除边界；S-03 已锁定内部验证 API 与 S-02 异步交接。 | S-02/S-03 Contract；真实接口和场景已通过 |
| 岗位 JD 解析路线未确定 | `closed by design` | S-03 已锁定确定性 Markdown 标题解析，不使用 MinerU/Qwen 或大模型语义解析。 | S-03 Technical Design、Parser 测试和真实场景 |
| 岗位/JD 成功快照和失败输入隔离未实现 | `closed` | 失败输入不得形成可用岗位事实；成功后只读查询只能返回 `succeeded` 快照。 | 数据模型、事务测试、真实成功快照和失败任务收敛证据 |

#### 当前裁决

G4 的业务和技术设计已由 S-02/S-03 文档锁定；代码、迁移、本地测试、Capability Acceptance、真实异步运行和成功场景证据均已完成，G4 标记为 `implemented`。S03 的 `IS-S03-01` 已完成开发者最小演示验收并标记为 `integration_delivered`。

### 4.5 G5：求职目标

#### 设计目标

当前后端文档将 G5 定义为当前候选人的活跃求职目标、基础过滤条件和合法状态迁移，并向下游提供目标快照。目标创建不绑定简历，Agent 启动时由 S-07 绑定当时有效的当前简历。多目标优先级、目标协作和复杂策略推荐不属于当前版本。

#### 当前差距

| 差距 | 严重性 | 说明 | 关闭证据 |
| --- | --- | --- | --- |
| 当前代码未发现 Job Goal API/Service/Repository | `closed` | S-06 已实现候选人归属的 GET/PUT API、Service 和 Repository。 | S-06 代码、API 测试和真实接口验证 |

### 4.9 G9：业务资料删除

#### 设计目标

G9/S-11 统一处理简历、求职资料和岗位 JD 的删除请求。三类资源共享“从当前可用资料中移除”的业务结果，但删除条件由资源类型、角色归属、当前使用状态和下游引用关系分别决定。

#### 当前证据

- 当前数据库已有 `resumes`、`candidate_documents` 和受控文件对象；
- 当前前端流程和后端交付范围均要求支持三类资料删除；
- 当前代码已有对象存储清理和上传失败清理，但未发现面向业务用户的资料删除 API、Service 或完整 Repository 用例；
- 当前已有 Job、S-03 解析任务和解析快照，但没有岗位 JD 删除 API、Service 或完整 Repository 用例。

#### 当前差距

| 差距 | 严重性 | 说明 | 关闭证据 |
| --- | --- | --- | --- |

#### 当前裁决

G9/S-11 已完成 Implement、Verify 和 Close，状态为 `integration_delivered`。它覆盖简历、求职资料和岗位 JD 三类资源，资源类型只决定删除条件分支，不拆成三个 Slice；正式简历删除也纳入本 Slice，且已按当前绑定、解析结果和下游引用规则验收。

岗位 JD 分支已提前完成业务事实裁决，但不提前进入实现：

- S-11 负责岗位 JD 删除，已在现有资源路由增加删除 API，不修改 S-02/S-03 的既有解析职责；
- 只有 S-03 解析任务进入 `succeeded` 或 `failed` 终态，且 S-08 尚未形成匹配发起事实时，岗位 JD 才可进入删除；`queued/running` 或已开始匹配时不得删除；
- 删除成功后从当前可用岗位列表移除；无其他可用岗位时展示空状态；当前业务读取不保留 S-03 解析快照，物理文件由对象清理边界另行处理；
- 匹配发起事实由 S-08 提供，受控演示可以使用后端拥有的模拟状态语义，客户端不得提交该事实；
- 删除不展示为用户可见的业务时间线事件，但必须保留不含 JD 正文、对象定位和原始异常的最小审计信息。

简历和求职资料的业务裁决已完成，并已由 S-11 Contract、领域实现、对象清理边界和引用场景验收：简历仅在解析任务进入 `succeeded/failed` 终态且 Agent 尚未启动时允许逻辑移除；`matching_ready/not_ready` 不改变删除资格；新上传的不同内容简历在 Agent 尚未启动时自动成为当前简历，解析未完成时仍不能启动 Agent。CandidateDocument 成功保存后可在 Agent 各生命周期阶段逻辑移除，移除后不得用于新的资料检索，已创建附件保留 7 天；已移除资料不参与重复上传幂等判断，重新上传创建新的业务资料。S11 三份 Scenario 已完成开发者真实验收，剩余工作仅为常规回归维护。

## 5. 技术使能与跨模块差距

### 5.1 异步任务

当前已有异步基础，但差距不在“是否有 Celery 类代码”，而在真实运行与业务模块接入：

| 方面 | 当前证据 | 差距 |
| --- | --- | --- |
| 任务权威状态 | `async_task_runs` 设计和 Repository 存在 | 需要证明后续任务类型不会绕过 PostgreSQL 权威状态 |
| 可靠入队 | Dispatcher/Worker 代码存在 | 需要真实验证投递—回填中断、重复投递和 Worker 丢失 |
| 幂等 | 简历解析固定 `v1` 幂等键设计存在 | G6/G8 等新任务必须逐项定义自己的资源锚点和幂等键 |
| 重试和超时 | 设计已规定软/硬超时、最多 2 次重试和失败分类 | 真实 Broker/Worker 运行证据尚未闭合 |
| 执行租约 | 代码和设计已有租约/令牌边界 | 需要验证迟到 Worker 不会写入业务结果或改变终态 |
| 可观测性 | 有脱敏日志和任务关联设计 | 需要检查真实日志、Prompt、追踪和异常不泄露敏感原值 |

### 5.2 智能体工作流（Agent Workflow）

当前后端 Agent 架构将 Agent 控制面作为条件能力，但当前业务工作流尚未形成实现证据。必须区分：

- `planned / validated / waiting_for_user / rejected / scheduled / completed / failed` 是编排状态；
- `queued / running / succeeded / failed` 是异步任务状态；
- 两者不能互相替代，也不能用 Celery 状态直接表达用户业务状态；
- Agent 只能生成经过 Pydantic 校验的结构化计划，不能直接写业务数据、拼接 SQL/Shell 或发起未经校验的外部请求；
- 涉及投递、进度、会话或其他副作用时，计划成功不等于获得副作用授权。

S10 整体已形成三条受限、可审计的沟通能力路径：S10-01 简历事实问答、S10-02 文件名匹配与附件交付、S10-03 主动岗位信息补齐与求职目标判断。项目仍没有可复用的通用 Agent Workflow 平台；该平台及其它 Agent 场景属于后续 Slice，不影响 S10 当前交付。

### 5.3 对象存储和敏感数据

对象存储的本地适配器可以复用，但以下边界必须在后续 Slice 中保持：

- 业务模块只通过对象存储抽象和 Repository 读取文件；
- 不向客户端返回绝对路径、`file://`、静态 URL、预签名 URL 或文件正文；
- 简历、联系方式、Token、模型原始响应和内部异常不得进入日志、追踪或非必要响应；
- 附加资料正文不自动进入 Agent/LLM 输入；
- 解析 Worker 只能接收经 Repository 校验的资源 ID，不能接收模型或客户端提供的路径。

```text

  → G3 解析/画像与真实异步验证
  → G4 岗位来源冲突裁决及 JD 快照

  → F1 真实前端闭环
```

某一模块的前置领域接口、契约或真实技术能力未通过时，只将依赖该能力的资源类型分支标记为 `blocked`，不把已经有证据的公共技术能力全部否定，也不得用 Mock、手工数据库写入或跨层访问替代门禁。

## 8. 当前结论

当前后端已经形成 G1–G3 的部分技术和业务基础，但尚未形成可直接支撑正式前端的完整闭环。最重要的事实不是“已有多少文件”，而是：

1. G1–G3 需要补齐真实运行、外部能力和前端接入证据；
2. G4 需要锁定岗位来源、归属和提供方式 Contract，不能依据历史开发包裁决；
3. G6–G8 的当前交付状态以总览表和各 Slice 证据为准，其中 G8/S10 已完成当前范围交付；G9 仍是目标和接口意图，尚未标记为已实现；G5/S-06 已完成当前目标保存交付；
4. 真实闭环应按已确认的资源依赖推进，不得提前创建完整未来数据模型；
5. S10 当前系统内沟通目标已完成交付；真实外部投递、真实外部 HR 消息、生产级 Agent 运营和多租户平台能力保持延期。

因此，后续工作转向 G1–G3 的真实验证缺口和 G9 的删除 Contract，再按依赖转化为可审计的 Slice 入口；G4 已作为下游能力复用基础。
