# 影响分析

## 受影响模块与边界

| 模块 | 影响 | 所有权/权限影响 | 备注 |
| --- | --- | --- | --- |
| FastAPI 应用入口 | 新增应用工厂、生命周期和路由挂载 | 无业务资源访问 | 禁止在入口初始化时泄露配置。 |
| `core` | 新增配置、异常、日志、请求上下文 | 无用户身份判断 | 为后续认证与资源归属校验提供请求 ID 与错误边界。 |
| API / schemas | 定义响应信封和健康检查 | 健康端点不接受用户资源 ID | 不把依赖异常原样返回。 |
| database | 新增引擎、Session factory、Base、Alembic | 后续只能经 Repository 使用 Session | 空基线不得抢占领域迁移所有权。 |
| cache / tasks | Redis 和 Celery 的配置与连通性 | 无业务键、无业务任务 | 任务探针不发送外部消息、不入业务库。 |
| 测试 | 新增测试分层与依赖替身 | 测试数据不得携带真实个人信息 | 集成测试使用独立数据库/命名空间。 |

## 契约与数据影响

- API：建立全局 `{code, msg, data}` 信封；`X-Request-ID` 可由调用方提供，否则由服务端生成。健康检查不属于业务资源 API，但必须遵守统一响应契约。
- 数据库与 Alembic：添加迁移运行时和空基线 revision，无业务 DDL。后续任何表、枚举、函数或触发器都必须由独立变更包的 SQL 审阅产物及 Alembic revision 同步定义。
- Redis/Celery：仅增加配置键、连接封装和探针任务。任务须设置序列化白名单、超时、重试策略和状态可查询能力；不配置自动执行任何业务任务。
- LLM、Prompt、追踪脱敏：本阶段不接入。日志脱敏机制必须先覆盖后续可能进入追踪的敏感字段。

## 风险与缓解

| 风险 | 等级 | 缓解措施 |
| --- | --- | --- |
| 过早抽象导致 Phase 0 膨胀 | 高 | 明确非目标；每项任务以支持首个简历处理闭环为验收依据。 |
| 配置缺失直到运行时才暴露 | 高 | Pydantic Settings 在启动时验证必填项；测试覆盖缺失与非法值。 |
| 基础层泄露密钥或个人信息 | 高 | 字段级脱敏、异常白名单和日志测试；禁止记录请求体及敏感 Header。 |
| 连接池或任务客户端生命周期泄漏 | 中 | 在 FastAPI lifespan 中创建/关闭；集成测试验证关闭行为。 |
| 后续绕过 Repository 访问 Session | 高 | Session 不作为 API/Service 依赖暴露；代码评审和架构测试检查 import 边界。 |
| 健康检查被误用于暴露内部信息 | 中 | liveness 不探测依赖；readiness 只返回聚合状态和请求 ID。 |
