# 异步任务运行业务模型

## 变更概述

在业务模型和数据模型中新增 MVP 精简的 `Async Task Run` 实体/`async_task_runs` 表，区分异步执行过程与简历、岗位 JD 等资源的最终处理状态；持久化任务归属、Celery 任务标识、幂等、版本与脱敏失败分类，并作为无独立 Outbox 表时的可靠入队记录。重试次数、退避、下次执行时间和超时策略交由 Celery 管理。同步裁决候选人画像为简历解析成功后的确定性派生结果：目标职位为解析必填事实，画像不再作为独立异步任务或检索索引载体。

## 影响模块

- 候选人资料准备与文档解析
- 岗位 JD 解析与岗位匹配
- Celery 异步任务、任务审计和后续工作流运行记录

## 数据库变更

新增数据模型契约：`async_task_runs` 表、四类相关枚举和索引约束。当前仅提供评审用迁移与回滚脚本；首次实现异步业务闭环时必须在工程中新增对应 Alembic revision 后方可执行。

## API 变更

无。任务运行记录不在本次定义新的外部查询或重试接口。

## Redis 变更

无。未来 Celery/Redis 任务实现须遵守本模型的幂等、状态和失败处理规则。

## 关键约束

- 资源状态与任务状态必须分离：资源表示下游是否可用，任务记录业务关联和终态审计，Celery 管理执行过程。
- 幂等键固定为 `{task_type}:{resource_id}:{task_version}`，并以资源、任务类型、任务版本和该键构成全量唯一约束；Celery 重试和重复投递只能复用同一任务运行。
- 上传事务同时创建资源和 `queued + celery_task_id = NULL` 的任务运行；独立、单实例 Dispatcher 在提交后以 Repository 行锁领取待投递记录，Broker 接受后才回填任务 ID，且不由 Celery Beat 驱动。投递与回填间中断允许同一任务运行 ID 的至少一次重复投递，Worker 通过原子领取与幂等写入保证不重复产生业务结果。
- 任务归属通过其资源归属链推导，禁止仅凭 `task_run_id` 访问候选人任务。
- 简历与岗位 JD 的异步解析共用 `parse_failure_code_enum`；关联终态 `async_task_runs.failure_code` 是资源失败原因的唯一权威来源，资源表不保存自由文本 `parse_error`。候选人附加资料不进入解析或异步任务。失败分类和追踪信息必须脱敏，不得保存简历原文、文件地址、模型原始响应或凭证。
- 最大重试次数、退避、下次重试时间、超时、Worker 运行时详情不进入业务模型，均以 Celery 任务配置和 Result Backend 为准。
- 候选人画像与成功解析简历一对一关联；`target_job_titles` 必填、只来自解析事实，并以至少含一个非空字符串的列表存储，单个职位使用单元素列表；`candidate_profile_generation` 任务类型和 `embedding_id` 均不属于当前 MVP 模型。候选人附加资料是原始消息附件资源，不使用任务类型或资源类型。
- Embedding、索引和检索不是资料处理流程的固定前置或固定步骤。

## 关联与实施状态

- 关联需求/变更包：CHG-2026-012、CHG-2026-015
- 当前状态：proposed；待异步任务物理数据模型和候选人资料准备设计评审时一并确认。

## 验收标准

- 业务模型能够明确表达任务运行、资源状态、Celery 关联、幂等、版本和脱敏失败分类。
- 候选人资料准备模块可依据模型区分“仍在重试”和“资源解析已终态失败”。
- 业务模型不重复保存 Celery 的最大重试次数、退避、下次执行时间或运行时计数。
- 数据模型为任务表及全部 Enum 字段定义独立枚举、索引和多态资源归属校验边界。

## 回滚方案

删除本次业务模型章节和提案变更包；不涉及运行时数据、Schema、API 或 Redis 回滚。
